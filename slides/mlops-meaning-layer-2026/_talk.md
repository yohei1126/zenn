<!-- _header: "A｜2026年の発表" -->

## A. 公開情報だと、つまりどういうことか

1. カタログ上のクエリ・BI・メタデータから **ビジネス定義の断片を自動抽出**
2. 利用統計で **「どれを信じるか」を裁定**（PageRank 型）
3. エージェントの推論ループに **コンテキストとして注入**

人手で全社オントロジーを先に書くのでも、LLM に Text-to-SQL を丸投げするのでもない **第三の道**

---

<!-- _header: "A｜2026年の発表" -->

## A. ユーザ便益

| 便益 | 内容 |
| :--- | :--- |
| **誤答の削減** | 「売上」など定義の取り違えが減る（*Context determines agent quality*） |
| **手メンテの軽減** | セマンティックビュー／モデルを全部人手で追い続けなくてよい |
| **エージェントの接地** | Genie / CoWork / CoCo が自社データに接地しやすい |

≠ OWL 公理全集　≠ グラフ書き込み拒否エンジンそのもの

<!-- _header: "B｜用語の系譜" -->

## B. オントロジーは新しい用語ではない

| 時代 | 意味 |
| :--- | :--- |
| **哲学** | 存在論 — 「何が存在するか」 |
| **1970年代 古典 AI** | 意味ネット／フレーム／記述論理。概念と関係を機械が推論するための知識表現 |
| **2000年代 セマンティック Web** | RDF / OWL。機械可読な共有意味と公理 |
| **2026 PF** | ビジネス定義 snippet の自動抽出・裁定・エージェント注入 |

同じ言葉でも、**何のために要るか** が時代で違う

---

<!-- _header: "C｜用語の違い" -->

## C. グラフ／知識グラフ／オントロジー

| 用語 | 違い |
| :--- | :--- |
| **グラフ** | ノードとエッジの **構造一般**（道路網・SNS も） |
| **知識グラフ** | 業務の実体と意味のある関係を載せた **実態** |
| **オントロジー** | 許される概念・関係の **設計図・契約**（型・制約） |

> 知識グラフ = オントロジー（契約）＋ 実態（データ）

---

<!-- _header: "C｜用語の違い" -->

## C. オントロジーがある／ない（例）

| 判定 | 関係 | 意味 |
| :---: | :--- | :--- |
| ✅ | `Supplier` → `Component` → `Product` | 許可されたパス |
| ❌ | `Supplier` —USED_IN→ `Product` | 関係の型が未許可 |

契約がなければ「壊れているか」を判断できない

<!-- _header: "D｜なぜグラフか" -->

## D. なぜ知識表現と推論にグラフを使うか

根拠: [シーズン1 第2部](https://zenn.dev/yohei/articles/2026-05-30-vkg-strategy2)

1. **多ホップ探索** — JOIN 爆発を避け、関係を辿る問題に自然  
2. **グラフアルゴリズム** — 最短経路、中心性、コミュニティ検出  
3. **グラウンディング** — 構造化コンテキスト・経路を LLM に渡し、ハルシネーションを抑制  

問題構造が **関係の連鎖** のとき特に効く（製造・SC・金融など）

---

<!-- _header: "E｜挫折" -->

## E. セマンティック Web のブームはなぜ挫折したか

- **主因: 知識獲得ボトルネック** — 人手で RDF/OWL を書き続けられない  
- 合意コスト・陳腐化・厳密推論の計算量は副因  
- 技術が間違っていたというより、**定義の供給と需要** がスケールしなかった  

製薬・医療など厳密統制が義務の領域に縮小

---

<!-- _header: "E′｜原理の違いと補完" -->

## E′. セマンティック Web 時代の AI と今の AI — 原理が違う

| | **記号処理の AI** | **ニューロンの AI**（深層学習・LLM） |
| :--- | :--- | :--- |
| **原理** | 知識を明示定義し、規則・論理で推論 | データから学習し、確率的に生成・判断 |
| **強み** | **厳密・正確**（定義どおりなら検証可能） | **柔軟**（全ルールを先に書かなくても対処） |
| **弱み** | **柔軟性がない**。知識獲得・定義が現実的でないと動かない | **正しさは保証できない**（ハルシネーション） |

> 厳密だが柔軟でない　×　柔軟だが厳密・正確でない  
> → **補完関係** に見える（どちらが上位ではない）

---

<!-- _header: "E′｜原理の違いと補完" -->

## E′. 補完は双方向に効くのでは

| 向き | 仮説 |
| :--- | :--- |
| **ニューラル → 記号** | LLM の柔軟性で、知識の **獲得・下書き・構築** がやりやすくなる |
| **記号 → ニューラル** | オントロジー／KG／決定論的ツール／グラウンディングで、**厳密さ・正確さ** を補う |

---

<!-- _header: "E′｜第三の壁と25年で一周" -->

## E′. ただし LLM 下書きだけでは回らない

1. LLM に獲得・構築を任せる → **間違いが起きる**  
2. 人間（ドメインエキスパート）のレビューが必要  
3. レビュー必須だと、また **人手ボトルネックで回らなくなる**  

**Databricks / Snowflake の考え（公開情報からの読み）**

- プラットフォームに溜まった **利用統計・履歴** からオントロジーを推定  
- エキスパート作業を経ずに **半自動** で意味レイヤーを育てる  

発想は **Google 知識グラフと同型**（行動から権威を推定）  
→ 入力が Web のリンクから **DWH の利用ログ** に変わっただけ  
→ **約25年で一周した**

## F. 今再び着目されているのはなぜか — 2つの文脈

| 文脈 | 内容 |
| :--- | :--- |
| **① PF（Databricks / Snowflake）** | 分析エージェント向けに、既存の **セマンティックビュー／カタログ意味を補強・自動裁定** する |
| **② RAG の限界を超える手法** | RDB・ベクトル DB・相互リンク MD では足りない **多ホップ関係探索・経路エビデンス** が要るとき |

同じ「再びオントロジー」でも、**動機が違う** — 混同しない

<!-- _header: "F′｜過渡期" -->

## F′. 自動構築＝セマンティックビュー不要、ではない

**まだ過渡期。PF が完全自動で完結するわけではない**

| | **ボトムアップ支援** | **トップダウン** |
| :--- | :--- | :--- |
| **やること** | シグナル・カタログ・認証アセットを整える | 意図・契約・柵を仕組みに押し込む |
| **系譜** | DE・基盤・ガバナンス | **EA／データアーキ／DM** の延長＋エージェントの柵 |

- Google KG も自動化と **キュレーションが併存** していたのと同型  
- 項目ごとの実務・コードは **Zenn / サンプル** へ（この場では列挙しない）

---

<!-- _header: "F｜再び着目 — 2文脈" -->

## F. 文脈① — セマンティックビューの補強

- 倉庫にはテーブルとセマンティックビューがあるが、**「売上」がどれか** は揺れる  
- PF の自動オントロジー = 利用ログから定義を裁定し、**エージェントのコンテキストを補強**  
- Google 知識グラフと同型: 人力で先に書かず、**行動データから逆算**

---

<!-- _header: "F｜再び着目 — 2文脈" -->

## F. 文脈② — RDB / ベクトル RAG では足りないとき

| 手法 | 得意 | 苦手 |
| :--- | :--- | :--- |
| ベクトル RAG | 似た文書 | 業務上つながる **遠い関係** |
| RDB / 定型 SQL | 集計・KPI | アドホックな多ホップ |
| 相互リンク MD | ゆるい関係 | 大規模・厳密な ID 連鎖 |
| **知識グラフ** | **関係の連鎖・経路の説明** | 構築・保守コスト |

---

<!-- _header: "G｜必須か" -->

## G. AI エンジニアに知識グラフ／オントロジーは必要か

**必ずしも必要ではない**

| 不要なことが多い | 必要になりやすい |
| :--- | :--- |
| FAQ・規程の意味検索 | 関係の **多ホップ** 探索 |
| 定型 KPI の集計 | エージェントが **経路で根拠** を残したい |
| まだエージェント要件がない | 部門横断の **ID 連鎖** |

RDB・ベクトル・Markdown で足りるなら、無理に KG にしない

---

<!-- _header: "H｜KGとオントロジー" -->

## H. 知識グラフだけではダメなのはどんな時か

| | 役割 |
| :--- | :--- |
| **知識グラフ** | **実態**（インスタンスのネットワーク） |
| **オントロジー** | 実態が適切に構築・更新されているかの **物差し**（型・制約） |

**オントロジーが必要になるとき**

- 複数人が更新する／壊れると損失が大きい  
- エージェントに勝手な経路を辿らせたくない  
- 「ちゃんとできているか」を説明・監査したい  

単発・小規模・壊れても安い実験なら、KG だけ（スキーマレス）でもよい場合がある

## I. DE / AI — 自社開発での位置づけ

```text
[ ③ プラットフォーム・コンテキスト ]  Genie Ontology / Cortex Sense  ← 文脈①
[ ② 組織フェデレーション ]            Bridge Keys + Graph Contract
[ ① コアドメイン ]                    型・制約の契約                 ← 文脈②の核
```

| 層 | DE | AI |
| :--- | :--- | :--- |
| **③** | カタログ・シグナル品質 | エージェントが何を引くか |
| **②** | 結合キー・契約の合意 | 決定論的ツールの前提 |
| **①** | 書き込み拒否・監査 | 辿ってよい関係の前提 |

**③は PF を使い、①②は人が固定する**  
（①②のスキーマ・ツール実装は [サンプル](https://github.com/yohei1126/supply-chain-impact-analysis-agent) / Zenn S2）
