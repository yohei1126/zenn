【口頭】0. タイトル（立ち上げのみ・十数秒） 大西と申します。普段は家電メーカーのDysonでデータとAIのプラットフォームアーキテクトとして働いています。 今日は、AIエージェントの知識表現と推論になぜグラフが使われるのか？記号的AIの復権とニューラルAIとの統合と題しまして発表します。 今回の発表のきっかけて、大手のベンダーが知識グラフやオントロジという技術への対応を強めていっている歴史的な背景についてブログに書いたところ、運営の方から勉強会で話しませんか？とお声かけいただき登壇しました。よろしくお願いします。

【口頭】1. 本発表の概要 今日は、知識グラフやオントロジーがなぜ再び注目されているのかを、RAGや既存システムとの関係、古典的AIからの系譜とともに整理します。 実装の詳細ではなく、どのような課題で必要になるのか、どこを人間が設計すべきか、判断するための地図を共有します。 知識グラフやオントロジは万能でも必須でもありません。自社の課題に照らして使うかどうかを考える視点を持ち帰っていただくことを目標とします。

【口頭】2. Databricks / Snowflake が発表したもの 最初に知識グラフやオントロジが、データやAI業界で注目されているという事実関係の紹介のため、 Databricks / Snowflake が今年のサミットで発表した内容を公開情報の範囲で紹介します。 Databricks は今年 Genie Ontology という機能を発表しました。これはプラットフォームに内蔵するデータカタログに蓄積する、メタデータや利用履歴から自社データの意味や定義に相当するオントロジというものを自動構築し、エージェントのコンテキストに注入することで、エージェントがより自社のデータについて深く理解できるようになり、適切にデータを分析できるようにするというものです。 Snowflakeの方は、Databricksよりも先にサミットを開催し、CoWorkというビジネスユーザが直接使うエージェント機能を紹介し、明示的ではありませんが、実はその背後にGenie Ontologyとほぼ同等のことを行う、Cortex Senseという機能の存在をひっそりと紹介していました。 これまでの業界の路線は、どちらかというと、物理テーブルのメタデータとビジネス上のメトリクスをマッピングする定義を人間が事前に用意するというものでした。これら業界ではセマンティックビューと呼ばれています。 つまりは人間のドメインエキスパートがやっていたことをプラットフォームが半自動でやることを宣言していたのです。 私自身は業務で使うグラフDBをLLMの支援を受けながら設計していましたが、その時にオントロジを整備してLLMに提示するとLLMによるグラフスキーマ設計が改善するという議論を聞いていたので、それが半自動化することに驚きました。

【口頭】3. 知識グラフとオントロジーとは何か ここで冒頭に出てきた用語の意味を解説させてください。 グラフというのは、点と線で関係を表す構造の一般名です。道路網やSNSもグラフです。 これに対して、知識グラフは、そのうち業務の実体と意味のある関係を載せたもので、実態・データの側です。 オントロジは、対象領域にどんな概念があり、どんな関係が許されるか、という知識グラフの構造や制約事項を定義したものです。 オントロジには、実態がありません。 RDB でいえば、オントロジーがテーブルスキーマ・制約、知識グラフが実際のレコード、とざっくり捉えてください。 さきほど、私が「グラフ設計の際にオントロジーを LLM に渡すと組み立てやすい」は、物差しがあると取り出し方が揃いやすい、という意味でした。

【口頭】4. 例: SPDM の簡易オントロジ 用語の解説をしましたが、実際にオントロジってどういうものか知りたい人も多いと思いますので、ここで具体例を示したいと思います。 製造業でよくある例として SPDM（Simulation Process and Data Management）を紹介します。これは製品の設計時に行う数値シミュレーションの手順と結果を扱う領域—です。このSPDMを例にしてオントロジーを作るとどうなるでしょうか？ オントロジの特徴は、概念同士をつなぐことです。矢印の元が主語、先が目的語、矢印が述語です。よって普通の文章として読み下しができます。 製品や部品は CAD モデルを持つ。部品は、ある解析ケースとして解析される。解析ケースはソルバーを使い、メッシュ・材料・荷重条件などを入力として取り、解析実行を生み、結果を得る。解析の要件や条件の根拠になるのは、顧客や製品の要求仕様、設計仕様・設計基準、試験仕様・試験規格、法規・安全規格といった仕様書である。 今読み上げた文章と図の **型と関係**がオントロジー、このオントロジを具現化し、実際の部品や実行結果などの事実や知識を埋め込んだものが知識グラフです。 知識グラフは単独では存在せず、実際にはワークフローや CAE やストレージなど SoR などと連動して動き、各システムの情報を関係を統合するのが知識グラフで、その構造を規定するのがオントロジです。

【口頭】5. グラフは既存システムを置き換えない 次にグラフは既存システムを置き換えないという話をします。 というのも、一時期、知識グラフがあれば SaaS や SoR を置き換えられる、不要にできる。そういう議論が一時期囁かれました。そんなことはありません。 グラフは既存のシステムを置き換えません。むしろ、バラバラに存在したシステムやデータを関連付けて、統合するために存在します。 さきほどの SPDM で言うと、ワークフロー管理システムは、解析ケースの進行や承認などのワークフローを担当します。 CAD や PDM にはモデル本体とバージョン管理を担当します 数値シミュレーション（CAE） 側にはジョブやソルバー設定、実行ログを置く。 オブジェクトストレージには、メッシュや結果の大容量ファイルを置く。 仕様書の本文は文書管理やベクトルで意味検索する。 グラフが持つのは、それらの ID と関係 —— 部品とケースと実行と結果と仕様をたどれるようにする部分だけです。 ワークフローやストレージを消す話ではありません。

【口頭】6. RAG の地図 — いつグラフが候補になるか グラフは既存システムを置き換えないという話をしましたが、LLMへのコンテキスト提供手段としても他を代替するものでもありません。 似た文書ならベクトル。正確な集計なら RDB やセマンティックレイヤー。ローカルの文書検索ならAgentic Search。 知識グラフが効きやすいのは、厳密な関係を多段で辿り、経路を説明したいときです。 知識グラフRAGは他の手段を置き換えません。むしろ適材適所でこれらを総動員し、適材を適所に配置する。知識グラフをRAGに使うのは、システムやデータをつなげて全体を統合する、関係を探索するところです。前のスライドと同じで、置き換えではなく統合の道具です。

【口頭】7. グラフである必要はあるか — 必須ではない ただし常に物理的にグラフとしてDB永続化にする必要はありません。選択肢は増えていってますので、設計判断は規模や複雑さによります。 関係が少なく人が読める程度なら、設定ファイルに書いておけばよい。 RDB にポインタを持って SQL でもよい。 グラフ的に分析したいだけなら、SparkやPostgreSQL の仮想グラフ機能を使い、メモリ上でグラフ分析もできます。 関係が大きく複雑で多段探索を速く回したいとき、物理グラフDBを構築する、という幅があります。 製造業の SPDM のように組み合わせが爆発する領域では、結果として物理グラフDBを選ぶことも多い。 しかし、最初から必須、ではない。

【口頭】8. なぜ知識表現と推論にグラフを使うのか — 古典からの蓄積を使える ここまでは、システムを作る際のグラフやオントロジの使いどころを中心に話しました。 ここからは、なぜAIの知識表現と推論にグラフが選ばれるのか歴史的な背景について紹介します。 大きな理由は、古典的な研究からの蓄積を利用できることです。利点は少なくとも二つあります。 一つ目は、**古典的 AI からの知識表現と推論の研究蓄積を使える**こと。概念と関係で世界を書く発想は古典哲学にもあり、古典的 AI では意味ネットワークやフレーム、2000年代にはセマンティック Web の RDF や OWL として標準化が進みました。数学的・論理的に知識を扱う理論が、すでに載っている、ということです。 二つ目は、**グラフアルゴリズムが便利**なこと。最短経路、中心性、コミュニティ検出など、関係の上で回りたい定石がそのまま使えます。同じことを SQL の再帰や手書きでやるより、簡単ですし、便利です。 つまりグラフは、知識表現・推論と解析の両方で既存資産に乗りやすい形です。ただし、この系譜は一度挫折しています。次は、セマンティック Web の挫折を見ます。

【口頭】9. なぜ過去10年ほど聞かなかったか — セマンティック Web の挫折 現代で、知識グラフやオントロジーが再びAIの分野で話題になっています。しかし、過去10年ほど、ほとんど聞かなかったのはなぜか。 それは、2000年代にオントロジーの最大のアプリであったセマンティック Web という技術が全く普及せず、オントロジーに対する失望が生まれたからです。 セマンティック Web を簡単に説明すると、世界規模に広がったWWW上に展開する世の中の知識に対して、数学的・論理的に厳密にメタデータを書きさえすれば、機械が推論できる、というものでした。 理論的には素晴らしいですが、実際には２つの理由で普及せずに終わりました。 全ての知識を人力で厳密に書き続けるには労力が足りない、という知識獲得の壁がありました。 もう一つは、厳密推論は計算が重く、当時のコンピュータでは実務規模で回せないことが多かった、という計算資源・計算量の壁です。 一方で、セマンティックWebの時代に知識グラフ構築の成功例が１個ありました。次はそれを紹介します。

【口頭】10. Google 知識グラフの成功（2010年代） グラフによる知識構築はセマンティックWebの失敗で終わったのかというと、そうではありません。 2010年代の知識グラフの成功例としてよく上がるのがGoogleの検索エンジンです。 Googleの検索エンジンでは、裏側で概念のグラフ構造を自動的に作る処理が行われており、検索キーワードに関連する概念を芋づる式に引っ張り、より深い文脈の検索結果を出せるようにするものです。 ではなぜGoogleは成功したか。ポイントは、統計処理、機械処理、アルゴリズム、そして巨大な分散システムというアプローチが非常に効率的だったから、ということです。Web 規模のシグナルから半自動で実体と関係を集め、権威付けや結線を機械で回す。人手のキュレーションがゼロだったわけではないと思いますが、人力に長く頼る部分はスケールしない——そこを主戦場にしなかったのが、前のセマンティック Web 寄りと違うところです。

【口頭】11. なぜ今またグラフとオントロジが着目されるか — 記号 × ニューラル 一度はセマンティックWebで挫折した知識グラフとオントロジー。なぜ今また着目されているか。 自分の見立てでは、古典的 AI の時代のAI、つまり記号的 AI の弱点を、現代のAIつまりニューラル AI（代表例はLLM）が補えるようになったからです。 記号的 AI は、硬く、厳密で正確、再現しやすい。一方で融通が効かず、管理コストが高い。 LLM を代表とするニューラル AI は、柔らかい、柔軟でそれっぽく使える。ただ厳密性に欠け、間違うことがある。 両者は正反対の性質なので、補完関係にあり、組み合わせるとうまくいきそうです。 LLM を使えば、セマンティックWebの時にボトルネックであった知識の獲得・構築がスムーズになります。 構築した知識構造に対して記号的AIによる検証結果（例えば、知識グラフ上の決定論的なクエリ）は、 LLM による推論の妥当性検証（グラウンディング）に使えます。

【口頭】12. 獲得・構築・保守に、またボトルネック LLM で知識の獲得・構築はスムーズになりましたが、それでも **ボトルネックはあります**。LLM の結果は間違っているかもしれないので、人手での下書きやレビューが必要になり、労力がかかります。一方で、エキスパートが厳密に書こうとするとスケールしない。結局、セマンティック Web と同じ問題に陥ります。 そこで現代のプラットフォーム達が2010年代と同じ解決策をたどります。

【口頭】13. PF 再訪 — Google と同じ構成が、いまも続く 最初に紹介した Snowflake の Cortex Sense、Databricks の Genie Ontology に話が戻ります。彼らは、プラットフォームに溜まった統計情報や履歴からデータの定義や意味をオントロジーとして自動構築し、AI が推論できるようにしています。Web リンクがカタログの利用ログに変わっただけで、**統計・機械処理でスケールさせる構成は、2010年代のGoogleと同じ解決方法が続いています**。 LLM に下書きをさせる道とも、人がOWLを全部書く道とも違います。知識獲得の壁を、プラットフォームの利用シグナルで迂回する道を現代に再度再現する事例が出てきました。

【口頭】14. まだ始まったばかり — 人間のモデリングは続く プラットフォームによるオントロジー構築は、まだ始まったばかりです。いまは、特定のベンダーがプラットフォーム依存の技術としてオントロジーを自動構築する機能を出し、世間に普及しつつあります。それ以外の製品は対応していないので、**全ての人が恩恵を受けるわけではありません。** また、2010年代にGoogleが知識グラフを自動構築したとしても、人間が情報を編集するキュレーションメディアというのが流行ったのを覚えている方は覚えていると思います。 もしオントロジ構築が自動化されたとしても、機械が適切にオントロジを構築できるようにヒントをあげる仕事は続くと思います。 また、機械が利用履歴を元にボトムアップでオントロジ構築を自動化する流れとは並行して、人間のドメインエキスパートがトップダウンでドメインモデリングを行う道はまだ残るのではないでしょうか？

【口頭】15. 現代のデータエンジニアリングの道具としてのオントロジー では、今現在でエンジニアはどうするべきか。 私自身は先ほど紹介したSPDMのようなオントロジを、ドメインエキスパートから提供してもらった情報、システムのデータなどを元に、LLMの支援を受けながら、オントロジを設計しています。 オントロジーには、グラフのスキーマと制約事項がこうなるべきだという情報を **YAML 形式で定義**できるようにしています。 そこから **Pydantic モデルを自動生成**し、グラフDBにデータを投入する際の入力データのバリデーションに利用しています。 データをグラフDBに投入したあと、グラフが壊れていないことを確認するため、**Cypher で非同期に検証**しています。 つまりオントロジは哲学論や概念論ではなく、データ基盤の維持管理を楽にするデータエンジニアリングの道具として再解釈しています。

【口頭】16. まとめ — 持ち帰り 一点目、知識グラフとオントロジーが知識構造と推論に有効な分野がある。しかし知識獲得・構築・保守にボトルネックがあり、LLMがあっても消えていません。 二点目、Snowflake や Databricks は Google と同じように、プラットフォーム の統計や履歴からオントロジーを自動構築し始めています。ただまだ始まったばかりで、全員の恩恵ではなく、**人間がモデリングする時代は続きます**。 三点目、グラフは既存システムやほかのRAG手法を置き換えず、あくまでもデータを繋ぐ目的で使います。オントロジーはグラフ構築のスキーマ・制約・検証を楽にする道具として使います。

【口頭】17. CTA — Zenn と GitHub 今回の発表の詳細や続きは、Zenn の連載にあります。シーズン1は仮想グラフ、シーズン2は論理フェデレーション、シーズン3は定義をどう信頼するか、シーズン4は現代の知識グラフとオントロジー。それぞれ第1部へのリンクを載せています。 サンプルコードは GitHub の supply-chain-impact-analysis-agent にあります。 ご清聴ありがとうございました。

【口頭】おまけ A. Palantir — 複数 SoR の統合とオントロジー（本編の SPDM との接続） 本編では省略した先例です。エンタープライズでオントロジーが再び話題になるとき、よく引き合いに出るのが Palantir です。陸・海・空・宇宙といった、もともと別系統——要するに複数の System of Record やドメインのデータを、オントロジーで統合して作戦を立案する、という意味で **統合の物差し** として使われてきました。本編の SPDM の例も、複数系統に分かれがちなデータを関係の型でつなぐ、という点では同型です。製品の細部は今日は扱いません。

【口頭】おまけ B. 推論の理論の例（古典〜セマンティック Web） 本編の「なぜ知識表現と推論にグラフを使うのか」の補足です。推論の例を四つだけ挙げます。一つ目は属性の継承。is-a の連鎖をたどって性質を引き継ぎます。二つ目はルールベースの前向き・後ろ向き推論。条件が揃えば結論を出したり、目標から必要な前提を逆にたどったりします。三つ目は OWL の基盤にある記述論理で、概念の包含や矛盾を形式的に見ます。四つ目は RDF の三つ組で、事実を主語・述語・目的語として書き、機械が扱えるようにします。 いずれも、「関係でつながった記号」の上で手続きが定義されてきた、という意味でグラフと相性がよいです。厳密に書き続ける・大規模に回すコストが挫折につながった、という本編の話ともつながります。

【口頭】おまけ C. 2つの文脈を混同しない ここで一度だけ、地図にラベルを貼ります。新しい話ではありません。経緯の入口と、PF の路線に名前を付けるだけです。 一つ目は、定義やセマンティックビューの揺れをどう信じるか——Sense や Genie、RDB から定義を揃える側はこっちです。二つ目は、バラバラのデータを関係で辿るか——数年前からグラフDBを置いてきた側で、SPDM や RAG 地図の「グラフが候補」もこっちです。PF と同じ構成が続く、と言ったのは主に一つ目。自分の話が長かったのは二つ目側からです。最初に言った「オントロジーが半自動なら知識グラフ構築が楽になる」は、①が進むと②の構築も楽になる、という交差の仮説でした。言葉は似ているので、混ぜないでください。本編では時間の都合で省略し、まとめでは置き換えない／必須ではない、に寄せています。
