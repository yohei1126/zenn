<!-- _header: "3｜オントロジーと知識グラフとは何か" -->

## 知識グラフとオントロジーとは何か？

| 用語         | 何か                            |
| ---------- | ----------------------------- |
| **グラフ**    | ノードとエッジの **構造一般**（道路網も SNS も） |
| **知識グラフ**  | 業務の実体と、意味のある関係を載せた **実態**     |
| **オントロジ** | 許される概念・関係の **設計図・物差し**（型・制約）  |

例: 

- 「部品 —使われる→ 製品」は許可。
- 「サプライヤー —使われる→ 製品」は型としておかしい、と止められるのが物差し側。

<!--
【口頭】3. 知識グラフとオントロジーとは何か

ここで冒頭に出てきた用語の意味を解説させてください。
グラフというのは、点と線で関係を表す構造の一般名です。道路網やSNSもグラフです。
これに対して、知識グラフは、そのうち業務の実体と意味のある関係を載せたもので、実態・データの側です。
オントロジは、対象領域にどんな概念があり、どんな関係が許されるか、という知識グラフの構造や制約事項を定義したものです。
オントロジには、実態がありません。

RDB でいえば、オントロジーがテーブルスキーマ・制約、知識グラフが実際のレコード、とざっくり捉えてください。
さきほど、私が「グラフ設計の際にオントロジーを LLM に渡すと組み立てやすい」は、物差しがあると取り出し方が揃いやすい、という意味でした。
-->

<!-- _header: "4｜例: SPDM の簡易オントロジ" -->

## 例: SPDM の簡易オントロジ（製造業）

**SPDM** = Simulation Process and Data Management

設計工程における数値シミュレーションの流れ・条件・結果を一つの枠でつなぐ管理

```text
[要求・設計・試験などの仕様書]──根拠となる──▶[解析要件]／[解析条件]
                              │
[製品／部品]──モデルを持つ──▶[CADモデル]
       │ 解析する
       ▼
[解析ケース]──使う──▶[ソルバー]
       ├──入力──▶[メッシュ] / [材料] / [荷重条件]
       └──生成──▶[解析実行]──▶[結果]
```

<!--
【口頭】4. 例: SPDM の簡易オントロジ

用語の解説をしましたが、実際にオントロジってどういうものか知りたい人も多いと思いますので、ここで具体例を示したいと思います。

製造業でよくある例として SPDM（Simulation Process and Data Management）を紹介します。これは製品の設計時に行う数値シミュレーションの手順と結果を扱う領域—です。このSPDMを例にしてオントロジーを作るとどうなるでしょうか？

オントロジの特徴は、概念同士をつなぐことです。矢印の元が主語、先が目的語、矢印が述語です。よって普通の文章として読み下しができます。
製品や部品は CAD モデルを持つ。部品は、ある解析ケースとして解析される。解析ケースはソルバーを使い、メッシュ・材料・荷重条件などを入力として取り、解析実行を生み、結果を得る。解析の要件や条件の根拠になるのは、顧客や製品の要求仕様、設計仕様・設計基準、試験仕様・試験規格、法規・安全規格といった仕様書である。

今読み上げた文章と図の **型と関係**がオントロジー、このオントロジを具現化し、実際の部品や実行結果などの事実や知識を埋め込んだものが知識グラフです。

知識グラフは単独では存在せず、実際にはワークフローや CAE やストレージなど SoR などと連動して動き、各システムの情報を関係を統合するのが知識グラフで、その構造を規定するのがオントロジです。
-->

<!-- _header: "5｜グラフは既存システムを置き換えない" -->

## グラフはデータ統合のための足場である - 既存システムを置き換えない

| 置き場（SoR／基盤）            | 何を置くか（例:SPDM）                            |
| -------------------         | ---------------------------------              |
| **ワークフロー管理**           | 解析ケースの進行、承認、タスク状態                   |
| **CAD (Computer-Aided Design)／ <br/>PDM (Product Data Management)** | CAD モデル本体、版管理 |
| **CAE (Computer-Aided Engineering)** | ジョブ定義、ソルバー設定、実行ログ                    |
| **オブジェクトストレージ**      | メッシュ／結果ファイル（大容量バイナリ）               |
| **文書管理 or ベクトル**       | 要求・設計・試験などの **仕様書本文**（意味検索）      |
| **グラフ**                   | 上記の **ID と関係**だけ（部品↔ケース↔実行↔結果↔仕様） |

<!--
【口頭】5. グラフは既存システムを置き換えない

次にグラフは既存システムを置き換えないという話をします。

というのも、一時期、知識グラフがあれば SaaS や SoR を置き換えられる、不要にできる。そういう議論が一時期囁かれました。そんなことはありません。 グラフは既存のシステムを置き換えません。むしろ、バラバラに存在したシステムやデータを関連付けて、統合するために存在します。

さきほどの SPDM で言うと、ワークフロー管理システムは、解析ケースの進行や承認などのワークフローを担当します。
CAD や PDM にはモデル本体とバージョン管理を担当します
数値シミュレーション（CAE） 側にはジョブやソルバー設定、実行ログを置く。
オブジェクトストレージには、メッシュや結果の大容量ファイルを置く。
仕様書の本文は文書管理やベクトルで意味検索する。
グラフが持つのは、それらの ID と関係 —— 部品とケースと実行と結果と仕様をたどれるようにする部分だけです。
ワークフローやストレージを消す話ではありません。
-->

<!-- _header: "6｜RAG の地図 — いつグラフが候補になるか" -->

## RAG／知識取得の地図（得意／苦手）

グラフが何かを置き換えると言うより、これら全てを適材適所で総動員する

| 手法                        | 得意              | 苦手になりやすい         |
| ------------------------- | --------------- | ---------------- |
| **ベクトル**                  | 似た文書・仕様書の意味検索   | 厳密な論理関係の多段追跡     |
| **RDB / SQL・セマンティック層**    | 集計・定型の正確な数値     | アドホックな多ホップ       |
| **Agentic Search**（リンク巡回） | ゆるい文書網の探索       | 大規模構造化・厳格な ID 連鎖 |
| **知識グラフ**                 | **関係の連鎖・経路の説明** | 構築・保守コスト（必須ではない） |

<!--
【口頭】6. RAG の地図 — いつグラフが候補になるか

グラフは既存システムを置き換えないという話をしましたが、LLMへのコンテキスト提供手段としても他を代替するものでもありません。

似た文書ならベクトル。正確な集計なら RDB やセマンティックレイヤー。ローカルの文書検索ならAgentic Search。
知識グラフが効きやすいのは、厳密な関係を多段で辿り、経路を説明したいときです。

知識グラフRAGは他の手段を置き換えません。むしろ適材適所でこれらを総動員し、適材を適所に配置する。知識グラフをRAGに使うのは、システムやデータをつなげて全体を統合する、関係を探索するところです。前のスライドと同じで、置き換えではなく統合の道具です。
-->

<!-- _header: "7｜物理グラフである必要はあるか — 必須ではない" -->

## 常に物理グラフである必要はない — 規模や複雑さによる

| やり方         | 向くとき（ざっくり）              |
| ----------- | ----------------------- |
| **設定ファイル**  | 関係が少なく、人が読んでメンテできる      |
| **RDB＋SQL** | 結合パスが既知・定型で足りる          |
| **仮想グラフ** <br/>(Spark, PostgreSQL など） | グラフ的に見たいが専用DBなしで済ませたい   |
| **物理グラフDB** | 関係が大規模・複雑で、多段探索を高速に回したい |

<!--
【口頭】7. グラフである必要はあるか — 必須ではない

ただし常に物理的にグラフとしてDB永続化にする必要はありません。選択肢は増えていってますので、設計判断は規模や複雑さによります。
関係が少なく人が読める程度なら、設定ファイルに書いておけばよい。
RDB にポインタを持って SQL でもよい。
グラフ的に分析したいだけなら、SparkやPostgreSQL の仮想グラフ機能を使い、メモリ上でグラフ分析もできます。
関係が大きく複雑で多段探索を速く回したいとき、物理グラフDBを構築する、という幅があります。

製造業の SPDM のように組み合わせが爆発する領域では、結果として物理グラフDBを選ぶことも多い。
しかし、最初から必須、ではない。
-->

## なぜ知識表現と推論にグラフを使うのか — 古典からの蓄積を使える

### 1. **知識表現・推論の蓄積** — 古典的 AI／セマンティック Web の資産に乗れる

- **古典哲学**:「存在・概念・関係」で世界を整理する発想（オントロジーの語源） 
- **古典的 AI（1970s〜）**: **意味ネットワーク**／フレーム。概念をノード、関係をエッジで表現
- **2000年代**: **セマンティック Web**。**RDF**（三つ組）・**OWL**（より厳密な意味・制約）

### 2. **グラフアルゴリズムが便利** — 探索・重要度・クラスタを定石で使える

- 最短経路、中心性（PageRank 等）、コミュニティ検出
- SQL 手書きより格段に楽   

<!--
【口頭】8. なぜ知識表現と推論にグラフを使うのか — 古典からの蓄積を使える

ここまでは、システムを作る際のグラフやオントロジの使いどころを中心に話しました。
ここからは、なぜAIの知識表現と推論にグラフが選ばれるのか歴史的な背景について紹介します。
大きな理由は、古典的な研究からの蓄積を利用できることです。利点は少なくとも二つあります。

二つ目は、**グラフアルゴリズムが便利**なこと。最短経路、中心性、コミュニティ検出など、関係の上で回りたい定石がそのまま使えます。同じことを SQL の再帰や手書きでやるより、簡単ですし、便利です。

つまりグラフは、知識表現・推論と解析の両方で既存資産に乗りやすい形です。ただし、この系譜は一度挫折しています。次は、セマンティック Web の挫折を見ます。

## なぜ最近までオントロジ・知識グラフが話題にならなかったか

- 2000年代、オントロジー最大のアプリ＝**セマンティック Web** が普及せず、 **オントロジーへの失望**が生まれたから
- セマンティック Webの目標 - 世の中の知識を **数学的・論理的に厳密に書きさえすれば、機械が推論する**
- 全ての知識を人力で厳密に書き続けるには、労力が足りない
- 厳密推論は重い。当時のコンピュータでは実務規模で回せないことが多かった

## なぜ今また着目されているか

- 古典的 AI 時代の **記号的 AI** の弱点を、 **ニューラル AI（LLM）** が補えるようになった
- LLMで知識の獲得・構築がスムーズになる
- 構築した知識構造で推論の妥当性を検証（**グラウンディング**）

|         | **記号的 AI**              | **ニューラル AI（LLM）** |
| ------- | ----------------------- | ----------------- |
| **たとえ** | コンクリート（硬い）              | スポンジ／粘土（柔らかい）  |
| **強み**  | 厳密・正確・再現しやすい            | 柔軟・それっぽく使える     |
| **弱み**  | 融通が効かない／管理コストが高い      | 厳密性に欠ける／間違う    |
| **例**   | ルール、RDF/OWL、KG上の決定論的クエリ | **LLM**               |

## 推論の理論の例（ごく簡易）


| 例                 | 何をするか                    | イメージ                       |
| ----------------- | ------------------------ | -------------------------- |
| **属性の継承**         | is-a の連鎖から性質を導く          | 部品A is-a 金属部品 → 密度の扱いを引き継ぐ |
| **前向き／後ろ向き推論**    | If-Then 規則を適用／目標から前提をたどる | 「温度超過なら要再設計」を事実に適用         |
| **記述論理（OWL の基盤）** | 概念の包含・矛盾を形式的に判定          | 「この型定義は矛盾していないか」           |
| **三つ組（RDF）**      | 主語・述語・目的語で事実を書く          | 〈解析実行003, 出力, 結果X〉         |


ポイント: グラフ（ネットワーク）表現は、こうした **記号的な推論手続きと相性がよい**  
（ただし厳密推論のスケール限界は、本編で触れたセマンティック Web 挫折の種でもある）

| **手段**        | 利用統計で定義を裁定しエージェントへ          | 知識グラフ＋物差し（必要なら。必須ではない）        |
