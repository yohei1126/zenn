# AI エージェントの知識表現と推論に
# なぜグラフを使うのか

知識グラフ・オントロジー・記号AIの復権

**大西 洋平** · MLOps 勉強会 · 2026/07

<!-- _header: "序論" -->

## エージェントは「売上」のどれを指すかわからない

ユーザーが **「売上を教えて」** と言っても、エージェントは自社の **どの売上** を指しているか持っていない

- 税込 / 税抜、出荷ベース / 受注ベース、連結 / 単体、事業部別、会計基準…
- 自社のデータアーキテクトに聞いたら — **「売上」の定義は文脈依存で数百種類以上ある」**

CoWork / Genie など分析エージェントが普及しても、現場の摩擦は **SQL が書けるか** ではなく **どの定義を選ぶか**

> ボトルネックは LLM ではなく **意味の層**（定義・関係・信頼すべき資産）

## 仮想グラフ — データを動かさず関係を載せる

| プラットフォーム | 提供形態 | 製品・機能 |
| :--- | :--- | :--- |
| **Google Cloud** | **単独**（自社統合） | BigQuery Graph / Spanner Graph（GQL） |
| **Snowflake** | **Neo4j 共同** | Neo4j Virtual Graph on Snowflake |
| **Databricks** | **Neo4j 共同** | Neo4j Virtual Graph on Databricks |

- **Google** … DWH / OLTP 双方にグラフ機能を **自前で内蔵**
- **Snowflake・Databricks** … レイクハウス上のデータを **Neo4j と連携**（ゼロコピー、Cypher）

**GQL / Cypher** → DWH 上のテーブルをノード/エッジとして辿る

## 対比 — 物理グラフ DB

| | 仮想グラフ | 物理グラフ |
| :--- | :--- | :--- |
| データの置き場 | **DWH に置いたまま** | 専用 DB へコピー |
| 強み | ガバナンス維持、導入の軽さ | トラバース性能、型の厳密固定 |
| 弱み | SQL 変換オーバーヘッド | ETL・二重管理・運用コスト |
| 狙い | 分析・GraphRAG の **入口** | **競争領域** のコアドメイン |

<!-- _header: "第1節｜いまのプラットフォーム" -->

## これらの狙い（なぜ同時に出たか）

1. 「売上」「MQL」など **定義の裁定** がエージェントの品質を決める
2. 物事の関係性で定義の裁定を行うグラフ・オントロジ手法の普及、しかしRDBは多ホップ探索が苦手
3. DWH 外への ETL コピーは **RLS・ガバナンス崩壊** を招く
4. 人力で全部書くオントロジーは **メンテナンスが破綻** しやすい

→ **辿り方（仮想グラフ）** と **定義裁定（自動オントロジー）** を PF が担う

## グラフとオントロジーとは何か

- **グラフ** … ノード（実体）＋エッジ（関係）で意味を表す
- **オントロジー** … 「どんな概念があり、どんな関係が許されるか」の設計図
- **知識グラフ** = オントロジー（TBox）＋ データ（ABox）

---

<!-- _header: "第2節｜歴史 — 1970年代から自動オントロジーまで" -->

## オントロジーによる意味検証の例：部品・製品・工程・サプライヤー
| 判定 | 関係 | 意味 |
| :---: | :--- | :--- |
| ✅ | `Supplier` ──**SUPPLIED_BY**──► `Component` | サプライヤーが部品を供給|
| ✅ | `Component` ──**USED_IN**──► `Product` | 部品が製品に使われる|
| ✅ | `Product` ──**PRODUCED_BY**──► `Process` | 製品が工程で作られる|
| ❌ | `Supplier` ──USED_IN──► `Product` | 関係の型が未許可|
| ❌ | `Process` ──SUPPLIED_BY──► `Supplier` | 工程と供給の結び方が不正|

サプライヤー停止の波及: `Supplier` → `Component` → `Product` → `Process` — **許可されたパスのみ** 辿れる

## セマンティック Web とは

**[Tim Berners-Lee](https://www.w3.org/People/Berners-Lee/)**（WWW 発明者）が 2000 年代に提唱

- Web ページを **人間が読む HTML** だけでなく、**機械が理解できる意味** で記述する
- 各ページ・各データに **厳密なメタデータ**（RDF のトリプレット：主語・述語・目的語）
- 共有 **オントロジー（OWL）** と **推論エンジン** で、ソフトウェアが自律的に結合・判断

> 今日の **AI エージェント** に近い構想 — ただし LLM ではなく **記号的・論理的** な Web

---

<!-- _header: "第2節｜歴史 — 1970年代から自動オントロジーまで" -->

## セマンティック Web が挫折した理由

- **厳密** だが **構造を人力で作り保守** するのが現実的でなかった
- 全 Web ページへの RDF 埋め込み・定義合意 — **知識獲得のボトルネック**
- 推論エンジンは動くが **入力がスケールしない** → 表舞台からフェードアウト

---

## Google 知識グラフの大成功（2012年〜）

- **ナレッジグラフ** … 実体（entity）と事実をつないだ巨大なグラフ（[Google 公式説明](https://blog.google/intl/ja-jp/products/explore-get-answers/2020_05_knowledgegraphknowledgepane/)）
- **ナレッジパネル** … 検索結果に出る要約ボックス（右図）— グラフから主要事実を自動表示
- Wikipedia・ライセンス DB・ウェブ全体から **自動収集**（万人に RDF/OWL を書かせない）

![w:880](./google-kg.png)

Florence Price の例 — 生没年・作品・関連リンクが **構造化されたパネル** として表示

| セマンティック Web | Google 知識グラフ |
| :--- | :--- |
| 人間が RDF/OWL を書く | **公開データ＋検索行動** から自動構築 |
| トップダウンで合意 | **ボトムアップ** でエンティティを識別 |

**人力で意味を先に定義する** のではなく **利用行動と既存データから意味を逆算する**

## LLM 時代 — RAG と限界

| 手法 | 得意 | 苦手 |
| :--- | :--- | :--- |
| ベクトル RAG | 似た文書の検索 | 業務上つながる **遠い関係** |
| RDB / Text-to-SQL | 構造化クエリ | スキーマ誤読・幻覚 |
| Agentic Search | ローカルファイル探索 | 大規模構造・RLS・再現性 |

LLM は **柔軟** だが **厳密さが足りない** → 記号AI時代の骨格が再登場

## どの道も困難 → 統計的オントロジー自動構築

| 道 | 限界 |
| :--- | :--- |
| ① 人力オントロジー / グラフ構築 | メンテナンス破綻（LLM 支援でも検証・保守が重い） |
| ② Text-to-SQL / RAG 丸投げ | 定義誤り・幻覚・多ホップ関係に弱い |
| **③ 統計的構築** | シグナル貧弱だと矛盾を増幅 |

**2026年 — OntoRank / Cortex Sense** … クエリログ・BI から snippet 抽出し、利用統計で定義を裁定

**Google 知識グラフと同じアイデア** — 人力で意味を先に書かず、**行動データからオントロジーを逆算する**

## 現実のプロジェクトでどうするか

**仮説**

- **プラットフォームで自動化される部分** と **人間（ドメインエキスパート）が明示的に設計する部分** が **共存** する
- 役割とスコープがはっきりした **ドメインごと** にオントロジー・グラフを作る
- それらを **論理的にフェデレーション（連合）** して問題を解く（物理統合はしない）
- 連合するとき **結合の約束事** が必要 — 共通IDと、どの順序でつなぐか

---

<!-- _header: "第3節｜現実のプロジェクトでどうするか" -->

## 設計の原則（全体）

| 原則 | 方針 |
| :--- | :--- |
| 自動構築 | **使えるなら使う**（③ プラットフォーム層） |
| グラフの置き方 | **仮想グラフを基本**、物理グラフの保守は避ける |
| 物理グラフ | **競争領域のコアドメインだけ** |
| 厳密オントロジー | **OWL 等は最後の手段** |

---

<!-- _header: "第3節｜現実のプロジェクトでどうするか" -->

## 段階的な厳密さ — 「簡易オントロジ」から OWL へ

**OWL のような厳密手法は開発速度を落とす** — 全プロジェクトがその厳密さを要するわけではない。**要件ごとに適度な厳密さ** を選ぶ

| 段階 | 手法 | 役割 |
| :--- | :--- | :--- |
| **ロード前** | **Pydantic**（簡易オントロジ） | 型・部分的制約で入力バリデーション |
| **ロード後** | **Cypher / GQL** | グラフが壊れていないか整合性チェック |
| **必要な分野** | **OWL・記述論理** | 厳密な意味検証（最後の手段でも可） |

- スキーマレスなグラフ DB では **アプリ層** で少なくとも型と制約を定義する（= **簡易オントロジ**。完璧ではない）
- Pydantic は **OWL を否定しない** — 規制・損失が許されない領域では OWL で厳密検証する

---

<!-- _header: "第3節｜現実のプロジェクトでどうするか" -->

## やってはいけないこと

- 全部を OWL / 人力オントロジーにする
- 全部を Text-to-SQL / ベクトル RAG に任せる
- 分析のためにだけ物理グラフを全社展開する
- 自動オントロジーを **シグナル品質の確認なし** で信頼する

**設計の本体** = どこまで統計に任せ、どこから人間が固定するか

## まとめ

1. PF は **仮想グラフ** と **統計的オントロジー** を同時に押している
2. 思想の系譜は **1970年代の記号AI** → SW 挫折 → **Google 型** の再現
3. LLM は柔軟だが **グラフ/オントロジーで厳密さを補う**
4. 現場では **仮想グラフ＋自動構築＋Pydantic** が現実解
5. OWL・物理グラフは **競争領域・最終防衛線** に限定
