## 概要

製造業では、設計工程で **QCD**（Quality / Cost / Delivery：品質・コスト・納期）の大枠が決まり、品質保証工程でリスクを防ぎ、製造工程で現実の形にする——という役割分担は常識です。にもかかわらず、現場では「CAE（Computer-Aided Engineering）上は合格だったのに試作で品証NG」「過去の割れ事例がExcelに眠っている」「設計変更が製造の歩留まりを壊す」といった手戻りが繰り返されます。

本記事（第1部）の目的は、この破綻を個人のスキルや部門間コミュニケーションの問題に帰さず、**データの観点差・ゲート化された品証・マルチモーダルな知見の壁**という構造として記述することです。第2部で理論モデル、第3部で実装像を述べるための問題定義編です。

## 1. 三者が「同じ製品」を見ているのに、同じ世界を見ていない

シーズン2では、部門別グラフを物理分離したまま Bridge Keys で結ぶ論理フェデレーションを扱いました。シーズン5の舞台は、その先にある **設計（EBOM/CAE）・品質保証（FMEA/DR）・製造（MBOM/BOP/MOM）** の三者です。

ここでのポイントは、分断が「システムが別だから」だけではないことです。同じ部品番号・同じ製品IDを共有していても、各ドメインが保持する **観点（ビュー）とトポロジー** が決定的に異なります。

| ドメイン | 主な資産 | 見ているもの |
| :--- | :--- | :--- |
| 設計 | EBOM、3D CAD、SPDM/CAE | 機能・構造・性能・設計意図 |
| 品証 | FMEA、DR記録、試作評価、不具合票 | リスク・故障モード・合否の根拠 |
| 製造 | MBOM、BOP、MOM、MES/IIoT | 工程・設備・資源・コスト・歩留まり |

品質保証は本来、設計意図と製造現実のあいだで「評価・検証するハブ」であるはずです。しかし多くの組織では、ハブとしての役割より **試作後の関所（ゲート）** としての運用に寄りがちです。その結果、QCDのトレードオフ（とくに品質とコスト）が後工程での設計変更や調整として現れやすく、過去の失敗知見も次の設計へ十分に戻りにくくなります。

:::message
**用語の注意書き（本節）**

* **Bridge Keys / 論理フェデレーション**：部門別に分かれたグラフを物理統合せず、共有キーで論理結合する仕組み（シーズン2）。
* **EBOM**（Engineering Bill of Materials）：設計視点の部品構成表。機能・構造の分解を表す。
* **MBOM**（Manufacturing Bill of Materials）：製造視点の部品構成表。工程・組立の都合でツリーが変わりうる。
* **CAD**（Computer-Aided Design）：コンピュータ支援設計。3D形状などの設計データを扱う。
* **CAE**（Computer-Aided Engineering）：シミュレーションによる工学解析（強度・熱・振動など）。本稿概要で初出済み。
* **SPDM**（Simulation Process and Data Management）：CAEのプロセス・解析データ・バージョンを管理する基盤。
* **FMEA**（Failure Mode and Effects Analysis）：故障モード影響解析。想定故障とその影響・対策を整理する手法。
* **DR**（Design Review）：デザインレビュー。設計の妥当性を多部門で評価・合否する関門。
* **BOP**（Bill of Process）：工程構成（どう作るか）を表すプロセス側の構成情報。
* **MOM**（Manufacturing Operations Management）：製造オペレーション管理。計画〜実行〜実績の製造業務全般を指すことが多い。
* **MES**（Manufacturing Execution System）：製造実行システム。現場の作業指示・進捗・実績を扱う。
* **IIoT**（Industrial Internet of Things）：産業向けIoT。設備センサ等からの時系列データの収集基盤。
* **トポロジー**：ここではBOMや工程の親子・接続構造（ツリー／グラフの形）を指す。部品番号が同じでも構造が一致しない、という意味で用いる。
* **ゲート**：試作後などの品質関所。合否判定の通過点として運用される段階を指す。
:::

## 2. 本シリーズで扱う論点の全体像

シーズン5では、設計・品証・製造を貫く課題を **問題定義（本記事）→ 理論（第2部）→ 実装（第3部）** の順で扱います。ここでは論点を一通り並べ、詳細は次節以降（および後続記事）に委ねます。

### 第1部（本記事）：なぜ知見が繋がらないのか

| # | 論点 | 一言で言うと |
| :---: | :--- | :--- |
| 1 | EBOM と MBOM の観点差 | 同じ製品でもトポロジーが違い、製造知見が設計へ戻りにくい |
| 2 | 関所で孤立しがちな品質保証（QA） | ハブであるべき品証がゲート運用に寄り、手戻りが後工程に溜まりやすい |
| 3 | マルチモーダル・ビッグデータの壁 | 幾何・CAE・テキスト・時系列が分かれ、人力で探す運用に依存する |

本記事の第3節以降で、この3点を順に掘り下げます。

### 第2部：どう理論的に繋ぐか

| # | 論点 | 一言で言うと |
| :---: | :--- | :--- |
| 1 | 設計の根拠を辿れるようにする | 仕様・解析・形状・品質リスク・工程の「なぜ」をつなぎ、後から説明できるようにする |
| 2 | 種類の違うデータを同じ物差しで比べる | 形・解析結果・文書など別形式の情報を、「似ている／似ていない」で並べて過去事例を引けるようにする |
| 3 | QCD（品質・コスト・納期）のバランスを取る | 制約の中でコストを抑えつつ、形や公差の変更が品質・納期にどう効くかを見える化する |

あわせて、設計の部品構成と製造の部品構成がどう対応するかを、無理に同じ形に揃えるのではなく対応関係として扱う方法も第2部で論じます。

### 第3部：現場の働き方をどう変えるか

| # | 論点 | 一言で言うと |
| :---: | :--- | :--- |
| 1 | 設計・品証・製造のデータを常に集めておく | 各工程の成果物や記録を裏側で取り込み、いつでも使える状態にしておく |
| 2 | 人力で探すのではなく、作業中に知らせる | 設計画面で形や公差を変えた瞬間に、過去のリスクやコストへの影響を横から提示する |
| 3 | 使うほど知見が溜まる仕組みにする | 提示への採用・見送りと、その後の合否結果を記録し、次の提案の精度を上げていく |

以下、第1部の論点1から詳しく見ます。

## 3. 論点1：EBOM と MBOM の観点差——フィードバックが戻りにくい構造

### 3.1 機能・構造指向 vs 工程・設備・資源指向

**EBOM**（Engineering Bill of Materials）は、設計視点の部品構成表です。製品を「何の部品・アセンブリで成り立つか」という **機能と構造の分解** として表現し、部品の親子関係は「何を構成するか」に近くなります。公差や材料、CAE境界条件も、この設計意図の延長に置かれます。

一方、製造側では次の三つが中心になります。

* **MBOM**（Manufacturing Bill of Materials）：製造視点の部品構成表。組立順や供給の都合で、設計のEBOMとは親子関係や粒度が変わりうる。
* **BOP**（Bill of Process）：工程構成。どの順序で、どの設備・治具・作業で作るかを表す。
* **MOM**（Manufacturing Operations Management）：製造オペレーション管理。計画から実行・実績までの製造業務を束ねる枠組み（現場の実行系としてはMESが担うことも多い）。

これらは同じ製品を **どう作るか** として表現します。工程順、治具、切削機、治工具、段取り、ロット、加工条件が第一級の情報です。設計のEBOMと製造のMBOMで部品番号が一致していても、ツリーの分岐点・粒度・親子関係（トポロジー）は一致しません。

この差は単なるマスタ同期の問題ではありません。**同じ実体を異なるグラフとして記述している**ため、製造現場の加工ログや歩留まりの変化を「設計のどの形状特徴・どの公差に紐づけるか」が自動では決まりません。

### 3.2 トポロジー不一致が生む「戻りにくさ」

現場データが設計へ戻りにくい典型パターンは次のとおりです。

1. 製造で歩留まりが落ちる（切削条件・治具・公差蓄積が関与）。
2. 改善は製造側のパラメータ調整や作業標準改訂で閉じる。
3. 設計側の CAD/EBOM には「なぜそのR・その公差なのか」の更新根拠が残らない。
4. 次の派生機種で、同じ幾何的リスク（形状・寸法の決め方に起因するリスク）が再登場する。

つまりボトルネックは「MESがある／ない」より先に、**EBOMとMBOMのあいだで「どの部品・どの工程が対応するか」が明示され、共有されていない**ことです。シーズン2の Bridge Keys が部門グラフをつなぐ鍵だったように、シーズン5ではこの構造の対応づけそのものが第一級の課題になります。

## 4. 論点2：関所で孤立しがちな品質保証（QA）のジレンマ

### 4.1 ハブであるはずの先行品証が、後工程ゲートに寄りやすい

DRBFM / FMEA / 試作評価は、本来は設計初期から製造制約を織り込む **先行品質保証** の装置です。ところが運用上は次のように偏りがちです。

* FMEA が PDF / Excel に固定され、CAD 変更と同期しない。
* DR が「会議の合否」として消費され、形状特徴へのリンクが残らない。
* 品証が「通す／落とす」関所になり、設計・製造の間に挟まれたハブとして機能しにくい。

ハブより関所に寄ると、情報は双方向に流れにくくなります。設計は「合格条件」を後から知り、製造は「なぜその形状か」を後から知り、品証は「過去に何を見たか」を人間の記憶とExcelに依存しがちです。

### 4.2 「CAE合格 → 品証NG → 大きな手戻り」のメカニズム

よくある連鎖は次です。

1. CAE（強度・熱・振動など）は境界条件とメッシュの範囲で合格する。
2. 製造では公差蓄積、熱変形、治具剛性、加工経路の影響が加わる。
3. 試作・品証で割れ・かじり・組付不能などが顕在化し、ゲートでNG。
4. 設計変更（R変更、肉厚、公差緩和／厳格化、材料変更）が広範囲に波及し、原価と日程に影響する。

ここでの本質は「CAEが嘘をついた」ではありません。**品証が扱うリスク空間（故障モード・現場制約）が、設計の幾何・CAE場と同一の意味空間に載っていない**ことです。結果として、品質を守る行為が後工程のコスト増のきっかけになり、「コストを下げると品質が落ちる／品質を上げるとコストが跳ねる」というトレードオフが再生産されやすくなります。

## 5. 論点3：マルチモーダル・ビッグデータの壁

ここまで、EBOMとMBOMの構造のずれと、品証がゲートに寄りやすい運用を見てきました。仮に部門をまたいで知見を戻そうとしても、もう一つの壁があります。設計・品証・製造が持つ情報の **データの形そのもの** が揃っていないことです。いわゆるモダリティ（表現の種類）が異なります。

| モダリティ | 例 | 人間の運用 |
| :--- | :--- | :--- |
| 幾何 | 3D CAD、メッシュ | 似た形状を人力で探す |
| 数値場 | CAE結果（応力・温度分布など） | 似た条件・似たホットスポットを人力で探す |
| テキスト／表 | FMEA、不具合票、DR議事録 | キーワードで過去事例を人力で探す |
| 時系列 | 加工ログ、センサ、歩留まり推移 | 異常パターンを人力で探す |

データ量が増えるほど、運用は人力で探すことに依存します。しかし設計者が公差を触った瞬間に必要なのは、検索窓ではなく、**その変更が過去の品証事例や製造コスト感度にどう似ているか**です。マルチモーダルな類似を人間に強いる限り、シフトレフトはスローガンにとどまりがちです。

シーズン4で議論した「契約としてのオントロジー／検証」は、ここでも前提になります。異種データを雑にまとめれば済む、という話ではありません。似ている事例を引くだけでは、なぜそれが問題なのか・どの工程に効くのかを説明しきれないからです。第2部では、**根拠を辿れる関係づけ**と、**種類の違うデータを同じ物差しで比べる方法**を分けたうえで、両者を組み合わせる考え方を置きます。

## 6. 設計・品証・製造、それぞれに見える問題

ここまでの話は、どこか一つの部門の怠慢ではありません。同じ製品を扱っていても、見える景色が違うために、次のような痛みとして現れます。

* **設計**：なぜそのR・その公差にしたかの根拠が残りにくく、造りやすさや品証の観点は後工程から戻りにくい。
* **品証**：FMEAや過去不具合が設計変更と結びつかず、ハブとしてつなぐよりゲートで合否を見る役割に寄りやすい。
* **製造**：上流で織り込めなかった制約が、歩留まりや手戻りとして現場に現れやすい。改善しても、設計の構成情報へ戻りにくい。

三者に共通するのは、部門をまたいだ知見が設計の早い段階で見えないことです。その結果として、たとえばQCDのうち品質とコストを同時に守りきれない局面が後工程で露わになる、といった課題が出ます（納期の遅れも同じ構造で起きやすいです）。試作やゲートの直前で初めて気づくのではなく、設計の早い段階で品証と製造の知見が見えるようにすることが、マルチモーダル知見統合の近道になります。

## 7. 第1部のまとめ、および第2部の予告

### 第1部のまとめ

本記事では、設計・品証・製造の知見がつながりにくい理由を、次の三点に整理しました。

1. EBOM と MBOM は同じ製品でも構成の形が異なり、製造側の知見が設計へ戻りにくい。
2. 品質保証はハブであるべきなのにゲート運用に寄りやすく、CAE合格と品証NGのあいだで大きな手戻りが生まれやすい。
3. 形・解析・文書・現場ログなどデータの種類が分かれたまま人力で探すことに頼っている限り、過去の知見は再利用しにくい。

個人のスキルや部門間のコミュニケーション不足に帰すより先に、観点の差・ゲートに寄った運用・データの形の違いという構造を押さえることが、第1部の結論です。

### 第2部の予告

続く第2部では、この分断をどう理論的につなぐかを扱います。論点は次のとおりです。

1. 設計の根拠を辿れるようにする（仕様・解析・形状・品質リスク・工程の「なぜ」をつなぐ）
2. 種類の違うデータを同じ物差しで比べる（形・解析結果・文書などから似た過去事例を引く）
3. QCD（品質・コスト・納期）のバランスを取る（形や公差の変更が何に効くかを見える化する）

「なぜつながりにくいか」を述べた第1部の次に、「どうつなぐか」へ進みます。
