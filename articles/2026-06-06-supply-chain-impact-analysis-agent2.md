## 概要

前回の [第1部：背景編](https://zenn.dev/yohei/articles/2026-06-06-supply-chain-impact-analysis-agent) では、大企業内において設計（EBOM）、製造（Routing）、調達（Sourcing）などのデータが組織的・システム的に分断されている現実と、それらを1つの巨大なデータベースに物理統合するアプローチがなぜ破綻するのかを解説しました。

データを物理的に集約できない以上、有事の横断的影響分析（例：サプライヤー途絶が最終製品や組立工程に与える影響）を瞬時に行うためには、**「各組織の独立性を維持したまま、論理的に結合してクエリを実行する」** 仕組みが必要です。

本記事（第2部）では、この仕組みを具現化する**「論理フェデレーション（Logical Federation）」の設計原則**について詳しく解説します。

各部門がデータの所有権とガバナンスを維持したまま、AIエージェントと連携して安全かつ決定論的にドメインをまたぐ推論を行うための「契約（Contract）」と「ツール境界」の設計思想に迫ります。

---

## 1. 論理フェデレーションの基本コンセプト：「物理分離・論理結合」

物理的な一元管理データベースを作らないのであれば、代替案は**「各組織がそれぞれのデータを個別のグラフ（またはデータストア）として保持し、クエリを実行する瞬間にのみ、共通の識別子で論理的に繋ぎ合わせる」**アプローチになります。

これが**「物理分離・論理結合（Physical Separation, Logical Federation）」**の原則です。

```
[調達ドメインのローカルグラフ]
Supplier X ──(SUPPLIED_BY)──► Component A (ID: COMP-103)
                                  │
                                  │ ◄── クエリ実行時に ID で論理結合
                                  ▼
[設計ドメイン of... / PLM]
Component A (ID: COMP-103) ──(USED_IN)──► Product Y (ID: PROD-901)
                                            │
                                            │ ◄── クエリ実行時に ID で論理結合
                                            ▼
[製造ドメイン of... / MES]
Product Y (ID: PROD-901) ──(PRODUCED_BY)──► Process Z (ID: PROC-10)
```

### 1.1 なぜこの設計にするのか？（得られるビジネス価値）

1. **データ所有権（ガバナンス）の維持**:
   各チームは自部門のローカルグラフに対する完全な書き込み・更新権限を持ちます。設計チームがBOMを更新しても、調達チームのシステムや権限管理を乱すことはありません。部門間の政治的な調整を最小限に抑え、データ更新の俊敏性を保てます。
2. **セキュリティの境界維持**:
   調達金額や仕入先リスクのような機密性の高いデータは「調達グラフ」だけに閉じ込め、参照権限をそこだけに限定できます。AIエージェントは、権限を持つユーザーがクエリを実行した際にのみ、そのユーザーの権限範囲内でクエリを実行して論理結合します。
3. **データ鮮度（SLA）の最適化**:
   毎日のルーティング工程の調整、週次のリスク情報、製品変更時のBOMといった、異なるライフサイクルを各部門独自のインジェストパイプラインで処理できます。全社一斉の重いバッチ処理は不要です。

## 2. フェデレーション契約（Bridge Keys）の設計

論理フェデレーションを成立させるためには、異なる組織が管理するデータの間で**「このIDだけは同じものを指し、同じルールで命名する」**という最低限の約束事（フェデレーション契約）を結ばなければなりません。

この契約となる共通IDを**「ブリッジキー（Bridge Keys）」**と呼びます。

### 2.1 典型的なブリッジキーの役割

製造業における製品供給・生産体制のシナリオでは、以下のIDがブリッジキーとして機能します。

| ブリッジキー | IDの表記例 | ドメイン横断の結合ルール |
| :--- | :--- | :--- |
| `Component.id` | `COMP-103` | **最重要の結合キー**。<br>設計のEBOM、製造の工程、調達の仕入情報すべての橋渡しを行います。 |
| `Product.id` | `PROD-901` | 設計ドメイン（EBOM）と製造ドメイン（Routing）を結合し、製品と組立プロセスの紐付けを行います。 |

### 2.2 ドメイン内に閉じるローカルID

逆に、他のドメインに露出させる必要がないデータは、ドメイン内ローカルなIDとして管理し、スコープを隠蔽します。

* `Supplier.id`（例: `SUP-001`）: 調達ドメイン内にのみ存在し、外部ドメインが直接このIDに関係性を結ぶことはありません。
* `Process.id`（例: `PROC-10`）: 製造ドメイン内に閉じ、他のドメインからは「どの製品・部品がどの工程に関係しているか」というインターフェースでのみ参照されます。

### 2.3 アイデンティティ解決とマスターの責務

実務において「同じ部品なのに、システムによって型番の表記が揺れている」という問題（アイデンティティ解決）は頻出します。これをグラフの結合ルール側でアドホックに解決しようとすると、クエリが著しく複雑化します。

設計思想として、**「アイデンティティ解決や属性マスタの参照は、各グラフとは別層の『正規コンポーネントレジストリ（マスターデータベース）』が担う」**ように責務を分離します。各組織のグラフは、このマスターレジストリが保証するクリーンなブリッジキー（`Component.id`）を書き込むことだけを保証すればよい状態を作ります。

## 3. マシンリーダブルな契約書：グラフ・コンテキストのメタデータ化

共通IDのルールや、どのドメインがどのノード・エッジの管理責任を持つかという定義は、人間の合意形成書としてだけでなく、システムやAIエージェントが自律的に解釈できる**「メタデータ（スキーマ定義）」**として構造化されていなければなりません。

これを本設計では**「グラフ・コンテキスト（Graph Context）」**と定義します。

### 3.1 グラフ・コンテキストに必要な4つの定義要素

グラフ・コンテキストは、主に以下の定義を内包するマニフェストファイルとして機能します。

1. **アイデンティティの定義（Identity Bindings）**:
   全ドメインで共通して使用するマスターエンティティとブリッジキーの指定（例: `Component` の `id` は全グラフで同一の現実世界のパーツを指すというルール）。
2. **ドメインの境界定義（Domain Scopes）**:
   各組織（ドメイン）が管理権限を持つノードの種類（Labels）と関係性の種類（Edges）の厳格なマッピング（例: `ebom` ドメインは `Component` と `Product` のみをノードとして持ち、`USED_IN` エッジのみを新規追加・編集できる）。
3. **フェデレーション経路（Federation Joins）**:
   有事の影響分析時などに、どのような順序でキーを受け渡して結合すべきかという「あらかじめ検証された走査テンプレート」。
4. **品質・データガバナンスのルール（Quality Gates）**:
   各組織が書き込んだグラフデータの品質検証ルール、および論理結合時にデータ鮮度の差（SLA Skew）を許容する許容範囲の定義。

このコンテキスト定義が存在することで、AIエージェントは「調達システムで影響部品を特定したら、次は設計システムで `Component.id` を使って製品を特定し、最後に製造システムで `Product.id` から工程を特定する」というロードマップを、実行時に自動的に組み立てることが可能になります。

## 4. AIエージェントと「ツール境界」の設計

第1部で述べた通り、LLMにデータベースのスキーマを直接渡してクエリ（SQLやCypher）をアドホックに生成させるアプローチ（Text-to-SQL）は、ハルシネーションや構文エラーのリスクが高く、実務では破綻します。

そこで、本アーキテクチャでは**「決定論的ツール（Deterministic Tools）」**と**「AIプランナー（LLM Planner）」**の責務を厳格に切り分けるツール境界（Tool Boundary）を導入します。

```
               [ ユーザーの質問 ]
                      │
                      ▼
┌──────────────────────────────────────────────┐
│  AIプランナー (LLM)                          │
│  - ユーザーの意図（Goal）を解釈              │
│  - ドメイン仕様や制約から手順（Plan）を組み立て│
│  - 決定論的ツールを選択し、IDを受け渡して順次実行 │
└──────────────────────┬───────────────────────┘
                       │ 実行指示 (API Call)
                       ▼
┌──────────────────────────────────────────────┐
│  決定論的ツール (Python + 各ドメインクエリ)    │
│  - カタログ化された安全なCypherの実行         │
│  - PythonによるIDの結合処理やグラフ探索       │
│  - 結果を構造化データ (JSON) で返却           │
└──────────────────────┬───────────────────────┘
                       │ 結果返却
                       ▼
               [ グラウンディングされた回答 ]
```

### 4.1 役割の境界線

* **AIプランナー（LLM）の役割**:
  * ユーザーの曖昧な入力から「何が起きているか（途絶の地域、サプライヤー等）」を解釈。
  * グラフ・コンテキストから「どのツールを、どの順番で呼ぶべきか」の計画（Plan）を策定。
  * ツールから返ってきた構造化データ（JSON）に基づいて、嘘のない根拠（エビデンス）を伴う自然言語の回答要約を生成。
* **決定論的ツール（アプリケーション層）の役割**:
  * 各ドメインデータベースに対するクエリの実行（事前に定義・最適化されたCypherを実行）。
  * ツール内部におけるIDの結合処理や、再帰的な多ホップ探索アルゴリズムの計算実行。
  * **LLMに対して、クエリの直接記述（Text-to-Cypher）は一切許可しない。**

この設計により、LLMが誤ったCypherを書いてクエリがエラーになったり、セキュリティ制限を無視してデータを引っこ抜くリスクを完全に抑え込むことができます。エージェントは高度な判断（計画と要約）に専念し、グラフ探索の実行は100%バグのないプログラムとして実行されます。

## 5. まとめ - 設計の着地点

シーズン2第2部となる本記事では、組織分断されたデータを前にした際の「論理フェデレーション」の設計原則を整理しました。

| 課題 | 物理統合（セントラルDB） | 論理フェデレーション（本設計） |
| :--- | :--- | :--- |
| **データ所有権** | 1つのチームが代表して所有（他チームの自由度が下がる） | 各チームが自システムで管理（独立性維持） |
| **セキュリティ** | ACLの再実装と同期が必要（漏洩リスク増） | ソースDB of... のセキュリティ境界をそのまま流用 |
| **クエリの品質** | LLMが直接全体クエリを書く（エラー頻発） | 事前に検証されたドメインツールの組み合わせ |
| **運用の容易さ** | 巨大ETLの構築・保守が必要 | 共通ID（ブリッジキー）の契約のみで稼働可能 |

この「物理分離・論理結合」のデザインパターンにより、大企業の組織構造を歪めることなく、AIエージェントを用いたサプライチェーン影響分析のインフラを構築することが可能になります。

次回（第3部：実装編）では、この設計原則に基づき、**LanceDB** と **DuckDB** を用いてローカル環境で物理分離されたグラフを構築し、Pythonによるフェデレーションとエージェント連携をどのようにコーディングしたのか、具体的な実装案を解説します。
