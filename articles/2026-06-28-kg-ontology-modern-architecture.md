## 概要

第1部では、現代のAI/DEスタックにおけるオントロジーの役割を、論理推論エンジンからデータ品質およびエージェント回答検証のための「契約（Contract）」として再定義しました。

第2部となる本記事では、「オントロジーに裏打ちされた壊れない知識グラフ基盤」と「ハルシネーションを起こさないAIエージェント」をシステムアーキテクチャに具現化するための、 **「3段パイプライン」** と **「検証タイミング（Validation Timing）」** の設計方針について解説します。

データエンジニア（DE）とAIエンジニア（AI）がいつ、どのような仕組みを用いて検証を行うべきか、その役割分担とベストプラクティスを掘り下げます。

## 1. 現代ナレッジグラフの3段パイプライン

オントロジーを開発のインフラとして機能させるためには、システムを以下の3段の独立したパイプラインとして整理します。

```text
  【Ingestパイプライン】      【Explorationパイプライン】      【Groundingパイプライン】
  データソース  ───────────► 決定論的探索ツール ──────────► 回答検証ゲート
    │ (スキーマ検証書き込み)     │ (Traversal / 結合)          │ (LLM要約監査)
  ▼                           ▼                           ▼
  Neo4j (L1-L3データ保証)     Bridge Keys (L4結合合意)    Evidence (回答の根拠証明)
```

1. **Ingest（スキーマ検証された書き込み）**:
   データソースからグラフデータベースにデータを投入するパイプラインです。書き込み境界においてオントロジーによる検証を強制し、不正なデータを一切排除します（[第1部 §3](https://zenn.dev/yohei/articles/2026-06-28-kg-ontology-redefinition#3-古典的オントロジー-vs-現代の定義) で述べた **CWA** —— 契約外は存在しないとみなし即拒否する前提）。
2. **Exploration（決定論的なツール探索）**:
   AIエージェントからのリクエストに基づき、オントロジーで安全性が保証されたツールを介してグラフを辿る（Traversal）パイプラインです。LLMに生のCypher（グラフクエリ）を生成させるのを防ぎ、予測可能な結合（Federated Join）のみを実行します。
3. **Grounding（回答の根拠検証ゲート）**:
   探索ツールが出力した構造化エビデンスデータと、LLMがユーザーに向けて生成した自然言語回答を突合し、ハルシネーションが含まれていないかを検証するパイプラインです。

## 2. 検証タイミング（Validation Timing）の設計方針

グラフDBは本来スキーマレスであり、管理を誤ればすぐにデータの一貫性が崩壊します。これを防ぐためには、「いつ」「誰が」検証を行うべきかという **検証タイミング（Validation Timing）** をシステム境界上に正しく設計する必要があります。

本アプローチでは、以下の6つのタイミングで検証を仕掛けます。

```text
  [スキーマ定義] ──► [投入前] ──► [書き込み時] ──► [ロード後 (L3)] ──► [結合時 (L4)]
   定義の整合       メモリ上チェック  書き込み拒否    定期バッチ監査       結合時の品質ゲート
```

| 段階 | タイミング | 主な目的 | 実行者 / 仕組み | 関連するレベル |
| :--- | :--- | :--- | :--- | :--- |
| **① スキーマ定義** | スキーマ定義・変更時 | スキーマと同期コードの整合性チェック | 人間によるコードレビュー、自動同期スクリプト | L0–L2, L4 |
| **② 投入前検証** | データロード前（メモリ上） | データベース負荷をかける前の早期エラー検出 | メモリ上の検証（Pydantic 等） | L1–L2 |
| **③ 書き込み時** | ストレージ書き込み時（境界） | スキーマ違反データの永続化をブロック | 書き込み API / ストレージバリデータ | L1–L2, L4 |
| **④ ロード後** | データベースロード後（全体） | 格納データ全体の整合性と品質の証明 | SHACL（Neosemantics）、Cypher による定期監査 | L3, L4 |
| **⑤ 結合時** | 複数グラフの結合・探索時 | 部門境界をまたぐ共通キーの整合性検証 | 結合処理のジョインゲート | L4 |
| **⑥ 継続的検証（CI）** | ソースコード変更時・テスト実行時 | 開発サイクルにおける継続的な回帰ガード | CI ランナー、回帰テストスイート | L1–L4, G\* |

### ロード後監査で使う SHACL と Neosemantics

表の **④ ロード後** に現れる **SHACL** と **Neosemantics** は、L3（ロード後の整合性証明）を担う部品です。 **③ 書き込み時** の Pydantic 検証や Cypher による定期監査と **併用** し、載っているグラフ全体が契約に適合しているかを **事後に証明** します。

* **SHACL（Shapes Constraint Language）** — [W3C の標準](https://www.w3.org/TR/shacl/)。 **「Shape（形状）」** としてノード・関係の制約（必須プロパティ、型、カーディナリティ、許可パターンなど）を宣言し、 **すでに Neo4j に載っているグラフ** がその Shape に適合するかを一括検証します。OWL Reasoner による暗黙推論（L5）とは異なり、 **載ったデータの整合性チェック** が目的で、[第1部 §3](https://zenn.dev/yohei/articles/2026-06-28-kg-ontology-redefinition#3-古典的オントロジー-vs-現代の定義) で述べた **CWA** 寄りの **事後検証** に向いています。参照実装では、Pydantic の SSOT から Shape 定義を **自動生成** し、スキーマと監査資産のドリフトを防ぎます（詳細は第3部）。
* **Neosemantics（略称 n10s）** — [Neo4j Labs のプラグイン](https://neo4j.com/labs/neosemantics/)。プロパティグラフ（LPG）上の Neo4j に、RDF 系の取り込みと **SHACL バリデーション** を載せるための橋渡しです。Neo4j 単体には SHACL エンジンがないため、 **④ ロード後** のバッチ監査で Shape を **グラフ DB 内に対して実行** するには n10s が必要になります。Cypher 監査や Pydantic 再検証と **同じ監査ランナー** から呼び出し、L3 の証明を多層化します。

**③ 書き込み時** ではアプリの書き込みゲート（Pydantic）が主役、 **④ ロード後** では **Cypher 監査 ＋ Pydantic 再検証 ＋ SHACL（n10s）** の3本立て——という分担が、本連載の L3 設計の要点です。

## 3. SSOT 原則：検証ルールの一元管理と自動生成

§2 では、スキーマ定義から CI まで **6 段階** に検証を分散配置しました。段階ごとに仕組みが異なる——投入前は Pydantic、書き込み時は API ゲート、ロード後は SHACL と Cypher 監査、CI ではエクスポート資産のドリフト検知——ため、 **それぞれのルールを手書きで別々に保守** すると、すぐに定義が食い違います。

* 書き込みゲートでは必須としている属性が、SHACL Shape には載っていない
* エージェント向けの公開スキーマだけ、接続ルールの更新が遅れている
* 監査用 Cypher の前提が、最新の型定義とずれている

こうした **ドリフト** は、どの段階の検証を通過しても「全体としては壊れている」状態を生みます。本連載の DE 設計では、これを防ぐために **SSOT（Single Source of Truth：単一の正本）** 原則を採ります。

**一箇所に契約を集約し、各検証資産はそこから自動生成する** —— これが前提です。参照実装では、L0〜L2（語彙・型・接続ルール）を **型付きスキーマ定義（Pydantic 等）** に集約し、それ以外の検証ルールは **手で二重管理しない** 方針にしています。

```text
  SSOT（スキーマ定義コード）
       │
       ├──► ② 投入前 / ③ 書き込み時 … 同一モデルによる実行時バリデーション
       ├──► ④ ロード後 … SHACL Shape の自動生成 → n10s でバッチ検証
       ├──► エージェント・Skills 向け … 公開用スキーマ（ontology.json 等）のエクスポート
       └──► ⑥ CI … 生成物と定義コードの乖離（ドリフト）検知
```

スキーマを変更したら、 **同期スクリプトを走らせて派生物を再生成し、CI で差分がないことを確認する** —— この運用が §2 の **① スキーマ定義** と **⑥ 継続的検証（CI）** をつなぎます。DE が毎回手で SHACL や JSON Schema を直すのではなく、 **正本を直し、残りを機械的に追随させる** ことで、6 段階すべてが **同じ契約** を参照し続けます。

Graph Contract（L4）の結合ルールは部門横断の関心事のため SSOT からは分離しますが、語彙・型・接続の **部門内契約** は SSOT に載せ、結合契約から **参照** する——という分担にします（第3部で具体手順を示します）。

## 4. データエンジニア（DE）の役割とベストプラクティス (L0〜L3)

データエンジニアの責任は、 **「ストレージ内にロードされたグラフデータの整合性が常に100%保たれていること」** を証明することにあります。以下は、§3 の SSOT 原則を DE の日常業務に落とし込んだ具体策です。

### 型付きスキーマによる契約定義（SSOT）

§3 で述べたとおり、ノード属性（L1）および接続ルール（L2）の正本は **型付きスキーマ（Pydantic 等）のコード一箇所** に置きます。投入前・書き込み時・ロード後・CI の各段階は、この正本から派生したルールを参照します。

### Write-time Guard (On write)

データをデータベースにインジェストするAPIやスクリプトは、直接Neo4jに書き込むのではなく、`GraphStore` のラッパーを介します。このラッパーの境界において Pydantic とエッジ定義による検証を強制し、スキーマ違反データ（型エラーや、未定義の接続関係など）は、書き込み処理そのものを拒否します。これにより、DB内は常にクリーンな状態に維持されます。

### 事後監査 (After load / L3)

しかし、手動操作や外部の直接ETLラインなど、アプリの書き込み境界をバイパスしてDBにデータが投入される「運用リスク」はゼロにはできません。
そこで、データベースにロードされた後（After load）に、定期的なバッチ監査（`audit_neo4j.py`）を実行します。
事後監査では、Cypherによる孤立ノードの検知や、Pydanticによるliveデータの再バリデーション、さらにはW3C標準の **SHACL（Shapes Constraint Language）** による検証を実行し、「データベース全体の整合性」を定期的にシステムテストとして証明（監査）します。

## 5. AIエンジニア（AI）の役割とベストプラクティス (L4, G\*)

AIエンジニアの責任は、データエンジニアが保証した「信頼できるグラフデータ」に対して、 **「安全に探索し、その事実をユーザーに100%歪めずに伝えること」** にあります。

### Graph Contract による結合合意 (L4)

サプライチェーンの例のように、生産ドメイン、購買ドメイン、物流ドメインなど、異なるチームや別のデータベースで管理されているグラフを安全に横断（結合）する必要があります。この結合ルールを宣言的に記述したものが `graph_contract.yaml`（Graph Contract）です。
どのキー（Bridge Key）を介してデータを結合するか、フェデレーション時の最低限のデータ品質要件は何かを、オントロジーの延長線上に明確に規定します。

### LLM 生成 Cypher の排除と決定論的探索

AIエージェントの実装において、ユーザーの質問をLLMに解釈させて、直接データベースに投げる Cypher を自動生成させるアプローチが広く見られます。しかし、これは実務本番環境では極めて危険です。データベースの負荷暴走や、意図しない書き込みクエリの実行、スキーマ違反の探索ルートによる誤答を引き起こします。
本スタックでは、LLMに Cypher を直接書かせるのではなく、オントロジーで安全性が証明された「名前付き探索ツール（Traversal Tool）」のみを提供します。LLMは与えられた入力パラメータ（部品IDなど）をツールに渡す役目に徹し、グラフ探索の実行そのものはシステム側で記述された決定論的クエリによって安全に実行されます。

### Grounding による回答要約の動的監査 (G\*)

探索ツールが取得した事実データ（エビデンスJSON）をもとに、LLMはユーザーへの自然言語回答を生成します。この最終要約の段階で、LLMは時に文脈にない勝手な推測や数値をでっち上げる「ハルシネーション」を起こします。
これを防ぐために、AIエージェントの出力ゲートにおいて、回答の検証プログラム（`grounding.py`）を動的に実行します。LLMが生成した回答内の主張が、ツールが出力したエビデンス（ノードIDやプロパティ値）と整合しているかを LLM-as-a-judge またはヒューリスティックなルールで判定します。整合性が取れない場合は回答をブロックし、事前定義された定型文（ヒューリスティックによる定型要約など）にフォールバックさせます。これにより、ハルシネーションのある回答がユーザーに届くのを未然に防御します。

## まとめ

壊れない知識グラフと信頼できるAIエージェントを構築するためには、データインジェストの瞬間から、データベースロード後のバッチ監査、そしてLLMの回答要約ゲートにいたるまで、 **各ライフサイクルに応じた検証タイミング（Validation Timing）の配置** と、 **SSOT からの自動生成** が不可欠です。

データエンジニアはL0〜L3を、AIエンジニアはL4〜G\*の検証レイヤーをそれぞれ責任を持って設計・運用します。

次回第3部では、これらの3段パイプラインと検証設計を具体的に動作させるサプライチェーン影響分析の「参照実装」を使い、コードリーディングとハンズオンのステップバイステップを追っていきます。
