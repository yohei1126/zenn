## 概要

本記事は、どこでも使える普遍的で抽象的なオントロジー構築の方法論を提案するものではありません。

[シーズン2 第2部](https://zenn.dev/yohei/articles/2026-06-06-supply-chain-impact-analysis-agent2)・[第3部](https://zenn.dev/yohei/articles/2026-06-06-supply-chain-impact-analysis-agent3) では、部門別グラフを物理分離したまま Bridge Keys と Graph Contract で結合する **分割統治と論理フェデレーション** を、設計から参照実装まで述べました。**シーズン4** はその上に載るレイヤーとして、**オントロジーを現代の DE/AI プラクティスに沿ってどう定義し、現場でどう使うか** を、実務者の視点から整理します。

具体的には、参照実装を組み上げる過程で著者が直面した2つの問題——グラフデータの整合性担保と、エージェント回答の根拠確認——を、 **Pydantic・CI・監査・Grounding** といったエンジニアリング上の部品で束ね、オントロジーを **データ品質と回答検証の契約（Contract）** として再定義する、という内容です。

## 1. なぜサプライチェーン影響分析から議論するのか

シーズン4 の動機づけは、抽象論ではなく **著者が参照実装を組み上げる過程で直面した具体的な問題** から始まります。その舞台が、 [シーズン2](https://zenn.dev/yohei/articles/2026-06-06-supply-chain-impact-analysis-agent) で題材にした **サプライチェーン影響分析** です。

[シーズン2 第1部](https://zenn.dev/yohei/articles/2026-06-06-supply-chain-impact-analysis-agent) では、設計（EBOM）・製造（Routing）・調達（Sourcing）の3ドメインが分断されたまま影響分析が必要になる——という **ビジネス上の問い** を整理しました（詳細は同記事 §3 参照）。

[シーズン2 第2部「組織境界を維持する論理フェデレーション」](https://zenn.dev/yohei/articles/2026-06-06-supply-chain-impact-analysis-agent2) では、各部門がデータを **物理分離して統治** し、Bridge Keys と Graph Contract によって **クエリ時のみ論理結合** する——いわゆる **分割統治（divide-and-conquer）** の設計原則を述べました。[第3部「サプライチェーン影響分析エージェントの実装」](https://zenn.dev/yohei/articles/2026-06-06-supply-chain-impact-analysis-agent3) では、Neo4j マルチDB・Pydantic・決定論的ツールによる **論理フェデレーションの参照実装** まで進めました。

シーズン2 が答えたのは **「部門別グラフをどう安全に結んで探索するか」** です。シーズン4 が答えるのは、その上に載る **「オントロジーをいかに定義・検証・運用するか」** —— データエンジニアと AI エンジニアという **実務者の視点** から見た、オントロジーの現代的解釈です。実装を進めるうち、著者は次の2つの問題に直面しました。シーズン4 で整理するのは、この壁に対する応答です。

**問題① グラフデータの整合性**  
**LPG**（Labeled Property Graph：ラベル付きプロパティグラフ。Neo4j など）のグラフデータベースは、デフォルトではスキーマレスに近く、型のドリフトや未定義リレーションの混入が起きやすい。探索を何度重ねても **「グラフが壊れていない」ことを証明できない** と、エージェントはデータを信頼して使えない。

**問題② エージェント回答の根拠**  
探索ツールが返した事実（エビデンス）と、LLM が生成した自然言語の回答が一致しているかを **システム的に検証する拠り所** がない。ハルシネーションを水際で防ぐ仕組みが、グラフ基盤の外側に残ってしまう。

かつての [セマンティックWeb](https://zenn.dev/yohei/articles/2026-05-30-vkg-strategy2) が目指した「全世界の意味を記述する巨大な知識表現」を再現したいわけではありません。**上記2つの問題を、現場で動くコードとして解く** —— それがシーズン4 の出発点です。

## 2. なぜいま「オントロジー」を再定義するのか

シーズン4 全体の視点は、哲学書的なオントロジー論や Reasoner 中心の古典モデルの説明ではありません。**参照実装を日々触る DE/AI 実務者** が、スキーマ定義・検証タイミング・回答の根拠確認を **コードと CI でどう回すか** —— そこにオントロジーの定義と活用方法を置きます。

問題①②に対する著者の答えは、古典的なオントロジーをそのまま持ち込むことではありません。**現代のデータエンジニアリング（DE）と AI エンジニアリング（AI）のベストプラクティスに沿って、オントロジーを再定義する** —— それが、快適・効率的・堅牢なシステムを組み上げるやり方だと考えています。

かつての [セマンティックWeb](https://zenn.dev/yohei/articles/2026-05-30-vkg-strategy2) や OWL の時代、オントロジーは Reasoner が未知の事実を導出する仕組みとして設計されました（系譜は [シーズン1 第2部 §2](https://zenn.dev/yohei/articles/2026-05-30-vkg-strategy2) 参照）。一方、現場の DE/AI チームが実際に使うのは `Pydantic` や JSON Schema、CI/CD、決定論的ツール、回答検証ゲートといった **エンジニアリング上の部品** です。LLM 時代には、あいまいな要約は LLM に任せ、オントロジーには **データの拒否・監査・契約** を担わせる方が自然です。

著者が本連載で採る再定義は、次の2層に集約されます。

* **DE 向け**: オントロジー = **データ品質を担保するスキーマと検証の契約**（書き込み時の拒否、ロード後監査、スキーマとコードの同期）
* **AI 向け**: オントロジー = **ツール出力と LLM 要約の整合を検証する契約**（決定論的探索の上での Grounding）

Pydantic で定義し、CI でドリフトを検知し、インジェスト境界で不正データを弾き、監査でグラフ全体を証明し、最後に回答の根拠を確認する——この一連の流れが、開発者にとって **理解しやすく、変更に強く、運用で壊れにくい** システムになります。それが「推論」から「契約」へのシフトであり、シーズン4 全体の設計思想です。

## 3. 古典的オントロジー vs 現代の定義

意味ネットワークからセマンティックWeb（RDF・OWL）に至る古典的な知識表現と推論の系譜は、[シーズン1 第2部](https://zenn.dev/yohei/articles/2026-05-30-vkg-strategy2) で詳述しています。本節では、その古典モデルと本連載が採る現代的定義の差分だけを対比表にまとめます。

本連載では、古典的なアプローチの焼き直しではなく、データエンジニアリング（DE）およびAIエンジニアリング（AI）のベストプラクティスを融合したアプローチを採ります。

| 次元 | 古典的オントロジー（セマンティックWeb） | 現代の定義（LLM前提・DE/AIプラクティス） |
| :--- | :--- | :--- |
| **主要前提** | 論理推論エンジン（Reasoner）が全てを解決する | **LLMのコンテキスト理解** と **近代的エンジニアリング** の融合 |
| **世界観** | オープンワールド仮説（OWA） | クローズドワールド仮説（CWA） |
| **表現と言語** | RDF/XML, OWL, SPARQL などの重厚な独自技術 | **Pydantic**, **JSON Schema**, **YAML** などの汎用エンジニアリング言語 |
| **検証の主眼** | TBoxによる公理の論理的一貫性チェック | **インジェスト時（On write）の拒否** と **ロード後の自動監査（CI/CD）** |
| **推論（Inference）** | OWL Reasoner による暗黙のノード/エッジの導出（高コスト） | 決定論的な **グラフアルゴリズム/Traversal** ＋ **LLM によるコンテキスト要約** |
| **Grounding (G\*)** | なし（グラフのデータ自体がSSOTで完結） | **LLMの回答がツール出力（Evidence）から逸脱していないかの動的検証** |

表の **世界観** 行に現れる2つの仮説は、 **「グラフや知識ベースに書かれていないこと」を、どう解釈するか** という前提の違いです。

* **オープンワールド仮説（Open World Assumption, OWA）** — 載っていない事実は、自動的には **「偽」** と断定しない。**真・偽・不明（未知）** のいずれかになりうる、という古典的セマンティックWeb・OWL 推論の前提です。「部品 A は部品 B に取り付けられる」と明記がなくても、別の公理から **関係を推論で導く余地** を残します。
* **クローズドワールド仮説（Closed World Assumption, CWA）** — **載っているデータの集合が、その時点での世界の全部** だとみなす前提です。スキーマや契約にない属性・関係は **存在しない（＝エラーとして拒否）** と扱います。RDB や LPG の書き込み境界検証、本連載のインジェスト拒否と相性が良いです。

本連載は **データ層の重心を CWA に置き**、契約外データは fail-fast で弾く設計に寄せます（OWA / CWA の使い分けは下記 ODS 補足参照）。これは技術的な好みだけではなく、著者が取り組む **コストや製造プロセスの最適化** のような問題領域では、 **エージェントの判断にハルシネーションが混ざると現場が混乱する** —— 未知の関係を暗黙推論で「補完」するより、 **契約どおりの事実だけで答える** 方が安全側だ、という背景もあります。OWL 推論（L5）を採用しない理由の一つも、この前提の差にあります（§5 参照）。

:::message
**補足: IPA Open Data Spaces（ODS）の OWA / CWA —— 本連載との思想の違い**

[IPA「Why Open Dataspaces: 設計思想とアーキテクチャパラダイム」（2026年4月）](https://www.ipa.go.jp/digital/architecture/reports/open-dataspaces-design-philosophy.html) では、 **OWA と CWA を層で使い分ける** 二層構造（Ontology Product + Data Product）が示されています。本連載も [論理フェデレーション](https://zenn.dev/yohei/articles/2026-06-06-supply-chain-impact-analysis-agent2) で複数ドメインを疎結合に結びます。**OWA / CWA は排他的な二択ではなく、レイヤーごとの重心の問題** —— フェデレーション有無ではなく、 **何を最優先するか** で寄せ方が変わります。

| | **ODS** | **本連載** |
| :--- | :--- | :--- |
| **主に解く問い** | 組織横断の **意味の発見・相互運用** とデータのプロダクト提供 | **コスト・プロセス最適化** 等——エージェント誤答が現場混乱につながる領域での **運用品質証明** と **根拠付き回答** |
| **OWA の重心** | **意味層** —— 未接続の語彙・定義を **偽と断定しない**（Dynamic Ontology 等） | 運用グラフ本体では **デフォルトにしない**（L5 暗黙推論も不採用） |
| **CWA の重心** | **Data Product 提供時** に選択的導入 | **データ層（L0〜L4）** で一貫（インジェスト拒否 + ロード後監査） |
| **スキーマ** | **スキーマフレキシブ** —— インスタンス先行、意味は後付け | **スキーマ先行** —— SSOT から定義 → 拒否 → 証明 |
| **推論** | Ontology Query → Data Query など **意味層の探索** | 決定論的ツール + LLM 要約 + **G\*** |

データスペース連携を本連載の外側に広げる場合、ODS の二層モデルは **意味層（OWA 寄り）とデータ提供層（CWA 選択）への重心シフト** の参照になり得ます。
:::

## 4. 想定読者と責務分界：DE はデータ品質、AI は回答検証

本連載の想定読者は、シーズン2 の参照実装（LPG + 論理フェデレーション + エージェント）を手で触る **データエンジニア（DE）** と **AI エンジニア（AI）** です。オントロジーを「契約」と捉えたとき、両者の関心領域は重なりますが、担うべき検証レイヤーは異なります。

### データエンジニア（DE）：スキーマ SSOT とインジェスト〜監査によるグラフ品質の担保

* **ゴール**: LLM やアプリケーションがどれだけ複雑な探索をしても壊れない、信頼できるグラフ基盤を維持する。
* **具体策**:
  - `Pydantic` 等のエンジニアリング言語でノード・エッジ定義を SSOT として一元管理する。
  - スキーマ定義から SHACL 等の検証資産を自動生成し、CI/CD でドリフトを検知する。
  - インジェスト境界（On write）で型違反・不正リレーションを拒否する。
  - ロード後監査でグラフ全体の整合性（孤立ノード、必須リレーション等）を定期的に証明する。

### AI エンジニア（AI）：決定論的探索と Grounding による回答根拠の検証

* **ゴール**: エージェントがグラフから得た事実（エビデンス）のみに基づいて回答し、要約段階のハルシネーションを水際で防ぐ。
* **具体策**:
  - LLM に Cypher を直接書かせず、オントロジーで保護された決定論的ツール（Traversal）に探索を委譲する。
  - ツール出力（JSON エビデンス）と LLM 要約の一致を、回答検証ゲート（Grounding）で動的に検証する。

## 5. 検証の段階整理：定義 → 投入 → 監査 → 結合 → 回答確認

参照実装では、オントロジー契約を **段階的な検証レイヤー** として整理しています。以下がその全体像です（参照ドキュメント [ontology-levels.md](https://github.com/yohei1126/supply-chain-impact-analysis-agent/blob/main/docs/ontology-levels.md) では **L0〜L5** および **G\*** と呼び分けています）。

### なぜこの5段階に分けるのか

この順序は、文献上のオントロジー階層をそのまま写したものではありません。**§1 で述べた問題①②を、DE/AI の現場で実装可能な検証タイミングに分解した結果** です。

まず、参照実装では **どの順に・何を・なぜ・どう検証するか** を次表にまとめます（検証タイミングの詳細は [第2部](https://zenn.dev/yohei/articles/2026-06-28-kg-ontology-modern-architecture)・[ontology-levels-project.md §5](https://github.com/yohei1126/supply-chain-impact-analysis-agent/blob/main/docs/ontology-levels-project.md#5-validation-timing-in-this-repo)）。**L0〜L4** はグラフデータの契約と証明、**G\*** はその上の回答検証——対象が異なるため記号も分けています。

| 順 | 段階 | いつ（検証タイミング） | 何を検証するか | 目的 | 主な手法 | 担当 |
| :---: | :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | **L0** 語彙 | スキーマ定義時 | エンティティ種別・関係種別の **呼び方** | 部門・ツール間で同じ語を指す **唯一の定義** を固定する | 用語集、スキーマ定義の一元管理、公開用スキーマの自動同期 | DE |
| 2 | **L1** 型・属性 | 定義時 ＋ 投入前 ＋ 書き込み時 | 各レコードの **属性の型と必須項目** | 型のずれや欠損を **データベースに載せる前・書き込み時に拒否** する | 型付きスキーマ（Pydantic 等）、投入前チェック、書き込み API の拒否ゲート | DE |
| 3 | **L2** 接続ルール | 定義時 ＋ 投入前 ＋ 書き込み時 | **許可される接続パターン**（どの種別同士を、どの関係で結べるか）と部門ごとの適用範囲 | 不正な関係・部門をまたいだ不許可リンクを **構造レベルでブロック** する | 許可エッジ一覧、部門別ホワイトリスト、書き込み時バリデータ | DE |
| 4 | **L3** ロード後証明 | データロード後 | **載っているグラフ全体** が L0〜L2 の契約に適合しているか | バッチ取込・手修正など書き込みゲートのすり抜けを **事後に証明** する | グラフ全体の定期監査、形状制約（SHACL）によるバッチ検証、実データの再型チェック | DE |
| 5 | **L4** 結合契約 | 契約定義時 ＋ 書き込み時 ＋ 結合時 | **部門間を結ぶ共通キー**、結合経路、横断品質ルール | 単一データベース内の L3 では見えない **部門横断の整合** を担保する | 結合契約書（Graph Contract）、結合処理時の品質ゲート、取込・結合フック | DE（探索は AI が決定論的ツール経由） |
| — | **L5** 推論 | （本シリーズでは不採用） | 公理からの **暗黙事実の自動導出** | 古典的推論エンジンが担う「知らない事実の発見」 | OWL 等の論理推論エンジン | — |
| 6 | **G\*** 回答確認 | エージェント応答時 | 探索ツールが返した **構造化エビデンス** と LLM **自然言語回答** の一致 | データが正しくても起きうる **要約段のハルシネーション** を水際で防ぐ | 回答検証ゲート、エビデンスとの突合、固定質問セットでの回帰評価 | AI |

著者がこの切り方を採る根拠は、次の4点に集約されます。

**1. 失敗モードごとに検証タイミングが異なる**  
型ドリフトや不正エッジ（問題①）は **書き込み時** に弾くのが最も安い。バッチ取り込みや手修正で on-write をすり抜けた異常は **ロード後監査** で拾う。部門をまたぐ参照欠落は **結合時** の契約違反として表れる。データが正しくても LLM 要約だけが嘘をつく（問題②）——これは **回答確認** でしか検知できない。**1つの検証（Reasoner 一発や LLM 自己チェック）ではカバーしきれない** ため、段階を分けます。

**2. 早い段階で fail-fast し、後段は「証明」に寄せる**  
**定義 → 投入**（L0〜L2）では、Pydantic や書き込みゲートで **契約外データの入库そのものを拒否** します（shift-left）。**監査**（L3）は、すでに載ったデータに対する **事後の品質証明** であり、インジェストだけでは担保しきれない全体性（孤立ノード、必須リレーション欠落など）を補います。後段ほどコストが高いので、前段で弾けるものは前段で弾く——という一般的な DE プラクティスに沿っています。

**3. シーズン2 の論理フェデレーションと責務分界に対応する**  
[シーズン2 第2部](https://zenn.dev/yohei/articles/2026-06-06-supply-chain-impact-analysis-agent2) の **分割統治** では、各部門グラフの品質と、部門横断の結合ルールは別問題です。**結合**（L4 / Graph Contract）は、単一 DB 内の L3 監査だけでは見えない **Bridge Key の参照整合性** を扱う段階として独立させます。DE が部門グラフを証明したうえで、フェデレーション契約に沿って結合する——という [第2部 §3.2](https://zenn.dev/yohei/articles/2026-06-06-supply-chain-impact-analysis-agent2) の二段検証と同型です。

**4. AI 層の検証はデータ層の外側に置く**  
決定論的ツールが返した JSON エビデンスまで正しくても、LLM の自然言語要約は別プロセスです。**回答確認**（G\* / Grounding）は、オントロジー契約の「上」に載る AI 固有のゲートとして分離します。探索の安全性（L2・L4 で担保）と、要約の忠実度（G\* で担保）を混同しないためです。

### なぜ L5（OWL 推論）は採用しないのか

[ontology-levels.md](https://github.com/yohei1126/supply-chain-impact-analysis-agent/blob/main/docs/ontology-levels.md) では、上記5段階に加え **L5** として OWL 等による暗黙推論も位置づけています。しかし本シリーズの参照実装では **L5 は採用しません**。

未知の事実を Reasoner に導出させる方式は、§3 で述べた **CWA** 前提の LPG や、決定論的ツール + エージェントという運用モデルと噛み合いにくい——参照実装を組み上げる過程で、その摩擦が繰り返し表面化しました。暗黙推論に期待されがちな「関係の自動導出」は、**決定論的なグラフ探索** と **LLM による要約** で代替可能であり、検証可能性（いつ・何が導出されたかを運用で説明できるか）の点でも、**明示的な定義・拒否・監査・結合・根拠確認** の5段階の方が実務と整合します。

L5 が古典モデルで担っていた位置づけ自体は [シーズン1 第2部 §2](https://zenn.dev/yohei/articles/2026-05-30-vkg-strategy2) で整理済みです。以下、各段階の概要です。

### 各検証段階の概要（L0〜L4・L5・G\*）

参照実装で扱う検証段階を、前節の表・図に沿って順に整理します。

```text
  L0  Vocabulary (語彙)            ─┐
  L1  Record Schema (属性スキーマ)   ├─ セマンティック検証（定義と投入）
  L2  Structural Constraints (接続) ─┘
       │
  L3  Instance Conformance (ロード後のグラフ整合性証明)
       │
  L4  Graph Contract (ドメイン間のフェデレーション合意)
       │
  L5  Reasoning (OWL等による論理推論) — ※本番運用ではスコープ外
       │
  G*  Answer Grounding (回答の根拠確認) — ※AI 層（L0–L4 の外側）
```

#### 語彙の定義（L0）

**何を扱うか** — エンティティ種別と関係種別の「呼び方」を定義する段階です。例えば、部品を表すエンティティ種別や、サプライヤーとの取引を表す関係種別といった **名称の一覧** です。

**なぜ必要か** — 設計・製造・調達のように部門が分かれると、同じ実体でも別の呼び方（「部品」「コンポーネント」など）が混在し、ツールやエージェントが **同じものを別物として扱う** 原因になります。L0 で語彙を **部門・ツール間で共有する唯一の定義** に固定しておくことで、以降の型チェック・結合・探索が **同じ辞書を参照** できます。語彙が揃っていなければ、L1 以降の検証も **何と照合すればよいか定まりません**。

#### 型と属性（L1）

**何を扱うか** — 各エンティティ・関係が持つべき **属性の型と必須項目** を定義する段階です。例えば、部品 ID が必須の文字列である、コストは数値である、といったルールです。型付きスキーマ（Pydantic 等）で記述します。

**なぜ必要か** — L0 だけでは「名前は合っているが型が違う」「必須項目が欠けている」データは止められません。型のずれや欠損は、探索結果やエージェント回答の **静かな品質劣化** につながります。L1 では **データベースに載せる前・書き込み時に拒否** し、契約外ペイロードが **永続化されない** 状態を作ります。問題①（グラフの整合性）に対する **最も早い fail-fast** の層です。

#### 接続ルール（L2）

**何を扱うか** — **許可される接続パターン**（どの種別同士を、どの関係で結べるか）と、部門ごとの適用範囲を定義する段階です。たとえば、部品からサプライヤーへの供給関係は許可するが、逆方向は不許可とする、といった **構造ルール** です。

**なぜ必要か** — L1 まで通っても、**許可されていない向きの関係** や **部門をまたいだ不許可リンク** はグラフを壊します。属性は正しくても、構造が狂えば影響分析の traversals は **意味のない経路** を辿ります。L2 は **構造レベルでブロック** する層であり、LLM に生クエリを書かせない **決定論的ツール** が安全に動く前提を作ります。

#### ロード後の整合性証明（L3）

**何を扱うか** — すでにデータベースに載っている **グラフ全体** を走査し、L0〜L2 の契約に適合しているかを **事後に証明** する段階です。グラフ全体の定期監査、形状制約（SHACL）によるバッチ検証、実データの再型チェックなどで行います。

**なぜ必要か** — L0〜L2 の書き込みゲートは強力ですが、バッチ取込の抜け道、管理画面からの手修正、運用バイパスなどで **すり抜けた異常** はゼロになりません。インジェストだけでは拾えない **孤立ノード・必須関係の欠落・全体性の崩れ** を、L3 が **「グラフは今も壊れていない」と説明可能** にします。問題①に対する **事後の品質証明** です。

#### 部門グラフの結合契約（L4）

**何を扱うか** — 複数のデータベースや部門ドメインを **部門間共通キー（Bridge Key）** で論理結合するときの契約です。結合経路、横断品質ルール、取込・結合時のゲートを含みます（Graph Contract）。

**なぜ必要か** — 各部門グラフを L3 まで証明しても、**部門をまたいだ参照欠落** や **結合キーの不整合** は単一 DB 内の監査だけでは見えません。[シーズン2](https://zenn.dev/yohei/articles/2026-06-06-supply-chain-impact-analysis-agent2) の分割統治では、部門内の品質と部門横断の結合は **別問題** です。L4 は **部門横断の整合** を担保する層であり、フェデレーション探索が **契約外の join をしない** ための根拠になります。

#### OWL による論理推論（L5）— 本シリーズではスコープ外

**何を扱うか** — OWL 等の論理推論エンジンが、スキーマの公理から **明示的に書かれていない関係や事実を自動導出** する段階です。古典的オントロジーが OWA 前提で担ってきた **「知らない事実の発見」** に相当します。

**なぜ参照実装では採用しないか** — 目的自体は理解できますが、§3 の **CWA** 前提の LPG 運用や、決定論的ツール + エージェントというモデルと **世界観が噛み合いにくい** ためです（詳細は **「なぜ L5（OWL 推論）は採用しないのか」**）。本連載では、暗黙導出の代わりに **明示的な定義・拒否・監査・結合** と、**決定論的グラフ探索 + LLM 要約 + G\*** で役割を分担します。

#### 回答の根拠確認（G\* / Grounding）

**何を扱うか** — オントロジー契約（L0〜L4）の **外側** に位置する、AI エージェント向けの検証です。探索ツールが返した **構造化エビデンス** と、LLM が生成した **自然言語回答** を突き合わせ、要約段で勝手な解釈（ハルシネーション）が入っていないかを確認します。

**なぜ必要か** — L0〜L4 までデータが正しく、ツール出力も正しくても、**要約だけが嘘をつく** ことは問題②の核心です。これはグラフ監査では検知できません。G\* は **要約段のハルシネーションを水際で防ぐ** 層であり、データ品質（DE）と回答の忠実度（AI）を **混同しない** ために L 系列とは別記号にしています。

---

## まとめ

現代のデータエンジニアとAIエンジニアにとって、オントロジーは高尚な「論理推論の仕組み」（[シーズン1 第2部](https://zenn.dev/yohei/articles/2026-05-30-vkg-strategy2) で整理した古典的AIの文脈）ではなく、 **「データ品質とエージェントの行動を保護するための開発者向け契約（Contract）」** であるべきです。

この契約を設計し、実際の開発・運用サイクルに組み込むことで、初めて「踏んでも壊れない頑丈な知識グラフ基盤」と「ハルシネーションを起こさない信頼できるAIエージェント」の両立が可能になります。

次回第2部では、上記の各段階（L0〜L4 および G\*）を実装に落とす **「検証タイミング（Validation Timing）の設計」** とアーキテクチャについて掘り下げます。
