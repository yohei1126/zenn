## 1. 卓上ロボット開発における一人運用の負荷

卓上ロボットアームに物体の把持や運搬（Pick-and-Place）を学習させる作業では、ソフトウェアの修正とモデルの学習が頻繁に発生します。筆者は現在、オープンソースの卓上ロボットアーム「[SO-101](https://github.com/TheRobotStudio/SO-ARM100)」を用い、模倣学習フレームワークである [Hugging Face LeRobot](https://github.com/huggingface/lerobot) を使って動作ポリシーの学習を進めています。

しかし、個人開発においてこのサイクルを一人で維持するのは容易ではありません。タスク失敗の原因をコードベースから特定して修正し、テストを実行し、学習ジョブを投入し、学習ログを監視してチェックポイントをシミュレーション環境で評価するという一連の工程を、開発者が手動で順次こなす必要があるためです。特に、コードの微修正や学習プロセスの監視といった定型作業に手を取られると、ポリシーの振る舞い分析や教師データの収集改善といった本来注力すべき判断に集中できなくなります。

そこで本記事では、スマートフォンのチャットから一言指示を出すだけで、コード修正からローカルマシンでの学習・評価までを自動で進める開発体制を紹介します。窓口となるチャットインターフェースには Grok Bot を使い、コードの調査や修正には [Cursor Cloud Agents](https://docs.cursor.com/agent/overview) を、GPU を用いたモデル学習とシミュレーション評価には自宅の MacBook Pro M4 上で常駐する [Cursor Self-Hosted Machine](https://docs.cursor.com/agent/self-hosted) を割り当てています。

この構成を導入すると、外出先からスマートフォンで修正を指示し、自宅の Mac で学習を走らせ、帰宅中や移動中に GitHub 上で評価結果を確認できるようになります。本記事の対象は、シミュレーション環境における ACT（Action Chunking with Transformers）ポリシーの学習と評価です。エージェントの役割分担、実行環境の選定理由、運用ルール、直面した課題とその回避策を順に説明します。実機 SO-101 への物理展開は次回の記事で扱います。

## 2. システム全体の構成と責務の分離

全体の協調動作は、チャット窓口、クラウド上のコーディング環境、ローカルマシンの実行環境、そして共有ストレージとしての GitHub リポジトリの4要素で成立しています。

```mermaid
flowchart TD
    User["開発者（スマートフォン）"] -->|"自然言語で依頼・進捗確認"| Grok["Grok Bot（対話窓口・ルーティング）"]
    
    subgraph ExecutionLayer["実行基盤"]
        CloudAgent["Cursor クラウドエージェント<br/>（VM環境：コード調査・Issue/PR作成）"]
        MacWorker["MacBook Pro M4 ワーカー<br/>（Self-Hosted Machine：MPS学習・評価）"]
    end
    
    Grok -->|"コード修正・PR作成を指示"| CloudAgent
    Grok -->|"学習・シミュレーション評価を指示"| MacWorker
    
    CloudAgent -->|"ブランチ作成・PR提出"| GitHub["GitHub リポジトリ"]
    MacWorker -->|"コード取得・評価結果をPRにコメント"| GitHub
    
    GitHub -.->|"Issue/PR・コメントの更新"| Grok
    Grok -->|"完了報告・結果要約"| User
```

各構成要素が担う役割は以下のとおりです。

- **Grok Bot（窓口・ルーティング）**: 開発者からの自然言語指示を受け取り、作業内容に応じてクラウドエージェントかローカルワーカーのどちらを起動するか判断します。実行中は一定間隔で進捗を確認し、ジョブ完了時に要約をチャットへ返信します。
- **Cursor クラウドエージェント（コード変更・管理）**: Cursor が管理するクラウド VM 上で動作し、リポジトリのコード調査、バグ修正、テスト実行、Issue や Pull Request（PR）の作成、マージコンフリクトの解消を担当します。
- **MacBook Pro M4 上の Cursor エージェント（計算処理ワーカー）**: 開発者のローカルマシン上でバックグラウンド動作するセルフホストワーカーです。PyTorch の MPS（Metal Performance Shaders）バックエンドを利用し、ロボットの動作ポリシー学習とシミュレーション環境での評価を実行します。
- **GitHub**: すべての成果物（コミット、PR、評価ログ、評価結果コメント）を集約する単一の真実源（Single Source of Truth）として機能します。

## 3. 計算リソースの選定：学習をどこで実行するか

エージェントをクラウドとローカルに分けた最大の理由は、Cursor クラウドエージェントの実行環境（VM）に GPU が割り当てられていない点にあります。クラウドエージェントの環境はコードの編集や静的解析、軽量な単体テストには適していますが、深層学習フレームワークを用いたテンソル計算を実行する能力はありません。そのため、モデル学習はエージェント外部の計算資源へ逃がす設計が前提となります。

学習を実行する基盤には、大きく分けて二つの選択肢が存在します。

| 選択肢 | 代表的な基盤 | メリット | デメリット・考慮点 |
| :--- | :--- | :--- | :--- |
| **クラウド GPU** | [Modal](https://modal.com/)、[RunPod](https://www.runpod.io/) など | 必要なときだけ高性能 GPU（A100/H100 等）を利用可能。マシンの電源管理が不要 | 起動ごとの従量課金が発生する。環境イメージの同期やデータ転送の設計が必要 |
| **ローカル GPU** | 自宅の Mac（Apple Silicon MPS）、NVIDIA GPU 搭載機 | 手持ちのマシンを使えば追加の計算費用が 0 円。データの外部転送が不要 | マシンを常時起動しておく必要がある。計算能力は手持ち機材のスペックに依存する |

手持ちに専用の NVIDIA GPU マシンがない場合でも、Apple Silicon 搭載の Mac であれば [PyTorch の MPS（Metal Performance Shaders）バックエンド](https://pytorch.org/docs/stable/notes/mps.html) を介して内蔵 GPU を利用できます。今回対象とする LeRobot の ACT ポリシー（5,000 ステップ程度のシミュレーション学習）はモデル規模が比較的小さく、MacBook Pro M4 の MPS 上でも数十分程度で完了します。

したがって本構成では、追加の GPU 費用を発生させず、かつ手元にあるリソースを有効活用するため、自宅の MacBook Pro をセルフホストワーカーとして常駐させる方式を採用しました。コーディング側のクラウドエージェントは「Auto」モードで運用することで X Subscription（Premium、月額 $30）の枠内に収め、学習側の追加インフラ費用も発生しないため、定額の範囲内で開発ループを維持できます。外部モデルを明示指定した場合の課金仕様については第8章で詳述します。

## 4. Grok Bot による指示受付と自律運用の境界

Grok Bot は、開発者と二種類のエージェントの間を取り持つオーケストレーターとして機能します。開発者がスマートフォンのチャット画面から「閉ループ評価でグリッパーが閉じる前に腕が上昇してしまう問題を調べて修正してほしい」あるいは「PR #12 のコードを取り込んで、シミュレーションで 5,000 ステップ学習して結果を報告してほしい」と入力すると、Grok Bot が作業の性質を判定し、適切なエージェントに命令を発行します。

長時間のジョブに対しては、定期的な状態確認（ポーリング）と完了通知を担います。学習やシミュレーション評価は完了までに 30 分から 1 時間程度を要するため、15 分ごとにワーカーのプロセス状態や出力ログを巡回し、全工程が終了した段階でメトリクスの要約をチャットに報告する運用としています。この監視機構により、開発者が端末の前に拘束される事態を防いでいます。

自律エージェントの暴走や意図しない変更を防ぐため、運用プロンプトには明確なルールを埋め込んでいます。

- **Issue 作成の制限**: リポジトリの調査や質問への回答にとどまる場合は Issue を立てず、コード変更を伴う作業に限り Issue と PR を作成させる。
- **モデル選択の固定**: クラウドエージェントのモデルには外部モデルを名名指定せず、原則として「Auto」モードを使用させる（費用の予期せぬ膨張を防ぐため。詳細は第8章）。
- **成果物形式の統一**: 評価結果や集計ログは、GitHub の PR コメントに Markdown 表形式で記録させる。

一方で、すべての判断をエージェントに委ねているわけではありません。PR の最終的なマージ判断と、MacBook 上の物理的・最終的な動作確認は、必ず人間の開発者が実施する境界線（Human-in-the-Loop）を維持しています。

## 5. クラウドエージェントによるコーディングと保守の自律化

クラウドエージェントにコーディングを指示する際は、指示の曖昧さを排す必要があります。指示文には「目的」「完了条件（Done の定義）」「やってはいけないこと（制約事項）」の3点を構造化して記述します。

```text
【目的】
シミュレーション評価環境において、グリッパーが物体を把持する前にアームが上昇を開始し、
タスクが失敗する事象の原因を特定して修正してください。

【完了条件】
1. 該当する制御ロジックの不具合箇所を特定し、Issue を作成すること。
2. 修正用のトピックブランチを作成し、把持完了判定のステート遷移を修正すること。
3. 既存の単体テストがすべて通過することを確認し、PR を作成すること。

【やってはいけないこと】
- モデルのアーキテクチャ定義やハイパーパラメータは変更しないでください。
- main ブランチに直接プッシュしないでください。
```

この指示に基づき、クラウドエージェントはコードベースを探索し、把持完了判定のしきい値とステートマシンの遷移条件に不整合がある事実を突き止めました。エージェントは原因を整理した Issue を発行したうえで、状態遷移フラグの更新順序を修正するコミットを行い、PR を提出しました。

また、評価環境の依存関係に起因するクラッシュの修正にもエージェントが機能しました。シミュレーション評価スクリプトの実行中にプロセスが突如セグメンテーション違反で停止した際、エージェントにログ解析を依頼したところ、GUI 描画ライブラリとヘッドレス環境の衝突を特定しました。エージェントは `faulthandler` を有効化した再現コードを実行してクラッシュ箇所を同定し、`opencv-python` を `opencv-python-headless` へ置き換える依存関係の修正 PR を自律的に作成しました。複数タスクを並行して依頼した結果として PR 間にコンフリクトが生じた場合も、対象ブランチのリベースと競合箇所の解消をエージェントに指示することで解決できています。

## 6. MacBook ワーカーによるモデル学習とシミュレーション評価

ローカルの計算処理は、MacBook Pro M4 上で常駐する [Cursor Self-Hosted Machine](https://docs.cursor.com/agent/self-hosted) が担当します。ワーカーはローカルリポジトリの所定ディレクトリを作業領域とし、Cursor のコントロールプレーンと HTTPS のアウトバウンド接続で通信するため、自宅ルーターのポート開放やインバウンド用 VPN の設定は不要です。

ワーカーが実行する学習ジョブは、Hugging Face LeRobot を用いた ACT（Action Chunking with Transformers）ポリシーの学習です。ACT は [Zhao らの研究（2023）](https://arxiv.org/abs/2304.13705) で提案された模倣学習手法であり、複数ステップの行動（チャンク）をまとめて予測することで動作の滑らかさとタスク成功率を高めます。本環境では、PyTorch のデバイス指定に `mps` を与えて実行します。

```bash
# MacBook Pro 上で実行される学習コマンド例
python -m lerobot.scripts.train \
    --policy.type=act \
    --dataset.repo_id=local/so101_pick_place_sim \
    --device=mps \
    --training.batch_size=8 \
    --training.steps=5000 \
    --output_dir=outputs/train/act_so101_mps
```

学習の進捗は、ワーカーが出力するログと生成されるチェックポイントファイルを通じて確認されます。5,000 ステップの学習が完了すると、ワーカーは続けて 2 つの評価モードを自動実行します。

1. **教師強制評価（Teacher Forcing / Offline Validation）**:
   検証用データセットの観測画像と関節角度を入力し、モデルが出力した行動チャンクと正解行動との間の絶対誤差（L1 損失）を計算します。
2. **閉ループシミュレーション評価（Closed-Loop Rollout）**:
   シミュレータ環境内でモデルにロボットアームを逐次制御させ、物体を指定トレイまで運搬できるかどうかのタスク成功率を計測します。

評価が完了すると、ワーカーは結果を Markdown 表に整形し、該当 PR に自動でコメントを投稿します。

| 評価指標 | ベースライン (main) | 修正版 (PR #12) | 判定 |
| :--- | :--- | :--- | :--- |
| **検証 L1 損失 (val_l1_loss)** | 0.042 | 0.039 | 改善 |
| **閉ループ成功率 (Success Rate)** | 35.0% (7/20) | **85.0% (17/20)** | 大幅改善 |
| **平均到達ステップ数** | 182 steps | 145 steps | 短縮 |

この投稿によって、開発者はスマートフォンの GitHub モバイルアプリを開くだけで、モデルの改善度合いを客観的な数値で把握できます。

## 7. 開発体験における実質的な変化

この3者協調体制を組んだことで、開発作業の進め方には顕著な変化が生じました。

第一に、開発サイクルの物理的な拘束が解消されました。従来はデスクの前に座り、エディタでコードを直し、学習スクリプトを叩いてログを眺める必要がありました。本構成では、外出先や移動中のわずかな合間にスマートフォンの Grok から「把持の判定ロジックを修正して学習を回しておいて」と指示を出すだけで、帰宅する頃には GitHub 上に修正コードと評価結果の双方が揃っています。

第二に、実行インフラの抽象化が進んだ点です。開発者は「どのマシンでどのコマンドを叩くか」を細かく指示する必要がありません。コード修正の指示であればクラウド VM が起動し、学習や重いシミュレーションであれば自宅の Mac が自動的に選定されて実行されます。

第三に、追加の計算機費用を抑えながら学習サイクルを常時維持できる点です。クラウド GPU インスタンスを長時間借りっぱなしにした場合の課金不安や、環境構築のオーバーヘッドを抱えることなく、手元の M4 Mac の計算余力をバックグラウンドで使い倒す運用が定着しました。

## 8. 実践で直面した課題と運用の回避策

実運用を継続する過程では、ツール同士の連携やインフラ特性に起因する摩擦がいくつか生じました。以下に、実際に直面した課題とその対処法を整理します。

### 長時間プロセスの死活監視における死角
ローカルワーカーで数十分に及ぶ学習を回す際、途中で Python プロセスがメモリ不足（OOM）やセグメンテーション違反で異常終了しても、エージェント側で即座に検知できないケースがありました。ワーカーはコマンドの完了を待機し続けるため、外見上は処理中と区別がつかなくなります。
この問題に対しては、学習スクリプトの標準出力をログファイルへ逐次リダイレクトさせ、Grok Bot の巡回時に `pgrep -fl train` によるプロセス生存確認と、ログファイルの末尾（`tail -n 20`）のタイムスタンプ確認を義務付ける運用プロンプトを追加して対処しました。

### クラウド VM の GPU 不在に起因するコマンド失敗
初期の運用では、Grok Bot が学習コマンドを誤ってクラウドエージェントに割り当ててしまい、`torch.cuda.is_available()` や MPS デバイスの初期化でエラー終了する事象が頻発しました。
エージェントの自律判断だけに頼るのをやめ、プロンプトのルーティング規則に「`lerobot.scripts.train` および `eval` を含むコマンドは、例外なく MacBook セルフホストワーカーにルーティングする」という決定論的なルールを明記したことで、誤配を完全に抑止できました。

### 並行 PR 間でのマージコンフリクト
クラウドエージェントに複数の修正を同時に依頼すると、それぞれが `main` から分岐した独立ブランチを作成するため、後からマージする PR でほぼ確実にコンフリクトが発生します。
これに対しては、エージェントに「PR を提出する前に必ず最新の `main` をフェッチしてリベースし、コンフリクトが発生した場合はその場で差分を解消してからプッシュする」という行動手順をルール化しました。

### モデル指定と課金構造の落とし穴
個人プランにおけるエージェント運用では、モデル選択によって課金経路が切り替わる点に留意が必要です。具体的には、「Auto」モードを選択した場合は Cost モードとして動作し、X Subscription（Premium、月額 $30）のサブスクリプション枠から消費されます。
しかし、ここで Claude、GPT、Gemini といった外部モデルを名前で直接指定すると、サブスクリプション枠の対象外となり、API の定価に基づいた前払いクレジットから別途引き落とされる仕様になっています。意図しない費用の発生を防ぐため、クラウドエージェントの設定は「Auto」に固定し、プロンプト内でも個別モデル名を指定しない運用ルールを徹底しました。

### チャット形態による機能差
Grok の対話インターフェースには 1 対 1 の個別チャットとグループチャットが存在しますが、外部ツールの呼び出しやバックグラウンドエージェント連携の挙動に差異があり、意図した自動実行がトリガーされない事象を経験しました。運用の安定化を図るため、開発指示と監視の窓口は検証済みの 1 対 1 チャットに統一しています。

### オフライン評価と閉ループ成功率の乖離
ロボット学習特有の問題として、検証データに対する絶対誤差（`val_l1_loss`）の低下が、必ずしもシミュレーション環境でのタスク成功率の向上に直結しないという現象に直面しました。オフライン誤差が下がっていても、閉ループ実行時には誤差が累積してロボットアームがあらぬ方向へ動いてしまうケースがあります。
そのため、エージェントの完了判定基準にオフラインの損失値だけを用いることを禁止し、必ずシミュレータ環境での「閉ループ評価成功率」を計測して PR に報告させる運用に改めました。

## 9. 自律開発の境界線と次回予告

本記事で実践したワークフローは、窓口（Grok Bot）、コード修正（Cursor Cloud Agent）、計算処理（MacBook Self-Hosted Worker）の3者に責務を分解することで、個人のロボット開発における作業負荷を大きく削減できることを示しています。

自律運用の成否を分けるのは、エージェントにすべてを丸投げすることではなく、**各ツールの物理的制約（GPU の有無、課金体系、接続経路）に合わせて明確な境界線を引くこと**にあります。コード調査と PR 作成はクラウドに逃がし、重い学習とシミュレーションは手元の M4 Mac に引き受けさせ、マージと物理確認の責任は人間が保持するという役割分担こそが、安定した一人運用を支える基盤となります。

次回は、本記事で学習・検証した ACT ポリシーのチェックポイントを、シミュレーション環境から卓上ロボットアーム「SO-101」の実機へ展開し、実世界のカメラ画像とサーボモーター制御を組み合わせて物体を把持させる実践プロセスを解説します。

## 付録

### A. エージェントへの指示プロンプト例

#### コーディング依頼プロンプト（クラウドエージェント向け）
```text
【作業目的】
閉ループシミュレーション評価スクリプト（scripts/eval_closed_loop.py）実行時に、
タイムアウトで失敗したエピソードの挙動ログを分析し、
グリッパーの開閉状態とアーム軌道の遷移ロジックを修正してください。

【制約・ルール】
- 変更理由と修正方針を Issue に簡潔に記載すること。
- main ブランチからトピックブランチを切って作業すること。
- モデルのハイパーパラメータやネットワーク構成は変更しないこと。
- 最新の main をリベースしてコンフリクトがない状態で PR を作成すること。
```

#### 学習・評価依頼プロンプト（MacBook ワーカー向け）
```text
【作業目的】
PR #{PR_NUMBER} のブランチをローカルにチェックアウトし、
SO-101 のシミュレーションデータセットを用いて ACT ポリシーの学習と評価を実行してください。

【実行手順】
1. デバイスに 'mps' を指定し、5000 ステップの学習を実行する。
2. 学習完了後、オフライン L1 損失の算出と、20 エピソードの閉ループシミュレーション評価を実施する。
3. 評価指標（val_l1_loss、成功率、平均ステップ数）を Markdown 表に整形し、PR #{PR_NUMBER} にコメント投稿する。
```

### B. 主要用語の解説

- **ACT (Action Chunking with Transformers)**:
  ロボットの連続的な動作軌道を複数ステップのひとかたまり（チャンク）として一度に予測する模倣学習モデル。予測のばらつきを抑え、高精度なマニピュレーションを可能にします。
- **MPS (Metal Performance Shaders)**:
  Apple Silicon の GPU 機能を macOS 上のフレームワークから利用するためのバックエンド。PyTorch では `torch.device("mps")` を指定することで、CUDA と同様にハードウェアアクセラレーションを有効化できます。
- **閉ループ評価 (Closed-Loop Evaluation)**:
  モデルが出力した動作によって環境（シミュレータまたは実機）の状態が変化し、その変化した観測画像やセンサ値を次の入力として逐次的に制御を進める評価手法。誤差の累積に対する頑健性を測定できます。
- **教師強制 (Teacher Forcing)**:
  系列データの学習・評価において、モデルの過去の予測値ではなく、正解データ（教師データ）の観測と行動を各ステップの入力として与える手法。モデル自身の蓄積誤差を切り離して単一ステップの予測精度を測る指標となります。
