提案用・議論用のスライド資料を、Grok Bot にチャットで頼むだけで、Markdown の下書きから GitHub Release に添付した PDF まで作れるようにしました。Markdown から PDF を組み立てる生成器は [md-deck](https://github.com/yohei1126/md-deck) という名前で、OSS として公開しています。

登場するのは、論点を伝えて版を確定させる書き手（私）、依頼を受けて Markdown を書き直す Grok Bot、スライド本文とスタイルガイドを置くスライド資料のリポジトリ、Markdown を検証して PDF にする md-deck、そしてタグの push で PDF をビルドして Release に添付する GitHub Actions です。

![登場人物と流れ。書き手⇔Grok Bot→スライド資料リポジトリ→md-deck、レビュー用PDFはGrok Botへ戻り、書き手のOK後にタグ→GitHub Actions→Release](/images/md-deck-flow.png)

上段では書き手と Grok Bot がやり取りし、破線は md-deck が作ったレビュー用 PDF が Grok Bot に戻る経路です。下段が書き手の OK のあとに版を確定させて Release に PDF を載せる流れです。

## NotebookLM で作っていたときの二つの不満

これまでスライド資料は Google NotebookLM で作っていました。資料を読み込ませて構成と文面を出してもらう用途では十分に役立ち、最初の一枚目を作るまでの速さには満足していました。

不満の一つ目は、作り直すたびに資料をアップロードし直す手間です。スライド資料は一度作って終わりではなく、議論の相手や論点が変わるたびに直します。そのたびに元資料を揃えて読み込ませる作業が発生し、直したい箇所が一行だけでも同じ手順を踏む必要がありました。

二つ目は、生成し直すと見た目が変わりやすいことです。レイアウトや配色、文字の詰め方が回ごとに揺れるので、前の版と並べて差分を確認しにくくなります。議論用のスライド資料では「前回からどこが変わったか」を相手と共有したい場面が多く、見た目の揺れが内容の差分を見分ける妨げになっていました。

この二つの不満は原因が別です。前者は、スライド資料の元になる情報が、手元で再利用できる形で残っていないことから生じます。後者は、生成のたびにレイアウトまで作り直していることから生じます。そこで、元情報はリポジトリの Markdown として持ち、レイアウトは決定的に（同じ入力からは同じ出力になるように）組む生成器に任せる、という分け方にしました。

## スライド資料のリポジトリと md-deck の分担

構成は、スライド資料ごとのリポジトリと、共通の生成器である md-deck の二つに分かれます。

| 置き場所 | 持つもの |
| --- | --- |
| スライド資料のリポジトリ | スライド本文の Markdown（`slides.md` など）、スタイルガイドの Markdown（`deck_style.md` など）、タグで PDF をビルドするワークフロー、Release に添付した PDF |
| md-deck | 入力の検証、Markdown から PDF までの組み立て、再利用できる GitHub Action |

**md-deck 自体はブランドの配色やフォントを持つテーマを同梱していません。** スタイルファイルの指定は必須で、指定がなければビルドは失敗します。テーマを生成器側に持たせると、生成器を更新したときに既存のスライド資料の見た目まで変わる可能性があり、スライド資料ごとに見た目を固定したいという目的と衝突するためです。

## どのツールを何に使っているか

図に出てくる要素と、その裏で使っている道具を、目的ごとに並べると次のようになります。

| ツール | 使う目的 |
| --- | --- |
| Grok Bot | チャットでの依頼の受付、`slides.md` の下書きと修正、スタイルガイドに沿っているかのレビュー、書き手の OK を受けたあとのリリースタグ付け |
| md-deck（CLI / GitHub Action） | 入力の検証、Markdown から HTML への変換、headless Chromium による 16:9 の PDF 化、PDF のメタデータの固定 |
| uv（`uvx`） | md-deck を PyPI に登録していないので、Git のタグを指定して md-deck を実行する |
| Playwright + Chromium | md-deck の内部で、HTML を PDF に描画する |
| GitHub Actions / GitHub Release | タグの push をきっかけに PDF をビルドし、Release に成果物として添付する |

md-deck のビルドでは、PDF を書く前に必ず入力の検証が走り、スライドからのはみ出しなどがあれば PDF を書かずに止まります。PDF を書き出したあとは、作成日時と更新日時を固定値に書き換えます。メタデータに日時が入ったままだと、ビルドした時刻が違うだけで PDF のバイト列が変わってしまうためです。

以前使っていた NotebookLM は、この表には入りません。資料の再アップロードと見た目の揺れという二つの不満から、上の組み合わせに置き換えました。

## md-deck に渡す入力ファイル

md-deck が受け取る入力は、スライド本文の Markdown とスタイルの Markdown の二つです。どちらも見本を [examples フォルダ](https://github.com/yohei1126/md-deck/tree/main/examples) に置いています。

スライド本文の Markdown は、front matter に `title`、`version`、`date`、`lang`、`style` の五つを必ず書きます。`style` にはスタイルの Markdown への相対パスを書き、本文は `---` でスライドを区切ります。本文から相対パスで画像を参照する場合は、その画像もスライドのファイルの隣（またはその下）に置きます。

スタイルの Markdown は、front matter に配色やフォントなどのトークンを YAML で書き、その下に書き手が読む文章の規範を書く形式です。必須のトークンは `color_background`、`color_text`、`color_title`、`font_family`、`font_size_body` の五つで、ほかのトークンは省略すると白黒の素の既定値になります。追加の CSS を書きたいときは、任意で `css` のコードブロックを置けます。トークンは md-deck が読み取ってレイアウトに反映し、文章の規範は書き手（私でも Grok Bot でも）が読んでスライドの文面に反映します。一つのファイルを md-deck と書き手の両方が参照するので、スライド資料の「見た目」と「書き方」の決まりが一か所にまとまります。

examples フォルダの三つのファイルは、それぞれ次の見本です。

| ファイル | 何の見本か |
| --- | --- |
| [deck_style.md](https://github.com/yohei1126/md-deck/blob/main/examples/deck_style.md) | スタイルの Markdown。YAML のトークン、書き手が読む規範、任意の CSS の三つを含む。白黒の見本であり、本番のテーマではない |
| [sample.md](https://github.com/yohei1126/md-deck/blob/main/examples/sample.md) | スライド本文の Markdown。入力の決まりと記法を一通り使った見本で、front matter の `style: deck_style.md` で上のスタイルを指す |
| [routing_demo.md](https://github.com/yohei1126/md-deck/blob/main/examples/routing_demo.md) | 図（`::: flow`）の見本。レーンをまたぐ矢印をノードを避けて直角に折り曲げる配置などを確認できる |

実際のスライド資料では、`deck_style.md` を自分の配色とフォントで書き換えたものをスライド資料のリポジトリに置きます。examples の見本は、生成器を試すためのものという位置づけです。

## チャットからタグまでの手順

この分担を前提に、スライド資料作りの手順はほぼチャットでのやり取りに置き換わりました。依頼先は、私がデスクトップとチャットで使っている Grok Bot です。

1. チャットで「こういう論点でスライド資料を作って」と依頼します。Grok Bot はスライド資料のリポジトリにあるスタイルガイドを読んだうえで `slides.md` を下書きし、md-deck で検証とビルドをして PDF を見せます。
2. 中身を見て、構成や言い回しの修正をチャットで伝えます。Grok Bot は Markdown を直してビルドし直します。元情報がリポジトリに残っているので、資料を再アップロードする手順はありません。
3. 必要なら Grok Bot にレビューも頼みます。スタイルガイドの規範に照らして、論理の飛躍や表記の揺れを指摘してもらいます。
4. 内容に納得したら、私が「OK」と伝えます。そこで初めて Grok Bot がリリースタグを打ちます。
5. タグの push をきっかけに、スライド資料のリポジトリの GitHub Actions が md-deck の Action で PDF をビルドし、Release に成果物として添付します。

**タグを打つのは書き手の OK のあとに限っています。** 下書きや修正版の PDF はいくらでも作り直せますが、Release に載った PDF は「この版で話した」という記録として相手と共有するものだからです。どの版を確定させるかは書き手が判断し、そのあとのタグ付け、ビルド、添付は機械的に進むようにしました。

Release に PDF を添付する形にしたのは、版と成果物の対応を GitHub 上で一意にするためです。タグ名から、その時点の `slides.md` と `deck_style.md`、そして生成された PDF の三つを辿れます。PDF そのものをリポジトリにコミットする方法もありますが、その場合は Markdown と食い違った PDF がコミットされる余地が残ります。タグを起点に CI でビルドすれば、CI はそのタグの時点の Markdown から PDF を作るので、添付される PDF とタグの Markdown が食い違うことはありません。

## ほかに検討した二つの方法

この形に決める前に、二つの方法を検討して採りませんでした。

一つ目は、NotebookLM を使い続けて、運用で手間を減らす方法です。資料をまとめてから一度に読み込ませるなどの工夫はできますが、再アップロードが必要な構造と、生成し直すと見た目が揺れる性質は残ります。そのため、版ごとの差分を相手と確認したい用途には合わないと判断しました。

二つ目は、生成器を非公開のまま、各スライド資料のリポジトリにスクリプトをコピーして使う方法です。最初は手軽ですが、スライド資料が増えるたびにスクリプトの写しが増え、どの写しに修正を入れたかが分からなくなります。これに対して OSS として一つのリポジトリにまとめておけば、各スライド資料のリポジトリはタグを指定して同じ生成器を取り込めます。生成器の更新を取り込むかどうかも、スライド資料ごとにタグを書き換えるかどうかで選べます。生成器には顧客や案件に固有の情報が含まれないので、公開しても困ることはありませんでした。

## md-deck を手元と GitHub Actions で試すには

md-deck は現在 v0.1.0 のタグを公開しています。手元で試すなら、リポジトリを取得して examples の見本をそのまま入力にするのが手早い方法です。

```bash
git clone https://github.com/yohei1126/md-deck.git
cd md-deck
uvx --from git+https://github.com/yohei1126/md-deck@v0.1.0 md-deck \
  check examples/sample.md
uvx --from git+https://github.com/yohei1126/md-deck@v0.1.0 md-deck \
  build examples/sample.md -o sample.pdf
```

`check` は Chromium を使わずに入力だけを検証し、問題を `ファイル:行: メッセージ` の形で列挙します。`build` は同じ検証を通ったときだけ PDF を書き出します。`examples/routing_demo.md` に差し替えれば、図の見本も同じ手順でビルドできます。手元に Playwright の Chromium がない場合は、`build` の前に `uvx --from git+https://github.com/yohei1126/md-deck@v0.1.0 playwright install chromium` で取得しておきます。

自分のスライド資料で使うときは、`examples/deck_style.md` と `examples/sample.md` をスライド資料のリポジトリにコピーし、配色と本文を書き換えるところから始められます。スタイルファイルは、スライドの front matter の `style:` で指定するか、`--style` で渡します。

GitHub Actions からは、タグを固定して Action を呼び出します。

```yaml
- uses: yohei1126/md-deck@v0.1.0
  with:
    source: deck/slides.md
    style: deck/deck_style.md
    output: dist/deck.pdf
```

タグの push で PDF をビルドして Release に添付するワークフローの例、スライドの記法、スタイルのトークン一覧は、[README](https://github.com/yohei1126/md-deck) と `docs/` 以下にまとめています。

## 決定的なビルドで保証できる範囲

同じ入力から同じ PDF が出るのは、同じ環境でビルドした場合に限られます。PDF のメタデータの日時は固定していますが、Chromium のバージョンやインストールされているフォントが違えば、描画結果も変わります。環境をまたいでピクセル単位で揃えたい場合は、Action のタグを固定するのと同じように、CI 上の Chromium とフォントも固定する必要があります。手元の環境で揃っているかどうかは、`build --check-deterministic` で二回ビルドし、バイト列が一致するかで確認できます。

日本語のスライド資料では、PDF を描画するマシンに CJK フォントが必要です。Action ではビルド前に Noto CJK を入れていますが、手元で `uvx` から実行するときは、Debian/Ubuntu なら `fonts-noto-cjk` などを自分で入れておく必要があります。

また、md-deck が決定的にするのはレイアウトだけです。スライドの論理が通っているか、相手にとって必要な情報が揃っているかは、書き手と、書き手が依頼した Grok Bot のレビューで確かめることになります。md-deck で得られるのは、直した箇所以外の見た目が変わらないことと、確定させた版を Release から辿れることです。

## いまできることと、この先やりたいこと

いまの時点でできるのは、Grok Bot へのチャットでの依頼から、書き手の OK を経て、タグに対応する PDF が Release に載るところまでです。生成器の md-deck は v0.1.0 として OSS で公開しており、examples の見本を使えば手元でも同じ検証とビルドを試せます。一方で、バイト単位で同じ PDF が出るのは Chromium とフォントが揃った環境に限られ、日本語の資料では CJK フォントを自分で用意する必要があります。

この先は、いまの制約に対応する次の三つを候補として考えています。

- PyPI への公開。現在は Git のタグを `uvx` に渡して実行しているので、パッケージ名だけで入れられるようにしたいと考えています。
- CJK フォントと Chromium の固定。手元と CI で描画を揃える手順を、利用者が個別に組まなくて済む形にできないか検討しています。
- スライド資料のリポジトリ側のテンプレート。`deck_style.md`、`slides.md`、タグで Release に PDF を添付するワークフローを一式にしておけば、新しいスライド資料を始める手間を減らせると考えています。

どれも公開時期を決めたものではありません。まずは自分のスライド資料で使いながら、困った箇所から順に手を入れていくつもりです。同じ形でスライド資料を作ってみたい場合は、examples の `deck_style.md` を自分の配色とフォントに書き換え、`check` が通るところまで進めるところから始めてみてください。
