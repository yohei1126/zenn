提案用・議論用のデッキを、チャットでの依頼だけで下書きから GitHub Release の PDF まで作れるようにしました。デッキの中身とスタイルガイドは各デッキのリポジトリに Markdown で置き、PDF を組み立てる生成器は [md-deck](https://github.com/yohei1126/md-deck) という OSS に切り出しています。同じ Markdown からは同じ PDF が出ることを目標にしており、公開してよい版かどうかは、人がレビューして OK を出してからタグで確定させます。

## NotebookLM で作っていたときの二つの不満

これまでデッキは Google NotebookLM で作っていました。資料を読み込ませて構成と文面を出してもらう用途では十分に役立ち、最初の一枚目を作るまでの速さには満足していました。

不満の一つ目は、作り直すたびに資料をアップロードし直す手間です。デッキは一度作って終わりではなく、議論の相手や論点が変わるたびに直します。そのたびに元資料を揃えて読み込ませる作業が発生し、直したい箇所が一行でも同じ手順を踏む必要がありました。

二つ目は、生成し直すと見た目が変わりやすいことです。レイアウトや配色、文字の詰め方が回ごとに揺れるので、前の版と並べて差分を確認する作業がしにくくなります。議論用のデッキでは「前回からどこが変わったか」を相手と共有したい場面が多く、見た目の揺れはそのままノイズになっていました。

二つの不満は原因が別です。前者は、デッキの元になる情報が手元の再利用できる形で残っていないことから生じます。後者は、生成のたびにレイアウトも作り直していることから生じます。そこで、元情報をリポジトリの Markdown として持ち、レイアウトは決定的に組む生成器に任せる、という分け方にしました。

## デッキのリポジトリと md-deck の分担

構成は、デッキごとのリポジトリと、共通の生成器である md-deck の二つに分かれます。

| 置き場所 | 持つもの |
| --- | --- |
| デッキのリポジトリ | スライド本文の Markdown（`slides.md` など）、スタイルガイドの Markdown（`deck_style.md` など）、Release に添付した PDF |
| md-deck | 入力の検証、Markdown から HTML への変換、headless Chromium による PDF 化、再利用できる GitHub Action |

スタイルガイドの Markdown は、配色やフォントなどのトークンを YAML で書き、その下に人が読む文章の規範を書く形式です。トークンは md-deck が読んでレイアウトに反映し、文章の規範は書き手（人でも Grok Bot でも）が読んでスライドの文面に反映します。同じファイルが機械向けと書き手向けの両方の役割を持つので、デッキの「見た目」と「書き方」が一か所にまとまります。

**md-deck 自体はデフォルトのテーマを持ちません。** スタイルファイルの指定は必須で、指定がなければビルドは失敗します。テーマを生成器側に持たせると、生成器を更新したときに既存デッキの見た目まで変わる可能性があり、デッキごとに見た目を固定したいという目的と衝突するためです。md-deck の `examples/` にはスライドとスタイルの見本がありますが、生成器を試すためのサンプルという位置づけで、実際のデッキや PDF は呼び出す側のリポジトリで管理します。

生成器の処理は、Markdown を HTML にし、それを headless Chromium で 16:9 の PDF に印刷する流れです。ビルドの前には必ず入力の検証が走り、スライドからのはみ出しなどがあれば PDF を書かずに止まります。PDF を書き出したあとは、作成日時などのメタデータを固定値に書き換えます。これは、ビルドした時刻の違いだけで PDF のバイト列が変わるのを防ぐためです。

## チャットからタグまでの流れ

この分担の上で、デッキ作りの手順はチャットでのやり取りにほぼ置き換わりました。依頼先は、デスクトップとチャットで使っている Grok Bot です。

1. チャットで「こういう論点でデッキを作って」と依頼します。Grok Bot はデッキのリポジトリにあるスタイルガイドを読んだうえで `slides.md` を下書きし、md-deck で検証とビルドをして PDF を見せます。
2. 中身を見て、構成や言い回しの修正をチャットで伝えます。Grok Bot は Markdown を直してビルドし直します。元情報がリポジトリに残っているので、資料を再アップロードする手順はありません。
3. 必要なら Grok Bot にレビューも頼みます。スタイルガイドの規範に照らして、論理の飛躍や表記の揺れを指摘してもらいます。
4. 内容に納得したら、私が「OK」と伝えます。そこで初めて Grok Bot がリリースタグを打ちます。
5. タグの push をきっかけに、デッキのリポジトリの GitHub Actions が md-deck の Action で PDF をビルドし、Release に成果物として添付します。

**タグを打つのは人の OK のあとに限っています。** 下書きや修正版の PDF はいくらでも作り直せますが、Release に載った PDF は「この版で話した」という記録として相手と共有するものです。どの版を確定させるかの判断は書き手が持ち、そのあとの作業（タグ付け、ビルド、添付）は機械的に進むようにしました。

Release に PDF を添付する形にしたのは、版と成果物の対応を GitHub 上で一意にするためです。タグ名から、その時点の `slides.md` と `deck_style.md`、そして生成された PDF の三つを辿れます。PDF そのものをリポジトリにコミットする方法もありますが、その場合は Markdown と PDF が食い違ったままコミットされる余地が残ります。タグを起点に CI でビルドすれば、添付される PDF は必ずそのタグの Markdown から作られたものになります。

## 検討して採らなかった選択肢

一つ目は、NotebookLM を使い続けて運用で手間を減らす案です。資料をまとめてから一度に読み込ませるなど工夫の余地はありますが、再アップロードが必要な構造と、生成し直すと見た目が揺れる性質は残ります。版ごとの差分を相手と確認したい用途には合わないと判断しました。

二つ目は、生成器を非公開のまま、各デッキのリポジトリにスクリプトをコピーして使う案です。最初は手軽ですが、デッキが増えるたびにスクリプトの写しが増え、修正をどこに入れたかが分からなくなります。OSS として一つのリポジトリにまとめておけば、各デッキはタグを指定して同じ生成器を取り込めます。生成器の更新を取り込むかどうかも、デッキごとにタグの書き換えで選べます。生成器には顧客や案件に固有の情報が含まれないので、公開しても困ることはありませんでした。

## 手元で試す

md-deck は現在 v0.1.0 のタグを公開しています。PyPI にはまだ登録していないので、uv の `uvx` で Git のタグを直接指定して実行します。

```bash
uvx --from git+https://github.com/yohei1126/md-deck@v0.1.0 md-deck \
  check slides.md
uvx --from git+https://github.com/yohei1126/md-deck@v0.1.0 md-deck \
  build slides.md -o out.pdf
```

`check` は Chromium を使わずに入力だけを検証し、問題を `ファイル:行: メッセージ` の形で列挙します。`build` は同じ検証を通ったときだけ PDF を書き出します。スライドの front matter で `style:` にスタイルファイルを指定するか、`--style` で渡す必要があります。最初は `examples/` の見本をコピーして書き換えるのが手早いと思います。

GitHub Actions からは、タグを固定して Action を呼び出します。

```yaml
- uses: yohei1126/md-deck@v0.1.0
  with:
    source: deck/slides.md
    style: deck/deck_style.md
    output: dist/deck.pdf
```

タグの push で PDF をビルドして Release に添付するワークフローの例、スライドの記法、スタイルのトークン一覧は [README](https://github.com/yohei1126/md-deck) と `docs/` 以下にまとめています。

## 決定的なビルドで保証できる範囲

同じ入力から同じ PDF が出るのは、同じ環境でビルドした場合です。PDF のメタデータの日時は固定していますが、Chromium のバージョンやインストールされているフォントが違えば描画結果も変わります。環境をまたいでピクセル単位で揃えたいなら、Action のタグを固定するのと同じように、CI 上の Chromium とフォントも固定する必要があります。`build --check-deterministic` を使うと、二回ビルドしてバイト列が一致するかを確認できます。

日本語のデッキには、PDF を描画するマシンに CJK フォントが必要です。Action ではビルド前に Noto CJK を入れていますが、手元で `uvx` から実行するときは、Debian/Ubuntu なら `fonts-noto-cjk` などを自分で入れておく必要があります。

md-deck が決定的にするのはレイアウトだけです。スライドの論理が通っているか、相手にとって必要な情報が揃っているかは、書き手と、書き手が依頼した Grok Bot のレビューの仕事として残ります。生成器が担うのは、直した箇所以外の見た目を変えずに済ませることと、確定させた版を Release から辿れるようにすることです。

次にデッキを作るときは、まず手元の資料から `deck_style.md` を一つ書き、`examples/` の見本と並べて `check` を通すところから始めるのがよいと思います。スタイルが決まれば、そのあとの下書きと修正はチャットの往復に任せられます。
