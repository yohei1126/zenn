提案用・議論用のスライド資料を、Grok Bot へのチャットでの依頼だけで、下書きから GitHub Release の PDF まで作れるようにしました。中身とスタイルガイドは、各スライド資料のリポジトリに Markdown で置き、PDF を組み立てる生成器は [md-deck](https://github.com/yohei1126/md-deck) という OSS に切り出しています。同じ Markdown からは同じ PDF が出ることを目標にしています。公開してよい版かどうかは、人がレビューして OK を出してからタグで確定させます。

## NotebookLM で作っていたときの二つの不満

これまでスライド資料は Google NotebookLM で作っていました。資料を読み込ませて構成と文面を出してもらう用途では十分に役立ち、最初の一枚目を作るまでの速さには満足していました。

不満の一つ目は、作り直すたびに資料をアップロードし直す手間です。スライド資料は一度作って終わりではなく、議論の相手や論点が変わるたびに直します。そのたびに元資料を揃えて読み込ませる作業が発生し、直したい箇所が一行だけでも同じ手順を踏む必要がありました。

二つ目は、生成し直すと見た目が変わりやすいことです。レイアウトや配色、文字の詰め方が回ごとに揺れるので、前の版と並べて差分を確認しにくくなります。議論用のスライド資料では「前回からどこが変わったか」を相手と共有したい場面が多く、見た目の揺れが内容の差分を見分ける妨げになっていました。

この二つの不満は原因が別です。前者は、スライド資料の元になる情報が、手元で再利用できる形で残っていないことから生じます。後者は、生成のたびにレイアウトまで作り直していることから生じます。そこで、元情報はリポジトリの Markdown として持ち、レイアウトは決定的に（同じ入力からは同じ出力になるように）組む生成器に任せる、という分け方にしました。

## スライド資料のリポジトリと md-deck の分担

構成は、スライド資料ごとのリポジトリと、共通の生成器である md-deck の二つに分かれます。

| 置き場所 | 持つもの |
| --- | --- |
| スライド資料のリポジトリ | スライド本文の Markdown（`slides.md` など）、スタイルガイドの Markdown（`deck_style.md` など）、Release に添付した PDF |
| md-deck | 入力の検証、Markdown から HTML への変換、headless Chromium による PDF 化、再利用できる GitHub Action |

スタイルガイドの Markdown は、配色やフォントなどのトークンを YAML で書き、その下に人が読む文章の規範を書く形式です。トークンは md-deck が読み取ってレイアウトに反映し、文章の規範は書き手（私でも Grok Bot でも）が読んでスライドの文面に反映します。一つのファイルを md-deck と書き手の両方が参照するので、スライド資料の「見た目」と「書き方」の決まりが一か所にまとまります。

**md-deck 自体はデフォルトのテーマを持ちません。** スタイルファイルの指定は必須で、指定がなければビルドは失敗します。テーマを生成器側に持たせると、生成器を更新したときに既存のスライド資料の見た目まで変わる可能性があり、スライド資料ごとに見た目を固定したいという目的と衝突するためです。

同じ理由で、md-deck の `examples/` にあるスライドとスタイルは、生成器を試すための見本という位置づけにしています。実際のスライド資料と PDF は、md-deck を呼び出す側のリポジトリで管理します。

生成器の処理は、Markdown を HTML に変換し、それを headless Chromium で 16:9 の PDF に印刷する流れです。ビルドの前には必ず入力の検証が走り、スライドからのはみ出しなどがあれば PDF を書かずに止まります。

PDF を書き出したあとは、作成日時などのメタデータを固定値に書き換えます。メタデータに日時が入ったままだと、ビルドした時刻が違うだけで PDF のバイト列が変わってしまうためです。

## チャットからタグまでの手順

この分担を前提に、スライド資料作りの手順はほぼチャットでのやり取りに置き換わりました。依頼先は、私がデスクトップとチャットで使っている Grok Bot です。

1. チャットで「こういう論点でスライド資料を作って」と依頼します。Grok Bot はスライド資料のリポジトリにあるスタイルガイドを読んだうえで `slides.md` を下書きし、md-deck で検証とビルドをして PDF を見せます。
2. 中身を見て、構成や言い回しの修正をチャットで伝えます。Grok Bot は Markdown を直してビルドし直します。元情報がリポジトリに残っているので、資料を再アップロードする手順はありません。
3. 必要なら Grok Bot にレビューも頼みます。スタイルガイドの規範に照らして、論理の飛躍や表記の揺れを指摘してもらいます。
4. 内容に納得したら、私が「OK」と伝えます。そこで初めて Grok Bot がリリースタグを打ちます。
5. タグの push をきっかけに、スライド資料のリポジトリの GitHub Actions が md-deck の Action で PDF をビルドし、Release に成果物として添付します。

**タグを打つのは人の OK のあとに限っています。** 下書きや修正版の PDF はいくらでも作り直せますが、Release に載った PDF は「この版で話した」という記録として相手と共有するものだからです。どの版を確定させるかは書き手が判断し、そのあとのタグ付け、ビルド、添付は機械的に進むようにしました。

Release に PDF を添付する形にしたのは、版と成果物の対応を GitHub 上で一意にするためです。タグ名から、その時点の `slides.md` と `deck_style.md`、そして生成された PDF の三つを辿れます。PDF そのものをリポジトリにコミットする方法もありますが、その場合は Markdown と食い違った PDF がコミットされる余地が残ります。タグを起点に CI でビルドすれば、CI はそのタグの時点の Markdown から PDF を作るので、添付される PDF とタグの Markdown が食い違うことはありません。

## ほかに検討した二つの方法

この形に決める前に、二つの方法を検討して採りませんでした。

一つ目は、NotebookLM を使い続けて、運用で手間を減らす方法です。資料をまとめてから一度に読み込ませるなどの工夫はできますが、再アップロードが必要な構造と、生成し直すと見た目が揺れる性質は残ります。そのため、版ごとの差分を相手と確認したい用途には合わないと判断しました。

二つ目は、生成器を非公開のまま、各スライド資料のリポジトリにスクリプトをコピーして使う方法です。最初は手軽ですが、スライド資料が増えるたびにスクリプトの写しが増え、どの写しに修正を入れたかが分からなくなります。これに対して OSS として一つのリポジトリにまとめておけば、各スライド資料のリポジトリはタグを指定して同じ生成器を取り込めます。生成器の更新を取り込むかどうかも、スライド資料ごとにタグを書き換えるかどうかで選べます。生成器には顧客や案件に固有の情報が含まれないので、公開しても困ることはありませんでした。

## md-deck を手元と GitHub Actions で試すには

md-deck は現在 v0.1.0 のタグを公開しています。PyPI にはまだ登録していないので、uv の `uvx` で Git のタグを直接指定して実行します。

```bash
uvx --from git+https://github.com/yohei1126/md-deck@v0.1.0 md-deck \
  check slides.md
uvx --from git+https://github.com/yohei1126/md-deck@v0.1.0 md-deck \
  build slides.md -o out.pdf
```

`check` は Chromium を使わずに入力だけを検証し、問題を `ファイル:行: メッセージ` の形で列挙します。`build` は同じ検証を通ったときだけ PDF を書き出します。どちらも、スライドの front matter の `style:` でスタイルファイルを指定するか、`--style` で渡す必要があります。最初は `examples/` の見本をコピーして書き換えると手早く始められます。

GitHub Actions からは、タグを固定して Action を呼び出します。

```yaml
- uses: yohei1126/md-deck@v0.1.0
  with:
    source: deck/slides.md
    style: deck/deck_style.md
    output: dist/deck.pdf
```

タグの push で PDF をビルドして Release に添付するワークフローの例、スライドの記法、スタイルのトークン一覧は、[README](https://github.com/yohei1126/md-deck) と `docs/` 以下にまとめています。

## 決定的なビルドで保証できる範囲

同じ入力から同じ PDF が出るのは、同じ環境でビルドした場合に限られます。PDF のメタデータの日時は固定していますが、Chromium のバージョンやインストールされているフォントが違えば、描画結果も変わります。環境をまたいでピクセル単位で揃えたい場合は、Action のタグを固定するのと同じように、CI 上の Chromium とフォントも固定する必要があります。手元の環境で揃っているかどうかは、`build --check-deterministic` で二回ビルドし、バイト列が一致するかで確認できます。

日本語のスライド資料では、PDF を描画するマシンに CJK フォントが必要です。Action ではビルド前に Noto CJK を入れていますが、手元で `uvx` から実行するときは、Debian/Ubuntu なら `fonts-noto-cjk` などを自分で入れておく必要があります。

また、md-deck が決定的にするのはレイアウトだけです。スライドの論理が通っているか、相手にとって必要な情報が揃っているかは、書き手と、書き手が依頼した Grok Bot のレビューで確かめることになります。md-deck で得られるのは、直した箇所以外の見た目が変わらないことと、確定させた版を Release から辿れることです。

## 最初のスライド資料をどこから作るか

これから同じ形でスライド資料を作るなら、まず手元の資料をもとに `deck_style.md` を一つ書き、`examples/` の見本と並べて `check` が通るところまで進めるのがよいと思います。スタイルが決まれば、そのあとの下書きと修正はチャットでの往復に任せられます。
