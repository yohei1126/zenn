# シリーズ記事第3部および実装リポジトリのアライメント計画（改訂版）

本計画は、実装リポジトリの Neo4j 移行計画（`instructions/supply-chain-neo4j-migration-plan.md`）を踏まえ、解説記事第3部（実装編）の執筆方針およびリポジトリとの整合性（アライメント）を整理したものです。

## 1. 食い違いとアライメント方針

### ① 用語の統一: 「Graph Contract（記事）」 ↔ 「Graph Context（実装）」
* **対応済み（2026-06-28）**: リポジトリの YAML SSOT を `ontology/contract/graph_contract.yaml` にリネームし、記事・ドキュメントのパス参照を統一。エージェント向け JSON エクスポート（`graph-context.json`）と `export_graph_context_bundle()` 等の識別子は **graph context** 概念として維持。

### ② ストレージ技術の変更: 「LanceDB」 ➔ 「Neo4j」
* **現状**: リポジトリは現在 LanceDB から Neo4j への移行プロセス中にあります。
* **対応**: 
  - 記事第3部では、ストレージとしての **Neo4j** の利用を前提として執筆します。
  - ベクトル/ハイブリッド検索（`bom_hybrid_query`）は本質的なフェデレーションの論点から外れるため、コードおよび記事から削除し、DuckDB による簡易テキスト検索または ID 直接指定によるアンカリングのみに簡素化します。
  - 組織ごとの「物理分離」は、Docker 上の単一 Neo4j インスタンスにおける **複数データベース（Multi-Database: `ebom`, `routing`, `sourcing`）** 機能で実現します。

## 3. 記事（第3部）の構成および執筆方針

第2部の設計（4大コア論点）を踏まえた実装方針を、**第3部の冒頭に重要な論点に絞って明記**し、詳細はリポジトリを読んでもらう構成にします。

### 3.1 冒頭に明記する設計➔実装のマッピング方針

| 第2部の設計論点 | 第3部の実装アプローチ（コア論点） | 記事での記述・解説方針 |
| :--- | :--- | :--- |
| **① データ所有権の保証** | ディレクトリ分割によるコード主権の明示 (`domains/`) | 各部門の開発・管理境界をリポジトリの配置レベルでいかに保証しているかを簡潔に解説。 |
| **② セキュリティ境界の維持** | Neo4j 複数データベースによる物理分離 (`ebom`, `routing`, `sourcing`) | データを一元化せず、Neo4j のデータベース境界によってアクセス制御や運用を独立させていることを解説。 |
| **③ クエリ品質と信頼性** | 決定論的ツール (`app/tools.py`) による Cypher のカプセル化 | LLM に Cypher を書かせず、事前に定義・検証された Cypher クエリのみをツール経由で呼び出す「ツール境界」の実装を提示。 |
| **④ 運用の容易さ** | Docker Compose によるローカル環境での手軽な起動 | 複雑なインフラ構築を避け、開発者が Docker で即座にマルチDB環境を立ち上げて動作検証できる容易さを強調。 |

### 3.2 ディレクトリ構成図のアップデート
Neo4j および DuckDB を用いた構成に修正します。
```text
├── ontology/
│   ├── contract/
│   │   └── graph_contract.yaml # 共有IDとフェデレーションの契約
│   └── schema.py       # Pydanticノード・エッジ定義
├── domains/            # 各部門（組織）の自律インジェスト領域
├── app/
│   ├── storage/        # Neo4j データベースアクセスドライバ
│   ├── federation/     # クエリ時の論理結合・影響分析エンジン
│   └── tools.py        # エージェント用決定論的ツール定義
└── data/
    └── bom.duckdb      # 共有 Component 属性マスタ (DuckDB)
```
