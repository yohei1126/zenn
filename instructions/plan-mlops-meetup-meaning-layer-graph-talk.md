## 1. 発表のゴール（聴衆が持ち帰ること）

1. **2026 年の主要データプラットフォーム** が、なぜ同時期に「仮想グラフ」と「意味レイヤー（オントロジー自動構築）」を出したかが分かる  
2. **仮想グラフ / 物理グラフ / オントロジー** の違いが、実務の言葉で説明できる  
3. **グラフ構造で知識を表す理由**（多ホップ関係・決定論的制約・LLM へのグラウンディング）が腹落ちする  
4. **記号 AI（厳密・硬い）とニューラル AI（柔軟・誤りうる）の補完関係** が、今の製品動向の背景として理解できる  
5. **自動オントロジー（OntoRank / Cortex Sense）** はセマンティック Web の古い問題を、似た型（統計＋ランキング）で再挑戦している

**MLOps 聴衆向けの接続:**  
モデル精度だけでなく、**データ基盤上の意味の層**（定義・関係・信頼資産）がエージェント品質のボトルネック。MLOps は「推論パイプライン」だけでなく **コンテキスト基盤の設計** とセットで考える必要がある。

### §1 プラットフォーム地図（3 分）— スライド 2–4

**目的（依頼の第一要件）:** 主要 PF の仮想グラフとオントロジー（意味レイヤー）の対応を先に見せる。

#### スライド 2: 2026 年、二大巨頭が同型の「コンテキストレイヤー」を出した

| | Snowflake | Databricks |
| :--- | :--- | :--- |
| エージェント UI | CoWork | Genie One |
| **意味の自動構築** | **Cortex Sense** | **Genie Ontology（OntoRank）** |
| カタログ | Horizon / Polaris | Unity Catalog |

**一言:** 製品名は違うが、**クエリログ・BI・メタデータからビジネス定義を統計的に裁定する** 同型機能。

#### スライド 3: 仮想グラフ — データを動かさず関係を載せる

| ベンダー | 製品・機能 | 要点 |
| :--- | :--- | :--- |
| **Google Cloud** | BigQuery Graph / Spanner Graph | GQL、DWH・OLTP 双方にグラフ |
| **Snowflake** | Iceberg 連携、Neo4j Virtual Graph | ゼロコピー、RLS 維持 |
| **Databricks** | Lakehouse 上のグラフ連携 | UC ガバナンス下 |
| **Neo4j** | Virtual Graph on Snowflake / Databricks | 専業グラフ DB の「データを動かさない」戦略 |

**商機の 2 本柱（S1 第1部より）:**

1. GraphRAG / エージェントが **関係性** を必要とする  
2. DWH 外への ETL コピーは **ガバナンス崩壊** を招く → 仮想グラフ

#### スライド 4: レイヤー対応表（1 枚に統合）

| レイヤー | 問い | Snowflake | Databricks |
| :--- | :--- | :--- | :--- |
| 辿り方（仮想/物理グラフ） | データをどう辿るか | Iceberg / VG 連携 | Lakehouse / VG |
| 関係・メタデータ | 何が何と関係するか | Horizon | UC メタデータ |
| **意味の構築・裁定** | どの定義を信頼するか | **Cortex Sense** | **Genie Ontology** |
| 型の固定（コアドメイン） | スキーマをどう守るか | dbt / CoCo パイプライン | S1 第3部（Pydantic 等） |

**話すこと:** 仮想グラフは **① 辿り方**、Cortex Sense / Genie Ontology は **③ 定義裁定**。別レイヤーだが、エージェント品質には **両方** 必要。

**図:** `2026-06-24-snowflake-cortex-sense-genie-ontology.md` §5.1 の表をそのままスライド化。

### §2 仮想グラフと物理グラフ（3 分）— スライド 5–7

#### スライド 5: グラフの最小定義

- **ノード** = 実体、**エッジ** = 関係、**プロパティ** = 属性  
- 関係が **第一級市民** → 多ホップ探索が JOIN 連鎖より素直

#### スライド 6: 物理グラフ DB（Native Graph）

- Neo4j 等、**インデックスフリー隣接** でトラバースが速い  
- 代償: 別システム、ETL、ガバナンス二重管理、運用コスト（S1 第1部 §4, 第3部）

#### スライド 7: 仮想グラフ（Virtual Graph）

- **データは DWH に置いたまま**、メタデータでノード/エッジを定義  
- GQL / Cypher → 最適化 SQL にコンパイル（レベル 3 VKG）  
- RLS・列マスクを **ソース側のまま** 継承

**比較 1 行:**

| | 物理グラフ | 仮想グラフ |
| :--- | :--- | :--- |
| 強み | トラバース性能、厳密な型固定 | ガバナンス、既存 DWH 活用 |
| 弱み | コピー・運用 | SQL 変換オーバーヘッド |
| いつ | コアドメイン・高頻度探索 | エンタープライズ分析・GraphRAG 入口 |

**図:** S1 第1部の mermaid（レベル 1–3 VKG）— **レベル 3 だけ** 口頭で触れ、図は簡略版。

### §3 オントロジーとは何か（2 分）— スライド 8–9

#### スライド 8: オントロジー = 意味の設計図（TBox）

- 哲学用語ではなく **「どんな概念があり、どんな関係が許されるか」の契約**  
- 例: `Component` —`USED_IN`→ `Product` は可、`Component` —`SUPPLIES`→ `Invoice` は不可  
- 知識グラフ = 設計図（オントロジー）＋ 中身のデータ（ABox）

#### スライド 9: エンタープライズで効くオントロジーの単位

- 全部を OWL で書く必要はない  
- **コアドメイン**（BOM、サプライチェーン）→ 人間が型を固定（S1 第3部）  
- **全社メトリクス**（売上、MQL）→ 定義が複数あり **裁定** が必要（S3）

**話すこと:** オントロジー推論の難所はアルゴリズムではなく **「誰が定義を書き、どう更新するか」**（S3 前編 §2.1）。

---

### §4 なぜグラフ構造で知識を表し、AI に推論させるか（4 分）— スライド 10–12

#### スライド 10: LLM だけでは足りない理由

| 手法 | 得意 | 苦手 |
| :--- | :--- | :--- |
| ベクトル RAG | 似た文書の検索 | **関係が遠いが業務上つながる** 情報 |
| Text-to-SQL | 即席クエリ | スキーマ誤読・幻覚 SQL |
| Agentic Search | 柔軟な探索 | 大規模構造・RLS・再現性 |

**例:** サプライヤー停止 → 部品 → 製品 → 影響売上（S2 シナリオ）。テキスト類似度では辿れない **ID の連鎖** が必要。

#### スライド 11: グラフが効く 3 つの理由（S1 第2部 §3 要約）

1. **多ホップ探索** — JOIN 爆発を避け、関係を辿る問題に自然  
2. **グラフアルゴリズム** — 最短経路、PageRank、コミュニティ検出を宣言的に  
3. **GraphRAG** — 構造化コンテキストを LLM に渡し、ハルシネーションを抑制

#### スライド 12: 推論の分担（ニューロ・シンボリック）

```text
  [ グラフ / オントロジー ]     決定論的・検証可能
           ↓ グラウンディング
  [ LLM / エージェント ]       柔軟・自然言語・計画
```

- **グラフがあれば推論は後工程**（S3 前編）— ボトルネックは **構築**  
- S2 の教訓: LLM には **決定論的ツール**（検証済み API）の順序だけ任せる

**デモ:** なし（20 分のため）。スライド 1 枚に Cypher/GQL のイメージクエリを載せる程度。

### §5 古典の背景 — 記号 AI の栄光と挫折（3 分）— スライド 13–15

#### スライド 13: 1960–70 年代 — 意味は「関係のネットワーク」

| 系譜 | 代表 | 思想 |
| :--- | :--- | :--- |
| 意味ネットワーク | Collins & Quillian (1969) | `is-a` / `part-of` で概念を結ぶ |
| フレーム | Minsky (1974) | スロット・継承・デフォルト |
| ルールベース | MYCIN | If-Then、後ろ向き推論 |
| 述語論理 | Prolog, DL | **厳密・決定論的** |

**話すこと:** 「ノードとエッジで意味を書く」は **50 年以上前から** ある。LLM 時代も骨格は同じ（S1 第2部 §2）。

#### スライド 14: 2000 年代セマンティック Web の挫折

- RDF / OWL — 人間が **先に全部書く** 前提  
- **知識獲得のボトルネック** — タグ付け・合意・陳腐化  
- 推論エンジンは理論上動くが、**入力がスケールしない**  
- 製薬・医療以外は表舞台からフェードアウト

**要点:** 技術が間違っていたのではなく、**定義の供給設計** が現実と合わなかった。

#### スライド 15: 二つの AI — 厳密さと柔軟性

| | 記号 AI（古典） | ニューラル AI（現代） |
| :--- | :--- | :--- |
| 出力 | 決定論的・検証可能 | 確率的・誤りうる |
| 構築 | 人間がロジックを書く | データから学習 |
| 弱点 | 融通が効かない、獲得コスト | ハルシネーション、再現性 |
| 関係 | **補完** — 現代は古典の「骨格」で LLM の厳密さを補う |

**話すこと（依頼の核心）:** 記号 AI は「死んだ」のではなく、**エージェントの信頼性レイヤー** として再配置されている。

### §6 現代 — 自動オントロジーと同型の再挑戦（2.5 分）— スライド 16–17

#### スライド 16: 第三の道（S3）

| 道 | 内容 | 限界 |
| :--- | :--- | :--- |
| ① 人力オントロジー | ドメインエキスパートが全部書く | メンテナンス破綻 |
| ② Text-to-SQL 丸投げ | LLM に任せる | 定義誤り・幻覚 |
| **③ 統計的構築** | クエリログ・BI から定義を抽出し **ランキング** | シグナルが貧弱だと矛盾を増幅 |

**OntoRank / Cortex Sense の共通型:**

- オントロジー snippet の自動抽出  
- **利用統計で「どの定義を信頼するか」裁定**（PageRank 型）  
- セマンティック Web が人力でやろうとしたことを、**行動データ** で再試行

#### スライド 17: 過去との同型性（1 枚表）

| 2000 年代の壁 | 2026 年の答え |
| :--- | :--- |
| 人間が RDF/OWL を書く | プラットフォームがログから snippet 抽出 |
| どの定義が正か合意できない | OntoRank / Cortex Sense が統計裁定 |
| 陳腐化 | 利用行動に追従（ただしシグナル品質が前提） |

**注意 1 文:** 魔法ではない。財務と営業で「売上」定義が矛盾したままなら、自動構築は **学習して増幅** しうる（S3 後編 §4）。

### §7 三層スタックと takeaway（1.5 分）— スライド 18–19

#### スライド 18: 全部自動 / 全部人力 ではない

```text
[ ③ プラットフォーム・コンテキスト層 ]  Genie Ontology / Cortex Sense
[ ② 組織フェデレーション層 ]              Bridge Keys + Graph Contract（S2）
[ ① コアドメイン層 ]                      Pydantic・BOM 型固定（S1 第3部）
```

- **③** は PF に委ねられる領域が広がった  
- **①②** はドメインエキスパートとアーキテクトが設計・合意

#### スライド 19: まとめ

1. 主要 PF は **仮想グラフ（辿り方）** と **自動オントロジー（定義裁定）** を同時に押している  
2. グラフは **関係性・多ホップ・決定論的制約** のためにエージェントに必要  
3. 記号 AI の知識表現は **LLM の補完** として復権している  
4. 自動オントロジーは **知識獲得ボトルネック** への再挑戦 — 入力がログになった点が新しい  
5. 設計の本体は **どこまで統計に任せ、どこから人間が固定するか**
