## 付録 F′. 自動でも人間の設計は不要にならない — 具体化

**問い:** オントロジーが自動構築されるなら、セマンティックビューや「ビジネス意味 ↔ 物理テーブル」のマッピングは全部不要か？

**答え:** **まだ過渡期。PF が完全自動で完結するわけではない。**  
プラットフォームがうまくオントロジーを構築できるよう **支援する仕事** と、人間が目的・意図から **トップダウンで仕組みに押し込む仕事** の両方が残る。

### 1. ボトムアップ側 — 「機械がうまく推定できるように支援する」

PF（Sense / Genie）は、カタログに溜まった **観測可能なシグナル** を材料に権威を推定する。材料が貧弱・矛盾だと、矛盾した定義を学習して増幅する（S3）。だからエンジニア／ガバナンスの仕事は「自動化を待つ」ではなく **入力を整える**。

| 必要なこと | 具体例 | 主担当の目安 |
| :--- | :--- | :--- |
| **シグナルが溜まる設計** | 分析・ETL がカタログ配下で実行される／クエリログが取れる経路にする | DE / 基盤 |
| **カタログを空洞にしない** | テーブル・カラムの説明、オーナー、セマンティックビューの登録 | DE / ドメイン |
| **認証アセット（certified）を増やす** | 「これが公式の売上定義」とマークしたビュー・メトリクスを用意する | ガバナンス / DE |
| **BI・Measure を正の信号にする** | 経営が見るダッシュボードの定義をエージェントが参照できるよう揃える | DE / BI |
| **矛盾シグナルの監視** | 財務と営業で別「売上」が同じ頻度で使われていないか。貧弱なら自動裁定を信じない | DE / AI |
| **権限・マスキングの整備** | 裁定結果がエージェント経路でも RLS を破らない | 基盤 / セキュリティ |
| **鮮度の運用** | 使われない定義・古いビューを退役させ、権威計算が腐らないようにする | DE / ガバナンス |

**口頭:** 「完全自動ではなく、**自動化が効く土台を人が作る**。Google にリンクが無いページと同様、シグナルが無いと権威は推定できない。」

### 2. トップダウン側 — 「目的・意図を仕組みに押し込む」

利用統計は「いま何が使われているか」は教えても、「何を正しいとするべきか／壊してはいけないか」は、競争領域では人が決める必要がある。

**系譜の読み:** これは新しい「AI 専用の仕事」というより、昔からある **エンタープライズアーキテクト（EA）／データアーキテクト／データマネジメント** の仕事に近い。意味の定義、意味↔物理のマッピング、マスタと制約、組織横断の合意——を、エージェント時代の成果物（認証ビュー・スキーマ契約・Graph Contract・ツール境界）に載せ直している、と説明できる。

| 必要なこと | 具体例 | 従来の近い役割 | いまの主担当の目安 |
| :--- | :--- | :--- | :--- |
| **意図の表明** | 「この製品では税抜出荷ベースの売上だけを正とする」等の方針 | データスチュワード／業務オーナー | ドメイン / PdM |
| **コアドメインの契約** | BOM・部品関係など損失直結の型・制約を Pydantic 等で固定（層①） | データアーキテクト／モデリング | DE |
| **結合の合意** | Bridge Keys・Join 順・Graph Contract（層②） | EA／統合アーキテクト | DE / アーキ |
| **エージェントの柵** | 生 SQL 自由生成を禁止し、決定論的ツールだけ渡す | （新）＋既存のアクセス制御の延長 | AI |
| **グラウンディング** | 回答をツールエビデンスに接地し、逸脱時はフォールバック | （新）品質保証の延長 | AI |
| **どこまで統計に任せるかの線引き** | 全社メトリクスは③、競争領域マスタは① — を文書化 | EA／データガバナンス | DE + AI + ドメイン |
| **意図の機械可読化** | 方針を YAML／スキーマ／認証ビューとして **カタログとアプリに載せる** | データマネジメント（カタログ・メタデータ） | DE |

**口頭:**

> トップダウンは会議だけで終わらせない。**意図をコードとカタログに押し込む。**  
> 中身は、昔の EA・データアーキ・データマネジメントがやってきたことを、エージェント向けの契約とカタログに載せている、と捉えると分かりやすい。AI エンジニアが全部新発明する話ではない。

### 3. 二つは対立ではなく役割分担

```text
  [トップダウン] 意図・契約・柵を人が書く
        │ 認証ビュー／スキーマ／Graph Contract／ツール定義
        ▼
  [ボトムアップ支援] シグナル・カタログ・鮮度を整える
        │
        ▼
  [PF 自動オントロジー] 利用統計で定義を裁定・エージェントへ注入
        │
        ▼
  [監視] 矛盾増幅・誤答 → 線引きとシグナルを見直す
```

Google 知識グラフも **自動化とキュレーションが併存** していた、と同型。  
この具体化が、そのまま **I（三層）** の中身になる。

## 3.1 語りの入口（2025後半〜2026半ば → なぜ驚いたか）

発表の冒頭〜第1節で使う **個人の動機ストーリー**。スライドの箇条書きではなく、口頭でつなぐ軸。

**時期:** 2025 年後半〜2026 年半ば（現場の支援と、ベンダー発表が重なる期間）。

### 時系列の骨格

1. **自分の現場（2025後半〜）** — 本業で、生産性向上・コスト最適化を目的とした知識グラフ構築チームを支援していた。対象は設計・部品・工程・物流など広範囲。複数のグラフが並行で作られ、設計時のコスト構造改善やサプライチェーン影響分析などに取り組んでいた。
2. **当時の仮説** — 知識グラフがちゃんとできていれば、ない状態より **探索・推論しやすい**。論点は「LLM だけで推論するか」ではなく、**関係が載ったグラフをどう用意するか** に寄っていた。
3. **拠り所としてのオントロジー** — その知識グラフが **適切に構築されているか** の拠り所がオントロジーである、と考えていた。
4. **壁** — しかしオントロジーを **手動で作るのは現実的ではない**、と感じていた。産業界で確立したオントロジーを参考にする案もあると聞いたが、業界オントロジーは **抽象的すぎる**。社内業務に寄せた内容が必要だが、**誰が・どう構築するのか**。DWH のドメインモデリングと同じ難しさ。
5. **2026 年前後の出来事** — Databricks と Snowflake が、オントロジーを **自動構築** する機能を発表した（Genie Ontology / Cortex Sense）。エージェントが自社データを理解できるようにする動き。
6. **驚き** — 自分が現場で抱えていた「意味の層をどう作るか／手動では無理では」の問いが、最大手の製品機能として前面に出てきた。

### 話すときの一言（要約）

> グラフがちゃんとあれば探索・推論はしやすい。その「ちゃんと」の拠り所がオントロジーだが、手動構築は現実的ではない——と考えていたところに、2025後半〜2026半ば、Databricks / Snowflake の自動オントロジーが来た。

### 使い方

- **§0 スライド 2–3** で「なぜ話すか／トピック／誰にいつ必要か」を明示する（詳細骨格は本節）。
- **§1** では製品対応表に入り、動機の再朗読はしない。
- 業界名・顧客名・秘匿グラフ構造は出さない。領域は「設計・部品・工程・物流／コスト最適化」程度に留める。

## 3.2 用語の説明（口頭必須）— グラフ / 知識グラフ / オントロジー

動機ストーリー（§3.1）で「知識グラフ」「オントロジー」を使う前か直後に、**聴衆が同じ言葉で聞けるよう** に短く定義する。詳細は §2・§3 のスライドで補強。

### 一言ずつ

| 用語 | 口頭での定義 | たとえ |
| :--- | :--- | :--- |
| **グラフ（一般）** | **ノード（点）とエッジ（線）** で関係を表すデータ構造。中身が何であるかは問わない | 友人関係のネットワーク、道路の接続図 |
| **知識グラフ** | グラフのうち、**業務・世界の知識**（実体とその意味のある関係）を載せたもの。型付きのノード／エッジで「何が何とどう関係するか」を表現する | 「部品 A は製品 B に使われ、サプライヤー C が供給する」 |
| **オントロジー** | 知識グラフの **設計図・契約**。「どんな概念があり、どんな関係が許されるか」。中身のデータそのものではない | RDB でいうスキーマ／制約に近い |

### 「ただのグラフ」との違い（話すときの対比）

- **ただのグラフ** — 構造だけ（点と線）。ソーシャルグラフも道路網も「グラフ」  
- **知識グラフ** — その構造に **意味のある実体と関係** が載っている。「誰が誰を知っている」ではなく、「どの部品がどの製品に使われ、誰が供給するか」のように、**ドメイン知識として辿れる**  
- したがって現場で「グラフを作る」と言うとき、多くは **知識グラフ（意味付き）** を指している。単なるトポロジー図ではない

### オントロジーと知識グラフの関係（TBox / ABox）

連載（S1 第2部）と同じ整理:

- **オントロジー（TBox 寄り）** — ルール・設計図。例: `Component` —`USED_IN`→ `Product` は可、無関係な型同士の接続は不可  
- **知識グラフ（ABox 寄り／実データ）** — 設計図に従って入れた具体例。例: 部品 `COMP-101`、製品 `PROD-901`、その間のエッジ  
- **関係:** オントロジーが「正しく構築されているか」の **拠り所**。知識グラフはオントロジーに沿った **実体のネットワーク**

> 口頭の型: 「グラフは構造。知識グラフは意味を載せた構造。オントロジーはその意味の設計図です。」

### どこで言うか

| タイミング | 深さ |
| :--- | :--- |
| §1 動機の直後（任意・15秒） | 上の「口頭の型」だけ |
| **§2 スライド 5** | グラフの最小定義 ＋ 「知識グラフとの違い」1行 |
| **§3 スライド 8** | オントロジー＝設計図、知識グラフ＝設計図＋データ |

**避ける:** OWL / RDF / TBox・ABox の用語説明に深入り（必要なら「設計図／データ」と言い換える）。哲学的「存在論」の話。

## 3.3 なぜ知識グラフが必要か（RDB・ベクトル・相互リンク MD では足りないとき）

多くの人が RAG に使うのは **ベクトル DB**、**RDB（＋セマンティック層）**、**相互リンクした Markdown**。それでも知識グラフが話題になる理由を、口頭では **二段** に分ける。

### A. わかりやすい理由 — 問題構造そのものがグラフ

金融・製造・サプライチェーンなど、業務の問いがもともと **関係の連鎖** である場合。

- 例: サプライヤー停止 → 部品 → 製品 → 影響売上  
- アプリ／分析のバックエンドとして、その関係を引く **DB（物理グラフ or 仮想グラフ）** が必要になる  
- 「なぜグラフか」は直感的に説明できる。**ここは押しやすい**

### B. それ以外に、知識グラフが要る場合はあるか

ある。ただし **「RAG なら必ず KG」ではない**。次のような **問いの形／エージェント要件** が出たとき、ベクトル・固定 SQL・Wiki リンクだけでは足りなくなる。

| 要件 | ベクトル / MD リンク | RDB（固定 SQL・セマンティック層） | 知識グラフ（関係レイヤー） |
| :--- | :--- | :--- | :--- |
| 似た文書を探す | 得意 | 不得意 | 必須ではない |
| 事前に決めた集計（先月の粗利） | 苦手 | 得意 | 必須ではない |
| **アドホックな多ホップ**（止まっていない経路をその場で辿る） | 苦手（類似度≠関係） | JOIN 連鎖・テンプレが破綻しやすい | **得意** |
| **関係の正しさで回答を縛る**（グラウンディング） | 弱い | 集計結果までは強いが経路説明は弱い | **経路・エビデンスを残せる** |
| **部門横断の ID 連鎖**（Bridge Key で論理結合） | ほぼ扱えない | 可能だが探索 UX が重い | **フェデレーション向き** |
| 説明可能性・監査（なぜその答えか） | 近傍文書の列挙 | クエリ結果 | **辿ったエッジの列挙** |

**口頭で言う「それ以外の理由」の核:**

1. **問いが関係探索型** — 「似ている文書」ではなく「つながっている実体」を辿る必要がある  
2. **エージェントの信頼性** — LLM の要約を、ツールが返した **構造化エビデンス（ノード ID・経路）** に接地したい（グラウンディング）  
3. **意味の契約** — オントロジー／Graph Contract で「辿ってよい関係」を決め、勝手な結合や幻覚経路を防ぐ  
4. **置き場はグラフ DB 専用とは限らない** — DWH 上の仮想グラフでもよい。必要なのは **関係を第一級で扱うモデル** であり、必ずしも Neo4j への全コピーではない

### 正直な境界（聴衆への誠実さ）

- FAQ・規程・手順書の意味検索だけなら、**ベクトルや相互リンク MD で十分なことが多い**  
- 定型 KPI だけなら、**RDB／セマンティック層で十分なことが多い**  
- 知識グラフが効くのは、**(A) ドメインが関係構造** か、**(B) エージェントが関係を辿り・根拠を残す必要がある** とき  
- GraphRAG は ①② の **上に載せる関係レイヤー** であり、ベクトルや RDB を捨てる話ではない（S1 第2部）

### 話すときの一言（要約）

> 問題がもともとグラフなら、知識グラフはアプリの DB として自然です。それ以外でも、多ホップの関係探索やエージェントのグラウンディングが要件になると、ベクトルや Wiki リンクだけでは足りなくなります。逆に、それがないなら無理に知識グラフにしなくてよい。

### どこで言うか

- **§4 スライド 10–11** の主メッセージにする（対比表の「なぜ足りないか」）  
- §3.1 の動機では深入りしない（時間があれば「だから探索用のグラフが要る」と一文）

## 3.4 なぜオントロジーが必要か — 自分の解釈と時代・PF の違い

### 自分の解釈（2025後半〜現場）

| | 役割 |
| :--- | :--- |
| **オントロジー** | スキーマ・型・制約などの **概念／契約**（何が存在してよいか、どう結んでよいか） |
| **知識グラフ** | その契約に沿った **実態（インスタンス）** |

**主用途:** 実態である知識グラフが **適切に構築されているか／更新されているか** を判断する **拠り所**。書き込み拒否・ロード後監査・ドリフト検知の物差し（シーズン4 の「契約」観）。

### それ以外にあるか（自分の解釈の拡張）

拠り所以外にも、同じ「契約」から派生する用途はある。ただし **主役は品質の物差し** でよい。

| 派生用途 | 内容 |
| :--- | :--- |
| **探索の安全柵** | エージェント／ツールが辿ってよい関係のホワイトリスト（決定論的ツール） |
| **部門横断の結合契約** | Bridge Key・Join 規則（Graph Contract）。単一グラフの型定義の延長 |
| **回答グラウンディングの前提** | 「正しい経路のエビデンス」を返すには、まずグラフが契約どおりである必要がある |
| **共有語彙** | 部門・ツール間で同じラベルを指す（L0）。これがないと検証も結合も始まらない |

口頭では: 「まず品質の拠り所。その延長で探索の柵と結合の合意にもなる。」

### 古典的 AI・セマンティック Web では何を意味したか

同じ「オントロジー」でも、**何のために要るか** が違う。

| 時代 | オントロジーの主目的 | 知識グラフ／知識ベースとの関係 | 典型的な約束 |
| :--- | :--- | :--- | :--- |
| **古典的記号 AI**（意味ネット・フレーム・DL） | **推論の材料** — 公理から未知の事実を導く | スキーマと事例が一体の知識ベースが多い | Reasoner が「知らない関係」を補完できる |
| **セマンティック Web**（RDF/OWL） | **機械可読な共有意味** — Web／組織をまたいで語彙と公理を共有 | TBox（用語）と ABox（事例）を分離して語ることが多い | オープンな結合・推論。OWA（書いてない＝偽とは限らない） |
| **自分（現場 KG）** | **構築・更新の正しさの契約** | オントロジー＝物差し、KG＝実態 | CWA 寄り。契約外は拒否。暗黙推論（L5）は採らない |

**挫折の型（セマンティック Web）:** 推論エンジンより先に、**人間が定義を書き続けること** がスケールしなかった（知識獲得ボトルネック）。自分の「手動は現実的ではない」は、この歴史と同じ痛み。

### 2026 年 Databricks / Snowflake の解釈

Genie Ontology（OntoRank）／Cortex Sense が言う「オントロジー」に近いもの:

- DWH 上の **ビジネス定義・メトリクス・結合候補** を、クエリログ・BI・カタログから **自動抽出し、利用統計で裁定** する  
- 目的は主に **分析エージェント（Genie / CoWork）が自社データを誤解しないこと** — 「売上」のどれか、どのテーブルを結ぶか  
- 出力は **コンテキスト／セマンティックレイヤー**（エージェントへの注入）。製造 BOM の LPG を書き込み時に拒否する「契約エンジン」そのものではない

### 自分 vs PF 2026 — どこが同じで、どこが違うか

| | **自分の解釈** | **Databricks / Snowflake 2026** |
| :--- | :--- | :--- |
| **解く問い** | この知識グラフは契約どおりか。壊れていないか | エージェントはどのビジネス定義を信じるか |
| **オントロジーの中身のイメージ** | 型・エッジ制約・結合契約（スキーマ／品質） | メトリクス定義・エンティティ対応・推奨 join（意味のスニペット） |
| **主な消費者** | インジェスト・監査・決定論的探索ツール | CoWork / Genie / Cortex Agents |
| **正しさの出し方** | 人間（またはコード）が契約を先に置き、データが従う | 利用行動から定義を **ボトムアップ推定・ランキング** |
| **失敗モード** | 契約が古い／現場と乖離 | シグナルが貧弱だと **矛盾した定義を学習して増幅** |
| **同じ点** | 「意味の層がないとエージェントは信頼できない」「全部を人手で書き続けるのは破綻する」 | 同左 |
| **違う点** | **グラフ実態の品質証明** が主戦場 | **定義の発見と裁定** が主戦場 |

**口頭の型（差を一言で）:**

> ベンダーの自動オントロジーは「どの定義をエージェントに渡すか」の話。自分の現場では「知識グラフという実態が契約どおりか」の物差しとしてのオントロジーが先にあった。言葉は同じでも、主に解いている問題が違う。重なるのは「意味の層がボトルネック」という診断だけだ。

### スライドへの落とし込み

- **§3 スライド 8–9:** 自分の解釈（設計図＝拠り所）＋ コアドメインは人が型固定／メトリクスは裁定、の二段  
- **§6 スライド 16–17:** PF は「定義の自動裁定」。自分の契約観との **同型（人手限界）と差分（品質 vs 裁定）** を 1 文で言う  
- **§7 三層:** ①コアドメイン（自分寄り・人が固定）②フェデレーション ③PF コンテキスト（Sense / Genie）— ここで差分を視覚化

## 3.5 なぜ昔は普及しなかったか／なぜ今また着目か／誰が着目しているか

§5–§6 の口頭用の骨格。技術史の細部より **普及しなかった理由 → 再着目の条件 → 主体** をはっきり言う。

### なぜ普及しなかったか

技術が「間違っていた」というより、**供給と需要の両方が揃わなかった**。

| 要因 | 古典的記号 AI | セマンティック Web（2000年代） |
| :--- | :--- | :--- |
| **知識獲得** | 専門家がルール・フレームを手書き。ドメインが広がると破綻 | RDF/OWL を人間が先に全部書く前提。タグ付け・合意・陳腐化で **知識獲得ボトルネック** |
| **計算・運用** | 大規模では推論・保守が重い | OWL 厳密推論は計算量爆発。エンタープライズ規模に乗らない |
| **需要側** | エキスパートシステム等の閉じた用途。全社データ基盤の必須部品ではなかった | 「機械が Web を理解する」ビジョンは壮大だが、**誰のどのプロダクトが毎日困っているか** が弱い |
| **残った領域** | 限定ドメイン | 製薬・医療など、厳密統制が義務の分野に縮小 |

**口頭の一文:**  
> 推論エンジンより先に、**定義を書き続ける人間** がスケールしなかった。需要も「全社の必須」までは届かなかった。

### なぜ今、再度着目されているか

昔の壁が消えたのではなく、**需要が先に立ち上がり、供給側に新しい手段ができた**。

| 変化 | 内容 |
| :--- | :--- |
| **需要: AI エージェント** | 「売上はどれか」「どのテーブルを結ぶか」を知らないと、LLM がいくら賢くても誤答する。**意味の層がエージェント品質のボトルネック** になった |
| **需要: ハルシネーション対策** | 類似検索だけでは関係の正しさを保証できない。決定論的な関係・制約・経路エビデンスが欲しい |
| **供給: LLM による下書き** | 人手でゼロから書く代わりに、スキーマ・テキスト・ログからマッピングを半自動で起こせる（検証は残る） |
| **供給: PF の自動オントロジー** | クエリログ・BI・カタログから定義を抽出し、利用統計で裁定（OntoRank / Cortex Sense）。セマンティック Web が人力でやろうとしたことを **行動データ** で再試行 |
| **供給: 仮想グラフ／レイクハウス** | データをコピーせず関係を載せる選択肢が増え、ガバナンスと両立しやすい |
| **思想の再配置** | OWL 全盛の「全世界を公理で書く」ではなく、**LLM（柔軟）＋グラフ／オントロジー（厳密）の補完**。記号 AI の復権というより **信頼性レイヤーとしての再配置** |

**口頭の一文:**  
> エージェントが現場に入ったことで「意味がないと困る」が先に来た。書き方は、全部人力から、統計・LLM 支援・契約のハイブリッドに変わった。

### 誰が着目しているか

| 主体 | 何を求めているか | 自分の解釈との距離 |
| :--- | :--- | :--- |
| **クラウド PF**（Snowflake, Databricks, Google 等） | 分析エージェント向けの **定義裁定・仮想グラフ／関係の辿り方** | 「どの定義を渡すか」に近い（§3.4） |
| **グラフ専業**（Neo4j 等） | DWH 連携の仮想グラフ、GraphRAG、運用グラフ DB | 物理／仮想の置き場の話 |
| **エンタープライズ基盤**（例: Palantir Ontology） | 物理テーブル上の **ビジネスオブジェクトと関係の論理層** | 意味の記述子としては近い先行例 |
| **業務で KG を組む現場**（製造・金融・SC 等） | 実態グラフの構築・保守、型・制約による品質 | **自分の主戦場**（契約＝拠り所） |
| **MLOps / AI エンジニア** | エージェントの誤答・再現性・グラウンディング | 「モデル以外のコンテキスト基盤」として必要になる |
| **データエンジニア／ガバナンス** | セマンティック層、認証アセット、定義の単一の正 | PF のシグナル品質・コアドメイン固定と接続 |
| **学術・標準（W3C 等）** | RDF/OWL/SHACL は存続。主役は「全社必須」から **部品・監査言語** へ | L5 推論は任意、SHACL 等の検証用途は残る |

**聴衆向けの一言:**  
> 着目しているのは研究者だけではない。**エージェントを売る／使う側**（PF・現場・MLOps）が、意味の層なしでは品質が出ないと気づいた。

### スライドへの落とし込み

| スライド | 言うこと |
| :--- | :--- |
| §5 スライド 16 | 普及しなかった理由 = 知識獲得＋需要不足（計算は副因） |
| §5 スライド 17 | 死んだのではなく再配置 |
| §6 スライド 18–19 | 今着目 = エージェント需要＋統計的供給。誰が = PF／現場／MLOps |
| §0 スライド 3 | 「必要なとき」と接続（エージェント・定義揺れ・多ホップ） |

### §4 なぜグラフ構造で知識を表し、AI に推論させるか（3 分）— スライド 10–12

**目的:** 「ベクトル・RDB・相互リンク MD で十分な人が多いのに、なぜ知識グラフか」に答える。詳細は §3.3。

#### スライド 12: 他手法との役割分担（足りないとき）

| 手法 | 得意 | 苦手／限界 |
| :--- | :--- | :--- |
| ベクトル RAG | 似た文書の検索 | **関係が遠いが業務上つながる** 情報（類似≠関係） |
| RDB / セマンティック層 | 定型集計・整合性 | アドホックな多ホップで SQL・テンプレが破綻しやすい |
| 相互リンク Markdown | 人間が書きやすいゆるい関係 | 大規模・厳密な ID 連鎖・再現性 |
| **知識グラフ** | **関係の連鎖・経路の説明・制約付き探索** | 構築・保守コスト（オントロジー） |

**話すこと（二段）:**

1. **わかりやすい側 (A):** 製造・金融・サプライチェーンなど、問題構造がグラフ → アプリ／分析のバックエンド DB として自然  
2. **それ以外 (B):** それでも要るのは、問いが **多ホップ関係探索** か、エージェントが **経路エビデンスでグラウンディング** したいとき。FAQ 検索や定型 KPI だけなら KG 必須ではない

**例:** サプライヤー停止 → 部品 → 製品 → 影響売上（S2）。テキスト類似度では辿れない **ID の連鎖**。

#### スライド 13: グラフが効く 3 つの理由（S1 第2部 §3 要約）

1. **多ホップ探索** — JOIN 爆発を避け、関係を辿る問題に自然  
2. **グラフアルゴリズム** — 最短経路、PageRank、コミュニティ検出を宣言的に  
3. **GraphRAG / グラウンディング** — 構造化コンテキストと経路を LLM に渡し、ハルシネーションを抑制  

**補足 1 行:** 置き場は物理グラフ DB に限らない。**仮想グラフ**でも「関係を第一級で扱う」は満たせる。

#### スライド 14: 推論の分担（ニューロ・シンボリック）

```text
  [ グラフ / オントロジー ]     決定論的・検証可能
           ↓ グラウンディング
  [ LLM / エージェント ]       柔軟・自然言語・計画
```

- **グラフがあれば探索・推論は後工程**（S3 前編）— ボトルネックは **構築**  
- S2 の教訓: LLM には **決定論的ツール**（検証済み API）の順序だけ任せる  
- §3.1 へ戻す: だから「手動オントロジーは現実的ではない」が痛かった → 自動構築への驚き

**デモ:** なし（20 分のため）。スライド 1 枚に Cypher/GQL のイメージクエリを載せる程度。

### §5 古典の背景 — 記号 AI の栄光と挫折（3 分）— スライド 15–17

**目的:** 「なぜ昔は普及しなかったか」を言い切る。詳細は §3.5。

#### スライド 15: 1960–70 年代 — 意味は「関係のネットワーク」

| 系譜 | 代表 | 思想 |
| :--- | :--- | :--- |
| 意味ネットワーク | Collins & Quillian (1969) | `is-a` / `part-of` で概念を結ぶ |
| フレーム | Minsky (1974) | スロット・継承・デフォルト |
| ルールベース | MYCIN | If-Then、後ろ向き推論 |
| 述語論理 | Prolog, DL | **厳密・決定論的** |

**話すこと:** 「ノードとエッジで意味を書く」は **50 年以上前から** ある。LLM 時代も骨格は同じ（S1 第2部 §2）。

#### スライド 16: なぜ普及しなかったか（セマンティック Web を含む）

- RDF / OWL — 人間が **先に全部書く** 前提  
- **知識獲得のボトルネック** — タグ付け・合意・陳腐化（主因）  
- 推論の計算量爆発（副因）  
- **需要** が「全社データ基盤の必須」まで届かなかった  
- 製薬・医療など厳密統制が義務の領域に縮小  

**要点:** 技術が間違っていたのではなく、**定義の供給設計と需要** が現実と合わなかった（§3.5）。

#### スライド 17: 二つの AI — 厳密さと柔軟性

| | 記号 AI（古典） | ニューラル AI（現代） |
| :--- | :--- | :--- |
| 出力 | 決定論的・検証可能 | 確率的・誤りうる |
| 構築 | 人間がロジックを書く | データから学習 |
| 弱点 | 融通が効かない、獲得コスト | ハルシネーション、再現性 |
| 関係 | **補完** — 現代は古典の「骨格」で LLM の厳密さを補う |

**話すこと（依頼の核心）:** 記号 AI は「死んだ」のではなく、**エージェントの信頼性レイヤー** として再配置されている。

### §6 現代 — 自動オントロジーと同型の再挑戦（2.5 分）— スライド 18–19

#### スライド 18: 第三の道（S3）＋ 誰が着目しているか

| 道 | 内容 | 限界 |
| :--- | :--- | :--- |
| ① 人力オントロジー | ドメインエキスパートが全部書く | メンテナンス破綻 |
| ② Text-to-SQL 丸投げ | LLM に任せる | 定義誤り・幻覚 |

**OntoRank / Cortex Sense の共通型:**

**誰が着目か（口頭で列挙）:** クラウド PF ／ グラフ専業 ／ 業務で KG を組む現場 ／ MLOps・DE。研究者だけではなく **エージェントを売る・使う側**。

#### スライド 19: 過去との同型性（1 枚表）

| 2000 年代の壁 | 2026 年の答え |
| :--- | :--- |
| 人間が RDF/OWL を書く | プラットフォームがログから snippet 抽出 |
| どの定義が正か合意できない | OntoRank / Cortex Sense が統計裁定 |
| 陳腐化 | 利用行動に追従（ただしシグナル品質が前提） |
| 需要が弱い | **エージェント品質 = 意味の層** がプロダクト課題に |

**注意 1 文:** 魔法ではない。財務と営業で「売上」定義が矛盾したままなら、自動構築は **学習して増幅** しうる（S3 後編 §4）。

**話すこと（§3.4 の差分・15秒）:** PF の自動オントロジーは **「どの定義をエージェントに渡すか」**。自分の現場のオントロジーは **「知識グラフという実態が契約どおりか」** の物差し。診断（意味の層がボトルネック／人手は破綻）は同じだが、主戦場が違う。

### §7 三層スタックと takeaway — DE/AI の位置づけ（約2分）— スライド 18–19

**目的（ゴール4）:** 普及していくオントロジー自動構築を、自社開発でどう置くか。

#### スライド 20: 全部自動 / 全部人力 ではない（三層）

```text
[ ③ プラットフォーム・コンテキスト層 ]  Genie Ontology / Cortex Sense
[ ② 組織フェデレーション層 ]              Bridge Keys + Graph Contract
```

| 層 | 誰が主に見るか | やること |
