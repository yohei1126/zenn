## 第1部：読みづらい・理解しづらい点

### 強み

- §2 の三ドメイン表と Mermaid は、製造業に詳しくない読者にも状況が伝わる
- §3 の有事シナリオ → ASCII パス図 → 手作業分析の限界、という流れがよい
- §5 Text-to-SQL/Cypher の限界は、第2部の「ツール境界」への伏線として機能する

### 改善したい点

#### ① §6 が設計編の内容に踏み込みすぎ

第1部の締め（§6）で、解決策の核心（Bridge Keys + クエリ時結合）と **シーケンス図まで** 出ている。背景編としてはやや先走りで、第2部との差が薄れる。

**修正案:**

- §6 は「**物理分離・論理結合という方向性だけ**」に留め、シーケンス図は第2部へ移す
- または §6 を「**次回予告**」に短縮

#### ② §3.1 のエッジ方向がやや分かりにくい

```
Product Y ◄──(USED_IN)── Component A
```

`USED_IN` の向き（Component が Product に使われる）を、初見の人は一瞬迷う。第2部と同様、**上から下へ流れる一方向** の図に揃える。

#### ③ §4.2 RDB の限界がやや唐突

グラフDB統合の話の直後に RDB JOIN の話が入り、焦点が散る。

**修正案:** 「**統合の選択肢は物理グラフ統合だけではない**」と1文足すか、§4 冒頭に小見出し「統合アプローチの比較（3択）」として整理。

#### ④ 「シーズン2」とシリーズ名の関係

概要で「シーズン2」と書きつつ、シリーズ名は「組織の境界を越えるAIエージェントの知識連携」。message 冒頭で

> 本シリーズ（シーズン2）は…

のように1行明示すると、シーズン1との関係がはっきりする。

#### ⑤ 第2部 message のリンクが「予定」のまま

第1部は `published: true` なのに、第2部が未公開でも URL は既に存在。第1部側の「（予定）」は外すか、公開前なら第2部 URL を載せない。

## 第2部：読みづらい・理解しづらい点

### 強み

- §2 Bridge Keys の表はコンパクトで有用
- §3 Graph Context の4要素は、設計記事としての骨格になっている
- §4 の LLM / 決定論的ツールの ASCII 図は責務分離が伝わる

### 改善したい点

#### ① §1.1 が第1部の再掲（上記「全体 §2」参照）

#### ② §5 ④「運用の容易さ」が実装寄り

Embedded DB（LanceDB 等）の採用理由が **設計編のまとめ** に入っている。これは第3部の技術選定の話。

**修正案:**

- 第2部 §5 ④ は削除 or 「ストレージ選定は第3部で述べる」に1文だけ
- 4つのコア論点は **所有権・セキュリティ・クエリ品質** の3つに絞る

#### ③ 「スキーマ検証モデル」が突然出る（§3.2）

シーズン1第3部を読んでいない人には不明。

**修正案:**

> スキーマ検証モデル（Pydantic 等で型・制約を定義する SSOT。詳細は[シーズン1第3部]）

のような1文を追加。

#### ④ Graph Context とツールのつながりが弱い

§3 で Graph Context（特に Federation Joins）を定義したあと、§4 で決定論的ツールに移るが、

- Federation Joins ＝ ツールの実行順序
- ツール内部 ＝ 名前付きクエリカタログ

という対応が書かれていない。**§4 冒頭に1段落** で橋を架ける。

#### ⑤ 非構造入力（ニュース→アンカリング）がない

第1部 §3.1 ではニュース起点のシナリオを出しているのに、第2部では **ID 起点のフェデレーション** しか設計していない。

**修正案:** §4 に「**3段階パターン**（LLM解釈 → 入口グラフでアンカリング → フェデレーション展開）」を1節追加。

#### ⑥ §3.2 の非同期参照整合性チェックが抽象

**修正案:** 具体例を1つ追加。

> 例：Sourcing に `COMP-999` が追加されたが EBOM に未登録 → 監査アラート

#### ⑦ エッジ所有権の表がない

Bridge Keys 表はある一方、**どのドメインがどのエッジを書けるか**（`SUPPLIED_BY` → Sourcing 等）が第2部にない。§2 か §3 に表を1つ追加。

#### ⑧ §5 表の「エラー率ゼロ」は言い過ぎ

> 決定論的ツールの連鎖によるエラー率ゼロの達成

は信頼性を損なう。「**LLM による ad-hoc クエリ生成エラーを排除**」程度が妥当。

#### ⑨ §4 ASCII 図の文字化け・全角混在

```
│  AIプランナー (LLM)                          　│
│  - ドメイン仕様や制約から手順（Plan）を組み立て.  　│
```

行末の全角スペースや `.` の混在で、プレビューでずれやすい。半角に統一。

#### ⑩ シーズン1第3部のリンク欠落（message L19）

第2部 message だけ第3部に URL がない。第1部・第3部と揃える。

#### ⑪ 組織境界 vs 技術境界の二層がない

「**技術 SSOT（全社） / 組織スライス（チーム） / 横断ランタイム**」の概念図が第2部にない。Bridge Keys と Graph Context の **誰が何を保守するか** がやや曖昧。Mermaid 1枚を §2–§3 に追加。
